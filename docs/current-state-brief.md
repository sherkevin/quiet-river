## 1. 项目是什么

`quiet-river`：把分散在各平台的关注对象汇成**一条按 tag 分组、时间倒序的内容河**。

产品哲学写在 README 第一段，它决定了下面很多取舍：

> 没有推荐算法，没有「猜你喜欢」，没有信息流广告。你关注谁，就看到谁；
> 点了某个 tag，就只看那一类；什么都不点，就是全部混排。

**刻意不做的事**（README 原文，这四条是设计边界不是待办）：

- **不做推荐排序**。时间倒序是唯一排序。
- **不做全文抓取**。只取 feed 提供的标题、摘要、链接、时间、作者、封面。要看全文点进原文。
- **不做账号体系**。数据全在本地文件里，没有服务端状态，没有登录。
- **不做移动端推送**。它是一个你主动打开的页面。

> **注意第 2 条与第 4 条**：新目标（站内阅读 + 划线 + 日报推送）与现有产品边界
> **直接冲突**。这不是「在现有基础上加功能」，是产品定位的扩展。评审新方案时
> 请把这个冲突当作前提，而不是当作可以忽略的历史包袱。

## 2. 代码形态与运行方式

```text
零运行时依赖（不需要 npm install），无构建步骤
Node.js >= 20（用内置 fetch 与 node:test）
约 6500 行 JS，其中前端 1552 行、服务端 442 行、lib 约 2400 行
数据全在两个 JSON 文件里：data/subscriptions.json（配置）+ data/cache.json（抓取结果）
测试 56 个全绿（公开形态）/ 65 个全绿（源码形态）
```

| 文件 | 行数 | 作用 |
|---|---|---|
| `server.js` | 442 | HTTP 服务、API 路由、服务端自动刷新定时器 |
| `lib/resolve.js` | 571 | 平台识别、feed 发现与验证、转发宿主归类 |
| `lib/feeds.js` | 254 | RSS/Atom/JSON Feed 解析、摘要截断 |
| `lib/store.js` | 254 | JSON 读写（临时文件 + rename 保证原子性） |
| `lib/refresh.js` | 211 | 抓取调度、同宿主串行与节流、失败退避 |
| `lib/adapters.js` | 308 | 免凭证适配器 + 私有适配器插件位 |
| `lib/access.js` | 211 | 公网访问口令闸 |
| `lib/xml.js` | 165 | **XML 解析器**（不是生成器，没有序列化能力） |
| `public/app.js` | 1552 | 前端全部逻辑（无框架，原生 DOM） |

关键约束：**`lib/xml.js` 只能解析不能生成**。现在唯一的 XML 输出是
`lib/opml.js`（30 行）里的字符串拼接。任何「导出 RSS」的需求都要新写生成逻辑。

## 3. 数据模型：我们不存正文（最重要的一条）

缓存条目的字段是固定的七个：

```js
{ guid, title, link, author, published, summary, image }
```

**没有 `content` 字段。**实测全量缓存：

| 平台 | 条目数 | `summary` 平均长度 | 带正文字段的条目 |
|---|---|---|---|
| 知乎 | 4176 | 166 字 | **0** |
| feed 类（博客/GitHub/arXiv 等） | 2981 | 225 字 | **0** |
| 小红书 | 253 | 0 字（通道只给标题与封面） | **0** |
| 播客 | 34 | 376 字 | **0** |
| 掘金 | 10 | 83 字 | **0** |
| **合计** | **7474** | 184 字 | **0** |

`summary` 被 `SUMMARY_LIMIT = 400` 硬截断（`lib/feeds.js:6`）。
前端点卡片的行为是 `window.open(link.href, '_blank')`——**跳外部网站**。

体积现状：`data/cache.json` 5.7MB；`/api/state` 单次响应约 4.9MB，
蜂窝网络下首屏已经偏慢（这是已知未修的技术债）。

> **这条决定了「站内阅读全文」是全新建设，不是改造。**任何方案如果假设
> 「我们已经有正文，只要把它导进阅读器」，都是错的。

## 5. 登录态适配器的真实机制与凭证需求

适配器本体不在仓库里（`.gitignore` 排除的 `lib/adapters.private.js`），
存在即自动挂载。这是有意的：**不把某个平台的反爬绕过写成公开代码**，
那等于发布一个绕过工具集，有 ToS 与下架风险。仓库只留插件位与文档。

### 知乎：登录态直连内部 API

```js
// 现有实现（节选，凭证从 gitignored 文件或环境变量读）
const headers = { Cookie: cookie, Referer: `https://www.zhihu.com/people/${token}` };
await get(`https://www.zhihu.com/api/v4/members/${enc}/answers?limit=20&offset=0` +
          `&include=data[*].excerpt,created_time,question`, { headers });
```

- 两路请求（`articles` + `answers`）各 20 条，按 `published` 合流排序。
  理由：技术内容大多在回答里，只抓专栏会把好博主判成空的。
- 两次请求之间强制 sleep 1.5 秒。
- 凭证只需要**一个登录态 cookie 字段**（知乎的 `z_c0`，HttpOnly，
  只能从浏览器 Network 面板的请求头里整段复制，`document.cookie` 读不到）。
- **请求的是 `excerpt`（摘要），不是 `content`（正文）**——见 §3。

### 小红书：驱动本机已登录浏览器

```js
// 现有实现（节选）：shell 出去调一个本机 CLI，解析它的 JSON
execFile('<本机浏览器驱动 CLI>', ['xiaohongshu', 'user', id, '--limit', '20', '-f', 'json']);
```

- **不读 cookie 文件**。该平台的登录态绑在浏览器会话上，cookie 寿命极短且导不出来，
  所以适配器调用一个能驱动本机已登录浏览器的 CLI 取数。
- 该通道只返回 `{id, title, type, likes, cover, url}`：**没有昵称，没有正文**。
  所以 `author` 留空（添加时要人工填名字），`summary` 为空串。
- 发布时间是解码出来的：**note id 前 8 位 hex 就是 Unix 秒**（已解码验证），
  因为列表接口不返回时间。这是本项目「拿不到发布时间就不写适配器」硬约束下的产物。

### 节流参数（实测得来，不是猜的）

```js
// lib/refresh.js
HOST_MIN_GAP_MS    = { 'adapter:zhihu': 8000, 'reddit.com': 60000, ... }
HOST_MIN_RECHECK_MS = { 'adapter:zhihu': 6*60*60*1000, ... }
MAX_CONSECUTIVE_FAILS = 3   // 连续失败 3 次，自动刷新跳过该源
KEEP_ITEMS = 60             // 每源最多保留 60 条
CONCURRENCY = 4             // 同宿主串行，跨宿主最多 4 并发
```

知乎那两个数字的来历：**约 17 次请求 / 15 秒就 403**（2026-09-11 实测）。
光调请求间隔治不了根（14 个源每轮就是 28 个请求），所以加了 6 小时最小重抓周期——
文章与回答不是按分钟变的，一天抓几次足够。**手动「刷新」也尊重这个周期**，
这是有意取舍不是 bug。

> 同宿主串行只保证不并发，不保证不打得太密。这句话在代码里写过两次，
> 第二次是给第三方转发宿主加节流时（见 §8）。

## 6. 部署拓扑：三个形态同时在线

| 形态 | 机器 | 托管 | 地址 | 活的程度 |
|---|---|---|---|---|
| 原机 | Mac | launchd（KeepAlive） | `127.0.0.1:4321` | 全活（含登录态源） |
| 公网 | 阿里云 ECS，北京，**2C2G**，Ubuntu 24.04 | systemd（专用用户 + `CAP_NET_BIND_SERVICE`） | 公网 IP:4321 + cloudflared 隧道兜底 | 匿名源活；登录态源停在快照 |
| 快照 | GitHub Pages | 静态托管 | 只读站点 | 只读，某一刻的河 |

部署脚本 `tools/deploy-ecs.sh` 走阿里云 workbench CLI（免 SSH 密钥直连），
**只带公开件**：私有适配器、凭证目录、全量缓存一律留在原机（白名单机制，
与 `tools/publish.sh` 同一套思路）。

访问口令闸（`lib/access.js`）：这个应用没有账号体系，公网裸奔等于匿名可写。
闸的形态是「口令换一年期 HttpOnly cookie」，保留 `?token=` 一次性登录。
**不给回环地址做豁免**——因为部署形态之一是 `ssh -R` 反向隧道，
那种形态下远端客户端在服务端看来就是回环。

> **2C2G 是硬约束。**新方案建议 4核8G，那意味着**换机器或加配置**。
> 这不是不能做，但要算进成本，且要回答「为什么现有形态在 2C2G 上跑得动
> 而新形态不行」——答案是新形态要跑浏览器（见 §5 小红书、§8 B站）。

## 7. 当前健康状况：登录态通道已静默失效 5 天

实测当日 `data/cache.json`：**253 个缓存键里 146 个带 error。**

| 源 | 数量 | 错误 |
|---|---|---|
| 知乎 | **115（全部）** | 109 个 `HTTP 401`、6 个 `403` |
| 小红书 | **13（全部）** | 浏览器会话需重新登录 |
| feed 类 | 18 | `fetch failed` 8、超时 4、非 feed 2、503 2、403 1、429 1 |

诊断过程（按项目自己的判别法）：

1. 知乎返回 401 `ERR_TICKET_NOT_EXIST`（认证失败，不是限流）。
2. 做单点健康检查：打 `/api/v4/me`（即 RSSHub 的 `check-cookie.ts` 用的同一端点），
   **同样 401**。
3. 项目文档里写明的判别法：「403 之后先做一次单点健康检查，
   **单点也失败才是真失效**」。→ 判定为**凭证真失效**。
4. 凭证文件最后修改于 9 月 11 日，已失效约 5 天。

> **这件事对新架构的意义，比它看起来重要**：128 个源静默停摆 5 天没人发现，
> 说明现有形态缺的是**凭证健康监控与主动告警**，不是抓取能力。
> 上一版方案的「来源状态必须可见、更新失败不能显示为没有新文章」正好解这个问题，
> 应当采纳——但它还缺主动告警（现在要靠人打开页面才看得见）。
>
> **反过来说**：新架构如果仍押在单一登录态凭证上，同样会静默失效。
> 所以无论走哪条路，凭证健康检查 + 失效告警都是第一优先级，
> **排在推荐算法和日报前面**。

### 8.1 RSSHub 公共实例全部不可用

2026-09-10 实测 8 个社区镜像，**0 个可用**：2 个 503、2 个被域名策略拦截、
4 个连不通。唯一返回 RSSHub 错误页的那个还暴露了它没装 Playwright chromium。

**自托管是唯一选项。**自托管有两条路（RSSHub 本身是 Node 项目，不一定要 Docker），
Node 直跑这条路踩到四个坑：

1. RSSHub 声明 `engines: ^22.22.2 || ^24.15.0`，更新的 Node 会让 pnpm 直接拒装。
   要在它的 `.npmrc` 里加 `engine-strict=false`，顺带加 `verify-deps-before-run=false`，
   否则每次 `pnpm run` 都重新触发一次失败的装包。
2. **pnpm 10 起不再读 `package.json` 的 `pnpm` 字段**，RSSHub 的 13 条 `overrides`
   和 3 个 `patchedDependencies` 会**静默失效**，装出来的是「非官方期望状态」。
   要把那三块照抄进 `pnpm-workspace.yaml` 再装。验证方式是看
   `node_modules/.pnpm` 下的目录名有没有 `_patch_hash=`。
3. `pnpm start` 需要 `dist/`，所以先 `pnpm build`。
4. **B站路由（视频与专栏都一样）现在强制走浏览器，chromium 是硬依赖而不是
   风控时的回退**，缺了直接 503。它要的版本跨境下载可能极慢，出路是设
   `CHROMIUM_EXECUTABLE_PATH` 指向本机已有的 Chrome/Chromium（版本号与
   RSSHub 声明的 revision 不完全一致也能跑通）。

> **每个 B站请求都会起一次浏览器，连续添加多个源容易撞 503，隔几秒单独重抓即可。**
> 这条对评估小红书路由的资源开销直接适用（小红书路由同样 `requirePuppeteer: true`）。

### 8.2 知乎对匿名请求全程拦截

三道墙：`zse-ck` JS 挑战、`x-zse-96` 签名、`40362` 风控。
**没有匿名出口**，这就是它在第 3 档的原因。

RSSHub 的知乎路由自己实现了这套签名（`execlib/x-zse-96-v3.ts` + JSDOM 跑 WASM VM
生成 `__zse_ck`），这点值得肯定——它确实解决了签名问题。

### 8.3 小红书没有关注列表可挖

登录态实测（CLI 的 `creator-profile` 与个人主页 UI 双路核对）：
该账号关注数 = 3，就是库里已有的 3 个源。**「排查关注列表」这个动作在小红书是空转。**

所以小红书候选改走**搜索聚合 + 主页实读**两段式：8 组领域词各取 20 条，
按 `author_url`（含 24 位 user id）聚合命中次数与最高赞，得 134 个候选作者；
再对筛出的 21 个逐个实读主页笔记，按三条判据定收不收，**收 10 人、排除 9 人**
（每个排除都有逐条理由）。库从 160 涨到 170 源，小红书 3 → 13 源。

> 搜索聚合的天花板要记住：它只看得见**被搜到的词**覆盖得到的号。
> 知乎那批有关注列表兜底（用户已经用脚投过票），小红书这批没有——
> 所以这 10 人是「检索能及」的下界，不是「用户兴趣」的全集。

### 8.4 公众号：wewe-rss 已死，两个公开转发目录互补

**WeWe RSS（9667★，MIT）已于 2026-07 失效**，仓库 archived 2026-03-20。
死因不是「上游归档」，而是**抓取能力全在一个已经物理消失的闭源单点上**：
它的登录与抓取全部托管在作者的闭源转发服务上，那个服务随 Deno Deploy Classic
平台下线一起消失了。部署能起但扫码登录必然失败，**没有任何 fork 修得了**。
作者只开源了外壳（issue 原话：「token 是从这个服务生成的，只做请求转发」）。

同类风险还有一个项目（284★）：根目录只有 README、images、lib 和一个编译好的
`website.jar`——**闭源 JAR，没有源码**，license 字段为空。文档挂在裸 IP 上
（单点个人基础设施）。机制与 wewe-rss 同族，靠微信读书登录态，
其用户协议自述可能导致账号被限制或封禁。**同样不考虑。**

**现在免费可用的只有两个公开转发目录实例**，都是免登录、免部署、免付费，
每个号直接给标准 RSS 地址：

| 实例 | 收录 | 每源条数 |
|---|---|---|
| A | 395 个号 | 20 条 |
| B | 375 个号 | 10 条 |

**两者只重叠 23 个名字。**只查一个会漏掉一半，而且漏的正好是要的那一半：
大厂技术号（快手技术、大淘宝技术、小红书技术、百度Geek说、蚂蚁技术、京东技术、
腾讯技术工程、滴滴技术、vivo互联网技术）**基本只在 B 里**。
所以识别逻辑从「单域名硬编码」改成了转发宿主表 + 按点边界匹配
（`evil-<host>.example` 与 `<host>.example.evil` 都不认，有回归用例）。

**付费私有部署**（150 元/年）能覆盖全部，但采集端闭源不可审计，
等于把微信登录态交给一个无法审计的服务。当前决策是不采用。

### 8.5 X/Twitter：官方 API 收费，Nitter 已死，只剩一个转发服务

Nitter 公共实例在 2026-08-24 收到停止函后系统性死亡，所以贴 `x.com` 主页抓不到。
目前有一个第三方转发服务仍在提供免费 RSS，实测 22/22 个账号 HTTP 200、
每源 50 条、`pubDate`/`guid`/`link`/`author` 齐全、最新文章在当天。据此入库 34 个
（后经内容复核降到 28）。

**档位故意留在第 3 档**，不因为「贴地址就能抓」提到第 1 档：平台本身仍是登录态墙，
能抓到只是因为有个第三方在转发。识别结果因此带一条 note 说清这是第三方转发、
服务方下线源就断。**这条 note 不是免责声明，是给半年后的自己看的——
wewe-rss 当初也是「贴地址就能抓」。**

一个实现细节，省得重复踩：**转发地址里的哈希不可由 handle 推导**。
试过 `md5(handle)` 与小写变体都不是；`/rss/user/<handle>`、`?screen_name=`、
`/api/user/` 等猜测路径全 404 或返回错误码。所以只能从现成目录取地址
（有一份公开 OPML 收录 160 个账号），添加页收的是转发地址而不是 handle。
`url` 存作者主页、`feed` 存转发地址——卡片上的「去主页」该跳作者，
且跳转不该随服务方改域名而失效。

### 8.7 大陆 ECS 部署的四个假象（每个都曾把排查引向错误方向）

| 假象 | 真因 |
|---|---|
| 手机访问 80 端口 `ERR_TIMED_OUT`，Mac 却拿到 200 | 大陆地域 ECS 未做 ICP 备案，云厂商在边缘对公网直连 80 丢包；**Mac 的 200 是公司办公网透明代理代答的** |
| 「nc 探测 80 端口通」 | 安全组入方向默认只开 22/3389/ICMP，握手是代理代答的 |
| Mac 上隧道客户端一启动就被 SIGKILL | 不是崩溃：隧道域名被办公网安全代理的域名策略拦截（返回中文 403 拦截页） |
| ECS 上 curl 自己的隧道地址返回 000 | 隧道域名 DNS 只回 IPv6，而 ECS 无 IPv6 连通（自测要加 `-4`；真实客户端不受影响） |

解法：服务改监听 **4321**（非标准端口规避备案拦截），隧道改在 ECS 上跑（出口干净）。

**固化的方法论**：验证公网可达性要用干净出口（在 ECS 上 curl 自己的公网 IP），
并访问一个「安全组放通但无服务监听」的端口看是立即 refused 还是空响应/超时；
**本机办公网观测到的 200 一律先怀疑**。

另：安全组默认不放 80 时表现为「TCP 握手成功但响应为空」，**极易误判成服务没起**。
8 个容器的栈里这个误判会浪费很久。

### 8.8 BestBlogs：闭源核心，但有真东西可挖

仓库 4026★ 但 **license 字段为空**（`/license` 接口 404，法律上未授权修改），
整棵树**没有一行应用代码**：只有 OPML 清单、产品文档、changelog、
调自家 API 的 CLI、agent skills、Dify 工作流 YAML。

它的核心资产是 600+ 源的质量池、AI 初评 + 编辑精审的运营流程、2 万用户的行为数据
——三样都开源不了。

**当前决策：当目录用，不当聚合器用。**明确不订它那条评分聚合 RSS，三个理由：

1. **排序权在它手里**。六维 AI 评分决定哪些文章进流，这正是要摆脱的东西。
   订一条别人筛过的流，等于把选择权换给了另一个推荐系统，只是它没有广告。
2. **源会丢**。聚合流里看不到「这是谁写的」，同一作者的文章被拆散、按分数进进出出。
   本项目按源组织（每个博主有专属页），聚合流进不了这个结构。
3. **重复计数**。它收录的文章大量来自已直接订的源，而条目 ID 是按 feedUrl 算的，
   去重不了。

可挖的真东西：`flows/Dify/dsl/v4/*.yml` 里是**生产环境实际在跑的 system prompt**。
一个发现——**公开的分析 prompt 与官网宣传的「六维评分」对不上**：
DSL 里实际是内容深度 40 + 相关性 30 + 实用性 20 + 创新性 10 + 减分项；
官网说的选题/内容/深度/实用/创新/表达是后来的迭代，没跟着开源。
它明确写了反通胀规则（「宁可偏低 2-3 分」「90+ 应极其稀有」
「多数文章在原创洞察维度应得 2-5 分」），**这套校准比 rubric 本身更值钱**。

同理不接它的 OpenAPI / CLI / agent skills：都要 API Key，而 RSS 端点已经免费够用。
**要 Key 的东西进来就多一个要续的凭证**，这是 8.4 那条教训的直接应用。

### 8.9 一个公共 RSSHub 实例是受限的

实测某公共实例的小宇宙（播客）路由可用，但 **bilibili 路由超时、zhihu 404、
weibo 超时**——是个受限实例，不能拿来替自托管的 `rsshubBase`。
而且本机 RSSHub 已经能跑小宇宙路由，没必要依赖公共实例
（**依赖公共实例正是 8.4 那个错误的形状**）。

### 8.10 收录判据（决定了 271 个源为什么是这 271 个）

知乎那批的入口是「我的关注列表」：**905 人全量排查，挖出 111 个源**（现库内 115）。

三条判据：

1. 作者**自己在做**，不是转述别人做了什么。（据此排除 AI 资讯号：
   量子位、InfoQ 中文、机器之心、AI前线、智东西——即使它们分数高、更新勤。
   从 170 个候选博客源里只挑出 8 个直连博客入库。）
2. 营销文体与面试辅导号不收。（「2026 XX 面试全攻略」系列量产号）
3. 正文本身是内容，不是引流桩。

配套方法：**筛选要算覆盖率**，简介不能当唯一证据（某博主简介写满技术词但实际在写
面试经验，覆盖率算出来才露馅）；**词表要随批次修**，判据是一手还是转述；
**收录后要做内容复核**，tag 按内容定不按名声定（一轮复核砍 6 源、重打 6 个 tag）。

> **这 271 个源与 16 个 tag 是三个月人工筛选的结果，是本项目最值钱的资产。**
> 抓取实现反而是最容易替换的部分。

## 9. 资产盘点：什么值钱、什么可替换

| 16 个 tag 与源的归属 | 同上 | **极高**：人工复核，ADR 记录了每次调整理由 | 可导出 |

## 10. 我们要外部评审人回答的问题

读完上面九节，请针对这七个问题给建议。**每个问题都请说明它依赖上面哪一节的事实。**

1. **全文获取这条链路怎么建？**我们全库 7474 条无一条存正文（§3），
   而目标是站内阅读全文。RSSHub 的知乎路由返回完整正文并带图片清洗，
   小红书有 cookie 时走逐条二次请求取全文，公众号要靠 `gather.content` 开关。
   这套组合的真实覆盖率与稳定性如何？还有哪些源拿不到正文，
   它们在新架构里应该怎么呈现？

2. **登录态凭证怎么运维？**现在 128 个源静默失效 5 天（§7）。
   新架构下知乎要 `z_c0` + `d_c0`（RSSHub 的 merge 逻辑会保留 `z_c0`，
   但需要 `d_c0` 当身份锚点），小红书要 cookie 或浏览器会话。
   健康检查与告警应该怎么设计，才能做到「失效当天就知道」？
   **凭证在机房 IP 上是否还能用，是本项目最大的未知数**（§8.7 的 ADR 结论是
   「登录态源不上服务器」）。

3. **13 个小红书源要不要在服务器上跑浏览器？**小红书路由 `requirePuppeteer: true`，
   每个请求起一次浏览器。我们在 B站路由上实测过这个模式的代价
   （连续添加多个源容易撞 503，§8.1）。现有实现是驱动**本机**已登录浏览器，
   服务器上跑不通（§9 标为不可迁移）。选项是：服务器上跑 Puppeteer + 自己的 cookie、
   保留原机当小红书的抓取节点、或者放弃小红书的实时更新只留快照。请权衡。

4. **2C2G 够不够？**现有形态在 2C2G 上跑得动（§6）。新形态要加 Postgres、
   Meilisearch、可能的 Chromium。上一版方案建议 4核8G 并说「2核2G 不建议承载整套组合」。
   如果必须留在 2C2G，哪些组件可以砍？（我们的判断是 Meilisearch 第一版可不部署、
   Karakeep 的浏览器容器可不部署，但小红书路由的 Chromium 砍不掉。）

5. **排序算法怎么冷启动？**上一版方案说兴趣信号「先来自你明确填写的主题」。
   但我们已经有 16 个 tag 与 271 个源的归属（§4、§8.10），
   这是现成的兴趣标注数据。怎么用它冷启动，比从零填主题词有效？
   另外我们的 tag 体系是按**阅读需求**拆的（ADR 记录：「深度学习是个筐，
   按阅读需求拆七个 tag」），不是按学科分类，这个特性对排序有什么用？

6. **17 个手记公众号要不要上自建采集？**现在它们只登记名字、内容为空、
   卡片提示去微信里搜（§4）。有一个 MIT 许可、活跃维护的自部署方案
   （Docker 一行起，带 Webhook/API/Agent 接入），但机制与已死的 wewe-rss 同族
   （靠扫码授权，§8.4）。差别是**抓取在自己手里**而不是托管在闭源单点上。
   为 17 个号引入一个要维护授权的服务，值不值？

7. **现有的时间轴 UI 保留还是替换？**它绑定「不做推荐排序」的产品哲学（§1）。
   新目标要推荐排序。三个选项：替换掉、并存（新平台当主入口、时间轴当「按时间看」
   的视图）、或者把排序能力加进现有 UI（但那会破坏它的设计边界）。
   这个选择直接决定要不要给我们加 RSS 出口（§4 末尾那个 122/271 的问题）。

## 附：上一版方案的两处判断错误（供对照，避免重犯）

本节自包含，读完这两条就够了。（我们内部还有一份逐条核到源码行的完整评审，
里面写了本机凭证文件名与私有工具名，**不随本文外发**——需要某个具体结论的
核实过程时，直接问我们，我们摘出对应段落。）

两处最关键的：

1. **把「条数更多」当成「资产更好」，漏了正文这个维度。**
   上一版认为我们现有的知乎适配器（20 条）优于 RSSHub（7 条）。
   实测两者的 API 请求参数：我们请求 `include=data[*].excerpt`（摘要），
   RSSHub 请求 `include=data[*].content`（**完整正文**）并用 cheerio 做了图片清洗
   （移除 noscript 与 mcn 卡片、解开跳转链接、修正懒加载属性）。
   **在「拿到可阅读正文」这个维度上 RSSHub 更优**，而正文正是新目标的核心需求。

2. **把「登录态资产」当成已建成的，而它当下是停摆的。**
   上一版说「115 个知乎源现在正在跑」。实测 115 个**全部报错**（§7）。
   登录态不是「换架构就会失去的资产」，而是一个需要持续人工维护、
   且已经断了 5 天没人发现的脆弱凭证。

两处纠正后，上一版「保留现有抓取层」的建议从「强烈建议」降级为「备选」，
且只在「决定保留现有时间轴 UI 作为并存入口」时才值得做（问题 7）。
