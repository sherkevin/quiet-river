# 私有阅读平台方案：RSSHub + We-MP-RSS + Miniflux + Karakeep + Reader Bridge

状态：Proposed（2026-09-16 规范化）

本文是用户提出的方案的**规范化版本**，不含评审意见（评审见
[`private-reader-platform-review.md`](private-reader-platform-review.md)）。

原始输入是同一方案的两个版本（v1、v2），内容重复度约 70%，配置值有冲突。
本文合并两版，冲突处在 §14 列出并标注「待决」，不擅自取值。

## 1. 目标

一个**对内开放**的自用阅读平台：没有其他用户，没有公共广场，展示的全部内容来自自己
关注的来源。七项能力：

1. 抓取不同平台的信息源
2. 有自己的推荐算法，但**只决定排序**，不决定可见性
3. 站内直接阅读全文，不跳转到外部网站
4. 阅读时划线高亮、写笔记
5. 能回看自己的笔记
6. 灵活自定义信息源
7. 日报推送

## 2. 三条前提与两条边界

**前提**

- 完全自托管，不依赖任何外部云服务
- 尽量不修改现成项目的源码，只通过 API 组合
- 抓不到全文时允许退回原文链接

**边界（必须在产品里显式呈现，不能藏起来）**

- 把容器起起来 ≠ 有了个性化推荐。内容转存与推荐卡片页需要集成开发，范围见 §10。
- 没有任何开源工具能保证知乎、小红书、公众号的所有博主长期可抓。系统必须在
  「全文可用」「只有元信息」「来源暂时失效」三种状态下都正常工作。
  **连发布列表都拿不到时，必须显示来源异常，不能显示为「没有更新」。**

## 3. 架构

```text
你关注的博主
    |
    +-- 普通博客：原生 RSS / Atom
    +-- 知乎、小红书：自建 RSSHub
    +-- 微信公众号：自建 We-MP-RSS
                    |
                    v
                 Miniflux
       订阅管理、定时/手动刷新、保存正文与元信息、记录来源错误
                    |  REST API
                    v
             Reader Bridge  <-- 唯一需要开发的服务
       内容同步、正文转存、去重映射、个性化排序、卡片页、日报
                    |  REST API
                    v
                 Karakeep
       站内阅读、划线、批注、收藏、搜索
                    |
                    v
             你的文章与阅读笔记

全部部署在自己的 Ubuntu ECS 上，Caddy 负责 HTTPS 与入口分流
```

### 组件职责与数据归属

| 组件 | 职责 | 改源码 | License |
|---|---|---|---|
| Miniflux | 订阅管理、调度、手动刷新、保存正文与元信息、来源错误记录 | 不改，走 API | Apache-2.0 |
| Karakeep | 站内阅读、划线、批注、收藏、检索 | 不改，走 API | AGPL-3.0 |
| RSSHub | 知乎、小红书等无 feed 平台转 RSS | 原则上不改 | AGPL-3.0 |
| We-MP-RSS | 公众号订阅、采集、全文 RSS 输出 | 不改，自建实例 + 自己的授权 | MIT |
| **Reader Bridge** | 同步、转存、映射、排序、卡片页、日报 | **本项目唯一开发项** | 自定 |
| PostgreSQL | Miniflux 的库 | 不改 | — |
| Meilisearch 社区版 | Karakeep 的搜索 | 不改 | MIT AND BUSL-1.1（见 §14 待决） |
| Caddy | HTTPS、反向代理、路径级鉴权 | 只写配置 | Apache-2.0 |

**数据归属三分，互不越界写库，全部走 API：**

```text
Miniflux  管订阅与未读
Karakeep  管正文档案与批注
Bridge    管映射与排序（自己的 SQLite）
```

Bridge 的映射表：

```text
Miniflux entry_id
    <-> 平台文章ID / 原始URL
    <-> Karakeep bookmark_id
    <-> 内容状态、快照哈希、排序分数
```

### 为什么要加 Miniflux，不让 Karakeep 包办

这是方案的核心论据，已核实成立：Karakeep 的 RSS 解析器只提取
`id / link / guid / title / categories`，创建书签时只传 `url`、`title`、`source`，
**RSS 里已有的正文被丢弃**；随后 Karakeep 会自己去抓原站。后果是：

```text
公众号适配器已经拿到正文
        -> 阅读器只收到链接
        -> 阅读器重新访问微信原站
        -> 被限制访问，正文反而丢了
```

Miniflux 的 entries API 直接返回 HTML 正文、作者、发布时间、来源与错误状态，
适合承接这批数据。**多部署一个成熟订阅服务，换少写一套订阅管理、调度、刷新、
错误处理与内容存储。**目标是减少二次开发与长期维护，不是机械地减少容器数量。

### 第一版明确不部署

本地大模型、向量数据库、独立任务队列、Kafka、Kubernetes、外部 AI API。
Karakeep 的浏览器容器与 Meilisearch 在第一版也不强制（见 §14 待决）。

## 4. 来源接入

### 4.1 博客：优先原生 RSS，缺正文再补抓

有原生 RSS/Atom 的直接订，不绕一层 RSSHub。Feed 已含全文就用 Feed 的；
只有摘要时才用 Miniflux 的正文提取（它自带本地 Readability 与站点规则）。

**不要无差别开启「重新抓取所有原文」**，已经拿到全文再抓一次不必然更完整。
**不要让每篇都先过浏览器渲染**：静态走普通 HTTP，动态页面才用浏览器。

### 4.2 知乎：订具体内容类型，不订泛活动流

```text
用户回答：/zhihu/people/answers/<用户ID>
用户文章：/zhihu/posts/people/<用户ID>
```

不订「全部动态」，避免把赞同、收藏等行为混进来。

三级结果，逐级降级：

| 获取结果 | 展示 |
|---|---|
| 完整回答或文章 | 站内阅读，可划线批注 |
| 只有标题与摘要 | 摘要卡片，主按钮进原文 |
| 有链接但正文需登录/付费 | 保留来源信息，标记「需原站阅读」 |
| 连发布列表都失败 | 显示「来源更新失败」，保留历史文章 |

凭证只用自己的合法访问凭证。遇到验证码或访问限制时暂停降频，
**不把绕过限制作为系统正常工作的前提。**

### 4.3 小红书：接入作者笔记，但必须校验链接字段

```text
/xiaohongshu/user/<用户ID>/notes
```

该路由需要浏览器运行环境，有反爬标记，可选配 Cookie。因此小红书
**不能按「普通静态 RSS」估算稳定性与资源消耗。**

已核实的具体缺陷：该路由的回退分支会把**封面图片地址**写进条目 `link`，
而不是笔记原文地址。所以 Bridge 必须校验：

> **图片地址不能被当成「打开原文」的目标；文章 ID、标题、原文链接不能靠标题猜。**

拿不到具体笔记地址时，最多展示「进入作者主页」并明确标注，
不提供一个看起来正确、实际打不开的按钮。

图片/视频本身不等于可划线的文字。能取到文字描述就对那部分做本地阅读；
纯图片/视频第一版保留元信息与原始入口，**不引入 OCR、视频下载与转录。**

### 4.4 微信公众号：自建 We-MP-RSS，授权纳入日常维护

操作流程：

```text
进入 We-MP-RSS 后台 -> 完成所选采集模式的账号授权 -> 添加公众号
   -> 验证能取到文章 -> 复制该号的 RSS 地址 -> 添加到 Miniflux
```

**「采集正文」与「RSS 输出正文」是两个独立开关，只开后一个不算数：**

```yaml
gather:
  content: true        # 是否采集正文
rss:
  full_context: true   # RSS 是否输出正文
  local: false         # 条目是否保留外部原始链接
```

（v1 给的是环境变量形式 `GATHER.MODEL` / `GATHER.CONTENT` / `RSS_FULL_CONTEXT` /
`RSS_LOCAL`，v2 给的是 YAML 形式，同一组开关。）

**微信读书模式只能当受限备选**：`weread_mp` 模式只取公众号最新一篇，
不能回补历史；两次采集之间更新多篇就会漏。

因此公众号来源必须显示「最后成功采集时间」与「授权是否有效」；
授权失效时暂停任务并提示重新授权，**不做无限重试。**

## 5. 更新机制

| 环节 | 第一版策略 |
|---|---|
| Miniflux | 按调度刷新，需要时手动刷新单源 |
| We-MP-RSS | 按公众号更新频率定时采集，初始每 2 小时 |
| RSSHub | 用缓存，限制同平台并发，失败退避 |
| Reader Bridge | 每 60~120 秒检查新条目与内容更新 |
| 推荐排序 | 有新条目或新反馈时重算 |

各来源的建议起始频率（v1 给的更细粒度）：博客 15~30 分钟；
知乎/小红书 30~60 分钟并结合缓存；公众号 60~120 分钟且错峰。
**这些是初始运行参数，不是平台承诺或实测最优值。**

### 手动刷新必须区分两个动作

**「刷新阅读器里的 feed」≠「要求上游重新抓博主」。**

```text
We-MP-RSS 尚未抓到新文章
      -> 此时反复刷新 Miniflux
      -> 仍然只能得到 We-MP-RSS 原有的内容
```

- 博客：直接在 Miniflux 刷新
- 公众号：必要时先在 We-MP-RSS 手动采集，再刷 Miniflux
- 知乎/小红书：刷 RSSHub 订阅，但尊重其缓存、授权与访问限制

界面要区分「已拉取最新缓存」与「已完成上游重新采集」，不能都叫「更新成功」。
第一版沿用各组件原生后台完成这些操作，不先做统一刷新控制台。

每个来源至少展示：最近检查时间、最近成功时间、当前状态
（正常 / 等待授权 / 更新失败）。

## 6. 正文转存

这里的「转写」指**提取、清洗、保存原文**，不经过 AI 改写。
否则划线记录的可能是模型改写内容，而不是作者原文。

### 6.1 处理顺序

```text
Miniflux 取得新条目
      -> 先保留标题、作者、时间、原始链接
      -> RSS 已有可用正文？
            有 -> 直接用
            没有 -> 尝试 Miniflux 的正文提取 API（可先返回结果、不覆盖库）
      -> 得到 全文 / 部分正文 / 元信息
      -> 清洗正文、处理图片、生成 HTML 快照
      -> 导入 Karakeep 本地阅读
```

**不要用登录提示、验证码页面或空正文覆盖已保存的摘要。**

### 6.2 调用 Karakeep 的导入接口

| 用途 | 接口 |
|---|---|
| 取 Miniflux 条目 | `GET /v1/entries` |
| 刷新指定来源 | `PUT /v1/feeds/{feed_id}/refresh` |
| 取正文但不覆盖库 | `GET /v1/entries/{entry_id}/fetch-content` |
| 上传 HTML 归档 | `POST /api/v1/bookmarks/singlefile?ifexists=skip` |
| 创建纯链接条目 | `POST /api/v1/bookmarks` |
| 补元数据 | `PATCH /api/v1/bookmarks/{bookmark_id}` |

```bash
curl --fail-with-body \
  -H "Authorization: Bearer ${KARAKEEP_API_KEY}" \
  -F "url=${ORIGINAL_ARTICLE_URL}" \
  -F "file=@article.html;type=text/html" \
  "${KARAKEEP_URL}/api/v1/bookmarks/singlefile?ifexists=skip"
```

**`url` 必须是文章原始地址**，不能是某个临时抓取服务地址；上传的 `file` 存本地内容。

两个系统鉴权不同：Miniflux 用 `X-Auth-Token`，Karakeep 用 Bearer Token。
密钥只放服务端，不进网页 JavaScript。

上传成功 ≠ 正文可读：还要等 Karakeep 解析完成。解析通过前卡片显示
「正在准备正文」，不能把 HTTP 200 当成「正文已可读」。

### 6.3 正文、图片、公式分别处理

保留标题层级、段落、代码块、表格、图片、来源链接；
去掉脚本、表单、跟踪像素、明显广告区块。

**正文存在本地，不代表正文里的图片也在本地。**Bridge 要把允许获取的内嵌图片
打包进快照，设单张与单篇大小上限，失败的图片留占位说明。
不要把 Miniflux 的私有媒体代理链接直接给另一个阅读器，
也不要默认所有图片都能长期外链。

公式与复杂表格必须用真实文章验收。第一版不追求复刻原站全部交互；
无法完整保留时在卡片上提示「排版可能不完整」，并始终保留原文入口。

### 6.4 内容状态机

来源级配置一个正文模式，文章级记一个实际状态：

```text
来源模式： full（已确认提供全文） / summary（已确认只有摘要） / unknown（未验证）
文章状态： FULL / PARTIAL / META / FAILED
```

**「网页上有很多字」不是全文成功的证据**：反爬提示、登录页、推荐列表也可能很长。
HTTP 200 同样不代表正文获取成功。

## 7. 划线、笔记与正文版本保护

### 7.1 有正文：直接用 Karakeep 原生能力

```text
推荐卡片 -> 本地文章 -> 选中文字 -> 划线 / 写备注 -> 在 Karakeep 中查看
```

Karakeep 已有高亮、备注、阅读详情中的批注展示，以及独立的高亮列表页。
**不另写一套文字选择、定位与保存系统。**

### 7.2 只有外链：仍允许文章级笔记

没有本地正文时无法对原文段落做可靠划线，但可以记文章级笔记。
「写文章笔记」创建一个带 `sourceUrl` 的文本书签，保存标题、作者、原文地址与心得。

> **有正文时做段落级批注；无正文时做文章级笔记。**

按内容状态区分体验：

| 内容状态 | 允许的阅读与笔记行为 |
|---|---|
| 完整文字正文 | 站内阅读、选中文本高亮、批注、整篇备注 |
| 部分正文或摘要 | 对已保存部分做记录，明确标记「非全文」 |
| 只有元信息 | 写整篇备注，点原文阅读 |
| 图片或视频为主 | 查看已有媒体、写整篇备注；不宣称图片文字可直接高亮 |

### 7.3 已批注的正文不自动覆盖（本方案最重要的一条）

> **文章一旦用于批注，就冻结当前阅读正文。以后抓到新版本，不自动替换。**

Karakeep 的导入支持 `skip` / `overwrite` / `overwrite-recrawl` / `append` /
`append-recrawl`。第一版默认 `skip`；需要保留更新时追加归档，
不自动触发重新解析与替换。

理由：保留多个 HTML 文件 **不等于** 高亮会自动正确迁移到新正文。
第一版不实现高亮迁移，直接避免无提示覆盖。

同时保存原文抓取时间与内容哈希，避免网站更新或清洗规则变化后高亮悄悄错位。

「只有卡片 -> 后来补齐正文」的情况，在**没有高亮时**可以自动升级；
用户自己写的备注不能被同步程序覆盖。

### 7.4 可选的人工补全入口

对服务器抓不到、但自己在浏览器里能正常阅读的文章，用 SingleFile 浏览器扩展
把所见页面存进自己的 Karakeep（官方集成方式）。

这是**用户主动保存已获准访问的内容**，不是设计验证码、登录或付费限制的绕过方案，
也不是自动订阅正常运行的前提。

## 8. 个性化排序

### 8.1 第一版不用大模型

第一阶段目标不是训练通用推荐系统，而是：

> **把自己已经关注的新增文章，按当前兴趣与来源偏好排好顺序。**

用一个可解释的 CPU 排序器，输入是配置的兴趣词、同义词、作者偏好、发布时间、重复度。

```text
score(i) = w1*兴趣匹配(i) + w2*来源偏好(i) + w3*时效性(i) - w4*重复程度(i)
```

v1 给的初始权重示例：`s = 0.55*I + 0.25*A + 0.20*F`，各项归一化到 0~1。
**这些是建议起始配置，不是实验得出的最优参数。**

兴趣匹配用 Python `scikit-learn` 的 `TfidfVectorizer`，字符级 n-gram 可直接处理
中文，不需要先搭分词服务。

排序后做轻量多样性调整：前十条同一作者尽量不超过两条；重复报道折叠但允许展开。

以后有足够反馈，再换本地 embedding 或学习排序模型。

### 8.2 四条产品规则（硬约束）

1. **候选集只来自当前关注的来源。**
   ```text
   候选文章 = 当前仍在订阅的来源中，近期更新且尚未标记已读的文章
   ```
   「近期」先做可配置窗口（如 7 天）。取消关注后新内容不再进候选，
   但已保存的文章与笔记保留。
2. **始终保留「按时间看」。**算法只改顺序，不让你失去查看完整列表的能力。
3. **没有全文不等于低价值。**外链文章仍按标题、摘要、作者参与排序，
   只标记「判断依据有限」。对正文未知的文章不生成「全文摘要」。
4. **打开不等于读完，划线不等于赞同。**第一版主要用显式反馈；
   「标记已读」「不感兴趣」「收藏」分别记录，不混成一个含糊的行为信号。
   划线与批注不能直接当喜欢，因为也可能是在批评原文。

### 8.3 排序必须真正控制页面

推荐卡片页由 Bridge 按分数生成。

**不采用两个取巧办法：**不通过伪造文章发布时间来实现排序；
不假定「把 RSS 排好序」就能控制下游阅读器（Karakeep 的列表接口主要是时间方向排序，
不接受自定义每篇分数）。

也不把「关键词标签」冒充已完成的个性化排序。

### 8.4 日报复用同一批结果

```text
从当天新内容去重、排序、选取 -> 保存为本地页面 /brief/daily/<日期>
```

第一版就是「精选条目 + 已有摘要/摘录 + 推荐理由」，不需要生成式摘要。
邮件或其他渠道只是以后增加的投递出口，不影响日报本身在自己服务器上完成。

## 9. 日常入口与卡片形态

日常只用一个入口，三个导航：

```text
reader.example.com/desk/       推荐阅读 / 最新更新（Bridge 提供）
reader.example.com/dashboard/  我的笔记 + 文章阅读（Karakeep 原生界面）
```

（v1 的路径规划是 `/brief/` 与 `/`，v2 是 `/desk/` 与 `/dashboard/`，见 §14 待决。）

**Karakeep 保持在站点根路径**，避免为改子路径而改前端构建；Caddy 只把 Bridge 的路径分流出去。

### 全文可读的卡片

```text
标题：某篇技术文章
作者：某博主    来源：个人博客
发布时间：......
状态：本站全文
推荐原因：与你设置的「Agent 工具调用」兴趣匹配

[站内阅读]  [查看原文]  [已读]  [不感兴趣]
```

### 取不到全文的卡片

```text
标题：某个知乎回答
作者：某博主    来源：知乎
发布时间：......
摘要：仅显示已获取到的内容
状态：需原站阅读，本站未取得全文

[打开原文]  [写整篇备注]  [已读]  [不感兴趣]
```

**不把登录提示、验证码页面、「请打开 App」误判成文章全文。**

### 元信息最低标准

卡片至少保留：标题、作者或订阅源名称、平台、原文链接、发布时间、获取状态。

不知道原始发布时间就显示「发布时间未知」，另列「首次发现时间」。
**不要用抓取时间冒充发布时间。**

来源失败时保留已有卡片但明确显示异常：历史内容仍可读，不代表新内容仍在进入。

第一版不重做 Karakeep 的阅读界面，也不把原网站嵌进 iframe。
点「站内阅读」进同域名下的 Karakeep 页面，原推荐页留在原标签页。
管理订阅用 Miniflux 原生后台，管理公众号授权用 We-MP-RSS 原生后台。
**暂时接受管理界面分开**，避免为统一后台与单点登录增加大量开发。

## 10. Reader Bridge 开发范围

技术选型：Python 服务 + 服务端 HTML 模板 + 本地 SQLite + scikit-learn。
不再搭一套复杂前端。

| 模块 | 必须完成 | 明确不做 |
|---|---|---|
| 同步与映射 | 分页读 Miniflux 条目；维护文章与书签的对应关系；重复与失败重试 | 不重写订阅管理与 RSS 解析 |
| 内容转存 | 判断正文状态；整理 HTML 与图片；调用 Karakeep 导入接口 | 不重写阅读器、浏览器抓取器、划线组件 |
| 排序与卡片页 | 读兴趣配置、算顺序、显示元信息与状态、提供操作按钮 | 不做公共推荐池或多用户系统 |
| 反馈与日报 | 记录显式反馈、调用已读接口、生成本地日报 | 先不做复杂行为模型与外部推送体系 |
| 状态衔接 | 已读操作、来源异常提示、正文同步状态 | 不直接改其他服务的数据库 |

**阅读状态以 Miniflux 为准**（卡片点「已读」调其 API）；
**备注、高亮、收藏以 Karakeep 为准。**

> 同步成功不等于已读，点击打开也不自动等于读完。

这样不用改 Karakeep 前端埋点，也能形成可控的第一版流程。

### 不能省的细节

- 同步必须分页并保存游标，不能只读「最近 100 篇」
- 按稳定文章标识去重，不能仅用标题；首次导入的历史文章不能全当作今日新发布
- 转存失败不丢原卡片；每次重试复用映射，避免生成重复笔记对象
- 原文 URL 与去重键分开保存，不随意删可能影响访问的签名参数
- 检查近期条目的**内容变化**，不只读新 ID（公众号可能先出标题、后补正文；
  Miniflux API 有更新时间筛选能力）
- 失败重试：导入 Karakeep 失败时记录仍留在待同步队列，
  不能因为「已读过这个 Miniflux ID」就永远跳过
- API 密钥只在服务端使用，不进网页 JavaScript
- **不要同时把同一批订阅再添加到 Karakeep 的原生 RSS 里**：只有 Miniflux 负责订阅入口，
  避免两条链路抢着创建、更新同一篇文章

> 这不是「复制几十行脚本」就结束的工作：重试、元信息一致性、正文版本保护都要实现。
> 但它比改造阅读器核心、从零写批注、维护多平台爬虫，范围小得多。

## 11. 部署

### 硬件

| 项目 | 建议 |
|---|---|
| 系统 | Ubuntu 24.04 LTS，x86_64 |
| CPU | 4 vCPU（v1）；2 核 4GB 可小规模试运行（v2） |
| 内存 | 8 GiB |
| 磁盘 | 80~100 GiB SSD，按图片与归档增长扩容 |
| 运行方式 | Docker Engine + Docker Compose 插件（不需要 Docker Desktop） |
| GPU | 不需要 |

**这是容量规划建议，不是实测最低配置。**资源压力主要来自网页采集与图片，
不是「只有一个读者」就轻。2 核 2 GiB 不建议承载整套组合。

存储不能按「只是网页」估算：假设每天存 100 篇、每篇连图片 1MB，
正文档案约 3GB/月。实际值运行后测量。

### 目录

```text
/opt/private-reader/
|-- compose.yaml
|-- Caddyfile
|-- .env
|-- versions.lock
|-- reader-bridge/
`-- data/
    |-- postgres/
    |-- karakeep/
    |-- we-mp-rss/
    |-- bridge/
    `-- caddy/
```

数据库容器内的挂载路径要按所选版本填写，不能机械复制旧教程：
例如 PostgreSQL 18 与 17 及以前版本的官方镜像默认数据挂载位置不同，
Miniflux 的安装文档已特别说明。

### 浏览器资源

RSSHub 的小红书路由需要浏览器环境，选带相应运行依赖的镜像
（官方 Compose 说明了这种方式），避免另部署一个浏览器服务。

Karakeep 第一版**不额外部署浏览器容器**：正文主要由上游与归档接口提供，
剩余网页先用普通 HTTP 提取。官方配置支持在不配浏览器地址时退回普通 HTTP，
代价是失去 JS 执行与截图能力。这符合降级要求，
不需要为「尽可能自动抓全每个网页」增加常驻浏览器。

### 版本锁定

本轮核实到的 Karakeep 发布版是 **v0.33.2（2026-08-11）**，作为首轮验证基线。

所有组件记录：源码版本或提交号、镜像标签、镜像 digest、对应配置、备份恢复方式。

**不要生产环境全写 `latest`，也不建议自动更新所有容器。**
尤其要区分主分支代码与发布版：前面核实的 API，要在最终锁定版本上做一次实际请求测试，
再进部署清单。

## 12. 配置与访问控制

### Miniflux

```dotenv
POLLING_FREQUENCY=60          # v1
# POLLING_FREQUENCY=15        # v2，见 §14 待决
# SCHEDULER_ROUND_ROBIN_MIN_INTERVAL=15
# FORCE_REFRESH_INTERVAL=5
WORKER_POOL_SIZE=2
POLLING_LIMIT_PER_HOST=1
POLLING_PARSING_ERROR_LIMIT=3

CLEANUP_ARCHIVE_READ_DAYS=-1
CLEANUP_ARCHIVE_UNREAD_DAYS=-1
```

先保留已读与未读文章，避免 Bridge 尚未同步完成、来源数据就被自动清理。
确认备份、保留策略与同步行为后再设清理周期。
15/60 分钟是调度配置，不是上游平台的更新保证。

**Miniflux 默认拒绝抓私有网络地址，而 RSSHub 与 We-MP-RSS 就在 Docker 内网，
需要显式处理私网访问配置。**

### Karakeep

```dotenv
DATA_DIR=/data
DISABLE_SIGNUPS=true
DISABLE_PASSWORD_AUTH=false
DISABLE_NEW_RELEASE_CHECK=true
DB_WAL_MODE=true

INFERENCE_ENABLE_AUTO_TAGGING=false
INFERENCE_ENABLE_AUTO_SUMMARIZATION=false
EMBEDDING_ENABLE_AUTO_INDEXING=false
SEMANTIC_SEARCH_ENABLED=false

CRAWLER_NUM_WORKERS=1
CRAWLER_STORE_SCREENSHOT=false
CRAWLER_STORE_PDF=false
CRAWLER_VIDEO_DOWNLOAD=false
```

另需正确填写 `NEXTAUTH_URL`、随机生成的登录密钥、Meilisearch 地址与密钥；
不配外部 AI 凭证。

**保留用于解析导入 HTML 的内容处理功能，不能把所有处理 worker 一起关掉。**

这些设置是减少外部依赖与资源占用，不是承诺仅靠环境变量就完成全栈隐私审计。

### 暴露面

| 服务 | 是否直接暴露公网 |
|---|---|
| Caddy 的 HTTPS 入口 | 是 |
| SSH | 仅允许自己的管理来源访问 |
| Karakeep 内部端口 | 否，由 Caddy 代理 |
| Reader Bridge | 否，由 Caddy 代理 |
| PostgreSQL、Meilisearch | 否 |
| RSSHub、We-MP-RSS 管理后台 | 第一版只走内网或 SSH 隧道 |
| 浏览器调试端口 | 绝不直接开放 |

首次安装时各管理页面只绑回环地址，通过 SSH 隧道访问；测试完成后再由 Caddy 统一提供入口。

**Docker 映射端口可能绕过 UFW 规则**，不能只配 UFW 却把所有容器端口绑到 `0.0.0.0`。
阿里云安全组用于限制入口。

大陆地域 ECS 用域名对外提供网站服务需处理备案要求；
**不要把「只有自己登录」当作当然豁免。**调试阶段先走 SSH 隧道。

### 鉴权

Karakeep 用自己的本地账户，创建账户后关闭注册。推荐页单独保护，
第一版接受两个登录入口，不部署额外身份平台，不把它描述成已实现单点登录。

**不要给整个域名统一加一层会占用 `Authorization` 的 Basic Auth，
却又期待 SingleFile 的 Bearer API 认证照常工作。**保护规则按路径区分，
或统一通过私有网络访问。Bridge 访问两个应用时直接用 Docker 内部地址与各自 API 密钥。

### SSRF

不能只「打开私网访问」就结束。把采集服务放独立网络，通过网络访问规则实现：
**允许指定的内部订阅服务；禁止访问云元数据地址、宿主机管理接口、无关私网服务。**

关闭公开注册，不提供匿名「抓任意 URL」的接口。
账户凭证与 Cookie 不进日志、公开仓库或网页响应。

## 13. 安全、故障、备份

### HTML 安全

导入内容必须移除脚本、事件处理器、不需要的嵌入页面；只允许预期的链接、图片、正文标签。

图片下载与原文提取要设超时、大小上限，并限制可访问地址，
避免一个恶意 Feed 诱导服务器访问本机、内网或云实例元数据接口。
可信的内部 RSSHub、We-MP-RSS 地址单独列入允许范围，而不是开放任意内网访问。

### 不把登录失败重试成账号风险

```text
短暂网络错误 -> 有限重试
访问频率限制 -> 退避
授权失效     -> 暂停，提示重新授权
验证码页面   -> 暂停，不循环尝试
正文不可读   -> 保留卡片
```

日志中不输出 Cookie、API Token 或完整授权请求。

### 四类故障必须分别显示

| 故障 | 页面处理 |
|---|---|
| 来源列表拉取失败 | 显示最后成功时间与错误状态，保留旧内容 |
| 新文章已发现但正文失败 | 显示元信息卡片与原文入口 |
| HTML 已上传但本地解析失败 | 保留卡片，标记处理失败，允许人工重试 |
| 推荐服务异常 | 回退 Miniflux 按时间阅读，不影响既有正文与笔记 |

最后一条意味着：推荐模块坏了，不会把整个阅读系统一起拖垮。

### 备份

至少备份：Miniflux 数据库、Karakeep 完整数据目录（库 + 附件）、
We-MP-RSS 数据与授权配置、Bridge 数据库（映射与兴趣配置）、部署配置与版本锁定文件。

> 只有文章 HTML、没有笔记数据库，不叫完整备份；
> 只有笔记数据库、没有被批注的正文，也不够。

每天备份，至少保留一份在另一台设备或服务器。
SQLite 用一致性备份（最简单的个人做法：短暂停止写入后打包完整目录），
PostgreSQL 用其备份工具。不随意复制正在写入的单个数据库文件。

**至少实际完成一次「另一套空目录恢复」**，不能只看到压缩包生成就认为备份可靠。
只在 ECS 同一块磁盘复制一个备份目录，防不了整机或磁盘故障。

### 升级要能回退数据

升级前备份，再在少量来源上验证。遇到数据库迁移时，
回退不只是换回旧镜像，还要考虑恢复升级前的数据。

**任何清理任务都不得默认删除带高亮、笔记的文章及其正文附件。**

## 15. 实施顺序与验收

不要先把所有容器启动起来就认为平台完成。

### 阶段 A：验证真实来源（不做推荐）

部署 RSSHub、We-MP-RSS、Miniflux、PostgreSQL。
每类来源各选 2~3 个实际关注的博主，验证：能否拿到新条目、原文链接是否正确、
全文还是摘要、手动刷新是否有效、授权异常是否可见。

**这一步决定来源是否值得长期运行，而不是等推荐页面写完才发现小红书或公众号无法稳定更新。**
尤其先确认公众号账号权限与小红书链接质量。

### 阶段 B：验证站内阅读与批注

部署 Karakeep（与 Meilisearch，若阶段 A 决定要）。
选几篇真实文章，通过归档 API 导入，检查中文、长文、代码、公式、图片、引用，
再实际划线、写笔记、重启服务、重新打开。

此阶段确认**固定版本上**的导入接口、阅读路由、批注持久化都符合预期。

### 阶段 C：接入 Bridge 与日常入口

完成同步、重试、卡片状态、本地排序，再通过 Caddy 提供日常访问。

### 阶段 D：日报与备份恢复

不新增另一条独立采集链，日报复用已有文章与排序。

### 验收标准

| 验收项 | 合格标准 |
|---|---|
| 博主订阅 | 添加后能获取对应作者发布的内容，不混入无关动态 |
| 手动刷新 | 明确区分上游采集与下游拉取，不只是刷新浏览器页面 |
| 正文保留 | Feed 已有全文时，不因再次访问原站失败而丢失 |
| 外链降级 | 没有全文仍保留可用卡片，原文链接准确 |
| 批注 | 刷新、重启、重新登录后，原句与备注仍能找到 |
| 个性化 | 改变兴趣反馈后顺序变化，但不引入未关注来源 |
| 故障恢复 | 同步失败能补偿，授权失效能发现，不静默漏文章 |
| 备份恢复 | 在新环境恢复后，文章、附件、笔记、ID 映射完整 |

## 16. 方案自述的取舍

> 采集调度不自己写，阅读批注不自己写，平台爬虫不从零写；
> 只开发把现有系统连接起来的内容同步、卡片降级与个性化排序。

第一版接受两个边界：**特殊来源需要人工维护授权；极少数内容只能跳原文。**
但文章与笔记的存储、候选来源范围、推荐逻辑、页面入口、备份与迁移，都由自己控制。

**这比直接大改 Karakeep 更符合「最小化二次改造」，也比堆几个 Docker 镜像后
宣称已完整实现，更接近真正可维护的部署方案。**
