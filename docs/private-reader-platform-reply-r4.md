## 一、导入接口这条路成立，我们上一轮错在哪

### 1. 你的核心论断我们核实了

你说「Bridge 调用 Miniflux 的入站 API，不等于 Miniflux 的抓取器访问私网」。源码支持：

- 端点注册在 `internal/api/api.go:55`，handler 是 `internal/api/entry_handlers.go:354`
- 请求体 `entryImportRequest`（`internal/api/messages.go:39-50`）接受
  `url`（必填）、`title`、`content`、`author`、`comments_url`、`published_at`、
  `status`、`starred`、`tags`、`external_id`
- 落库走 `internal/storage/entry.go:252` 的 `InsertEntryForFeed`。
  **这个函数体内只有事务开始、按 hash 查重、写入、提交四步，
  `updateEntry` 出现 0 次，没有任何 fetcher、scraper 或网络调用**
- 正文在 handler 内就地清洗（`entry_handlers.go:429` 调 `sanitizer.SanitizeHTML`），
  不走抓取链路

所以私网拦截在这条路径上根本不参与判断。**上一轮我们查到的那条约束依然真实**
（抓取器在 DNS 解析后、TCP 建连前检查目标 IP，`request_builder.go:184-199`），
它只是不适用于入向路径。`FETCHER_ALLOW_PRIVATE_NETWORKS` 我们保持 `false`，
这一点和你一致。

### 2. 来源记录的创建路径我们也核了，支持你的结论

你担心过「导入接口需要已有 feedID，而创建 feed 会不会又去抓」。核过了，不会：

`internal/reader/opml/handler.go:60` 的 `Import` 是「解析 → 查重 → 校验 → `store.CreateFeed`」，
调的是 **storage 层**的 `CreateFeed`，不是 `internal/reader/handler/handler.go:108`

`miniflux:disabled` 属性支持在 `internal/reader/opml/opml.go:47,50`，

补一句和你一致的提醒：这里用的是 Miniflux 自己的 OPML 创建能力，
**不是**我们项目里那个会漏源的旧导出。迁移依据是完整的来源台账，OPML 只是载体。

### 3. 我们错在哪，以及为什么这个错误值得记下来

上一轮我们的推理是：「Miniflux 拉不到内网 → 受限来源进不了 Miniflux → 必须双库」。

你那句「采集调度由 Bridge 管，与文章必须存 Bridge 没有必然绑定关系」是这轮最有价值的一句。
我们当时把这两件事绑在一起了，因为它们在我们的旧架构里确实是绑在一起的
（旧项目里谁采集谁存）。

这条已经写进我们的内部决议记录，连同错误本身——
**网络限制通常是不对称的：出向严、入向松是常见设计**，因为出向代表
「这个服务会主动连到不可信的地方」，入向代表「可信调用方通过认证接口写数据」。
看到「出向被拦」，下一句应该先问「那入向呢」。

我们已把这条决定记进内部决议（编号 0016，取代上一轮的 0014；
0014 的安全决定被完整继承，被取代的只是它的双库推论）。需要原文我们摘给你。

**因此实施方案 §10.1 的数据归属表不用改**，这是采纳你这条路径的主要收益。

## 二、四处补充，都在这条新路径上

这四条你方案里都没有。**前两条会让文章静默消失或静默错位，第三条会造成两类来源行为不一致，
第四条会让资源验收测错对象。**建议全部写进 v1.1 的正文与验收项，不要只留在往返信件里。

### 补充一：导入不传 `status` 时默认是 `read`，不是 `unread`

`entry_handlers.go:384-386`：

```go
if importRequest.Status == "" {
    importRequest.Status = model.EntryStatusRead
}
```

这条你提到了，我们核实无误，但要强调它的后果有多安静：
首次导入如果忘了显式传 `unread`，文章**直接以已读状态入库**，
在「未读」视图里永远看不到。日报的候选集定义是「最近 7 天发现、尚未标记已读」
（你 §8.1），**这批文章会整批消失，且不报任何错**。

所以对接约定第一条必须是：**首次导入显式传 `status: "unread"`**，
并且契约测试要断言「导入后能在未读视图查到」，不能只断言返回码。

### 补充二：重复导入不更新正文，但**无条件重写已读状态**

这条你也提到了，我们把它拆到 SQL 层，因为它决定了「补正文」该走哪条路。

`InsertEntryForFeed`（`entry.go:262-274`）先按 hash 查重：

```go
entryID, err := s.getEntryIDByHash(tx, entry.FeedID, entry.Hash)
alreadyExistingEntry := entryID > 0
if alreadyExistingEntry {
    entry.ID = entryID          // 只赋 ID，不写任何字段
} else {
    s.createEntry(tx, entry)
}
```

已存在时不调用 `updateEntry`，所以标题、正文、作者、时间**一律不变**。

但 handler 在落库之后**无条件**执行
`SetEntriesStatus(userID, []int64{entry.ID}, importRequest.Status)`
（`entry_handlers.go:446`），而 `SetEntriesStatus`（`entry.go:412-428`）
是一条裸 `UPDATE entries SET status=$1`，**没有「仅当未读时」的保护**。

合起来是两件反直觉的事：

1. 把重新导入当「补正文」的手段是**无效的**，正文不会变
2. 每次重试都会把已读状态刷成请求里带的那个值。
   如果 Bridge 的重试逻辑统一带 `unread`，**用户读过的文章会被反复重置为未读**

### 补充三：补正文要走 `PUT /v1/entries/{entryID}`，它正好满足两个要求

这条是我们替你查的，因为你只说了「后续补正文使用更新接口」，没说这个接口的行为边界。
核完发现它**恰好同时满足「能改正文」和「不动已读状态」**，这是它优于重新导入的根本原因：

- 请求体 `EntryUpdateRequest`（`internal/model/entry.go:88-91`）只有
  `title` 和 `content` 两个指针字段，`Patch` 方法在值非空时才覆盖（`:93-101`）。
  正好适合「先有摘要、后补全文」
- 同样会清洗正文（`entry_handlers.go:337` 也调 `SanitizeHTML`）
- **不触碰已读状态**，这一点核到了 SQL 层：
  `updateEntryHandler`（`entry_handlers.go:292-353`）全函数没有 `SetEntriesStatus` 调用，
  落库走 `UpdateEntryTitleAndContent`（`internal/storage/entry.go:51-63`），
  那条 `UPDATE entries SET` 只写 `title`、`content`、`reading_time`、`document_vectors`
  四个字段，**`status` 不在其中**

**一个会让实施者困惑的细节：这个接口成功时返回 201 而不是 200**
（`entry_handlers.go:351` 调 `response.JSONCreated`），哪怕它是更新语义。
契约测试别按 200 断言，否则会在一个完全正常的调用上失败。

### 综合二、三，对接约定固定为四条

1. 首次导入**必须**显式传 `status: "unread"`
2. 保存 `external_id` 与返回的 entry ID。
   `external_id` 是 hash 的输入（`entry_handlers.go:411-414`：为空时才退回用 URL 算 hash），
   保存它是为了后面能精确查询，不靠标题去重
3. **补正文走 `PUT /v1/entries/{entryID}`，不走重新导入**
4. 请求超时后先按 `external_id` 或 URL 查询是否已写入，再决定重试

这四条要写成契约测试，不能只测一次返回 201 就算过——你这句话说得对，我们照办。

### 补充四：屏蔽规则只作用于抓取路径，导入路径完全不应用

这条是我们核导入接口时顺带发现的，你和我都没提过。**它是一个路径不对称**：

| 路径 | 是否应用 `block_filter_entry_rules` / `keep_filter_entry_rules` | 后果 |
|---|---|---|
| 常规抓取（`internal/reader/processor/processor.go`） | **应用两次**：`:75` 在抓取正文前，`:147` 在正文替换内容后 | 命中规则的条目走 `continue`，**根本不入库，不报错** |
| 导入接口（`entry_handlers.go:354-466`） | **完全不应用**（该区间 `IsBlockedEntry` / `filter.` 出现 0 次） | 传进来就存，无视规则 |

后果是：**同一套规则对普通来源生效、对受限来源不生效**。
将来如果配了任何屏蔽规则，普通来源的文章会被静默丢弃，Bridge 导入的文章不会。
这种不一致在排查时极难定位，因为两边的表现都「看起来正常」。

你方案 §8.1 要求「源端发现、Feed 保存和元信息同步不按推荐分过滤」，
§4.5 要求「采集不预先按兴趣删除」，你这轮又专门提醒
「不要拿 Miniflux 的保留／屏蔽规则来做兴趣推荐」。**三条方向一致，我们采纳，
并把它写成一条更硬的规定：第一版不配置任何 `block_filter_entry_rules` /
`keep_filter_entry_rules`。**

理由有两条，第二条是这轮才有的：一是它会静默丢条目，与「已发现内容全部保存」冲突；
二是**它在两条路径上行为不一致**。

如果将来确实需要屏蔽（比如过滤某个源的推广条目），应当**在 Bridge 侧做**，
让规则对两类来源一致生效，并且被屏蔽的条目要留在台账里标记状态，而不是消失。

### 补充五：WeRSS 的 `gather.browser_type` 是死配置，实际起的是 webkit

你说「不能直接认定一定是 Firefox，实际引擎要看运行代码」。**这个修正成立，
而且比你说的更彻底**——那个配置项在内容采集链路上根本没被读过：

- `gather.browser_type` 全仓只有两处读取，**都在 PDF 导出路径**：
  `tools/mdtools/export.py:90`、`core/exporter.py:67`。
  配置样例 `config.example.yaml:150` 写的 `browser_type: ${BROWSER_TYPE:-firefox}`
  对正文采集没有任何作用
- 正文采集走 `driver/wxarticle.py:29` 和 `:81`，两处都实例化
  `PlaywrightController()`，**不传 browser_type 参数**
- 所以用的是构造函数默认值 `webkit`（`driver/playwright_driver.py:54`），
  之后可被两种方式覆盖：`BROWSER_TYPE` 环境变量（`:136-138`，
  只认 webkit/chromium/firefox/msedge），或本地 Chrome 自动发现（`:141-143`，
  发现到就把引擎改成 chromium 并打印一行日志）

**结论：资源表要改的不只是「加一份 WeRSS 浏览器开销」，而是「测的对象要换」。**
在 Linux 容器里，如果没设 `BROWSER_TYPE`、也没有可发现的本地 Chrome，
实际起的是 **webkit**，不是 firefox，也不是 chromium。
这三套的内存峰值和冷启动时间都不一样，照着 firefox 做容量规划会算错。

你说的「磁盘上安装两套浏览器和两个浏览器同时占用内存不是一回事」，我们同意，
并补一句：**磁盘上要装哪几套，取决于实际启动日志，不取决于配置文件**。
所以 P0 的实测项应该是「启动一次真实采集，从日志里读出实际引擎」，
而不是「读配置文件推断引擎」。

你那条「四种不同事件」的区分我们照单采纳：**请求返回、请求超时、任务完成、
浏览器退出是四件事**，名额不能在 HTTP 一返回就释放，也不能在超时后直接开第二个任务。
这一条比「并发设为 1」这个数值本身重要得多。

## 四、你那条权限边界的提醒，我们采纳并写进 P0

你说：「Miniflux 保持私网保护，并不意味着 Bridge、浏览器和图片下载器天然安全。
它们仍需要阻断不可信 URL 指向云元数据、宿主机和无关内部服务。
只是固定配置的内部 API 调用与不可信文章 URL 获取，必须使用不同的权限边界。」

**这一条我们上一轮没系统讲过，是这轮你给的第二个有价值的框架**（第一个是入向路径）。
它解决了一个我们原本会含糊处理的问题：上一轮我们否掉「打开私网开关」时，
理由里混着两种完全不同的威胁，而它们的防御手段不一样。

按你的区分，我们这样落：

| 调用类型 | 信任级别 | 防御手段 |
|---|---|---|
| Bridge → Miniflux 导入接口 | **固定配置的内部服务地址**，调用方是可信的 Bridge | API 认证 + 内网可达即可，**不需要** URL 校验 |
| Bridge / 浏览器 / 图片下载器 → 文章里的 URL | **完全不可信**，来自外部 HTML 内容 | 必须做 SSRF 防护：拒绝云元数据地址、宿主机地址、无关内部服务；DNS 解析后按实际 IP 判定 |
| Miniflux 抓取器 → 公网 Feed | 不可信（正文抓取会处理外部 HTML 与重定向） | 保持上游默认私网拦截，**开关不打开** |

第三行就是我们上一轮那条 P0-A 的安全决定，它和第二行是同一类威胁、同一套防御，
只是执行者不同。**Miniflux 已经替我们做好了第二、三行，我们要补的是第一行之外
Bridge 自己的那部分。**

具体进 P0 的验收项：Bridge 的正文抓取与图片下载在解析目标 URL 后、建连前，
按实际 IP 拒绝 `100.100.100.200`、`169.254.169.254`、回环、Docker 网段与数据库地址；
并且**重定向后的每一跳都要重新判定**，不能只查第一个 URL。
这一条的测试方法和 Miniflux 那条一样：从容器内构造一个指向元数据地址的条目 URL，
确认抓取失败且失败原因被记录。
