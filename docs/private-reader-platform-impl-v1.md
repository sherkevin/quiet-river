# 1. 产品定义与冻结边界

## 1.1 六项核心能力

| 编号 | 固定要求 | 验收含义 |
|---|---|---|
| R01 | 自己选择博主，多平台自动订阅 | 来源清单由用户维护；不擅自新增作者；有自动更新而非仅有原站入口 |
| R02 | 打开或刷新列表时提交更新检查 | 不是只重画本地缓存；显示每个来源本轮检查、等待和失败状态 |
| R03 | 在本站阅读取得的内容 | 能拿到正文就保存和阅读；正文失败时保留元信息与正确原文链接 |
| R04 | 高亮、批注和自己的笔记 | 有正文可做段落级高亮；无正文可写整篇备注；记录可回看、备份和导出 |
| R05 | 自己的推荐算法 | 对已经关注的新增内容排序；算法、特征、反馈和结果在自己的平台 |
| R06 | 个性化日报及通知 | 从本地已采集内容中选出优先阅读集合；未入选文章仍可在全量列表找到 |

  **“获取全部新增帖子”是采集目标，不是对外部网站永不漏抓的保证。**  我们保证不因为兴趣分低而主动放弃发现和保存；平台限流、有限 Feed 窗口和访问失败造成的缺口，必须单独记录和披露。

## 1.2 控制权的准确含义

  **关注范围由你控制，不要求每个上游内容通道都由你运营。**

允许使用作者原生 RSS、已存在的按博主转发源、自建 RSSHub，以及针对未覆盖来源的开源自建采集组件。第三方按作者提供的 Feed 属于外部内容输入，不等于外部推荐服务。

同时固定以下边界：

| 项目 | 决定 |
|---|---|
| 阅读平台及其必要运行组件 | 完整开源、可修改，可在自己的 ECS 运行和备份 |
| 推荐与日报计算 | 只在自己的服务器执行；不提交给 BestBlogs 或其他平台代排 |
| 第三方按作者转发源 | 允许接入；注明提供方、实际延迟、有限历史窗口和失效风险 |
| 来源侧推荐池 | 不用它替代既有关注来源；本地日报精选完全允许且属于核心功能 |
| 凭证授权 | 允许使用自己的合法凭证；允许第三方 Feed 不等于同意向第三方交出登录态 |
| 收费和扩容 | 默认不购买额外服务，不自动变更 ECS 规格；费用变更须单独批准 |
| 部署拓扑 | 生产阅读、数据、排序和任务服务在 ECS；不以 Mac 常驻采集作为默认前提 |
| 公开分享 | 默认关闭；个人阅读和批注不自动发往个人主页、Pages 或公开 RSS |

  **自托管的是平台，不是互联网。**  上游网站仍决定访问条件；允许外部 Feed，也不等于放弃对自己数据库、笔记、推荐算法和软件版本的控制。

## 1.3 明确撤销的旧判断

以下旧结论不再适用于本方案：

| 旧结论 | 当前定案 |
|---|---|
| 第三方转发一律不合格 | 按博主转发允许使用，现有公众号和 X 通道保留并验收 |
| 为 2C2G 直接删除小红书、B站、公众号需求 | 不删除；用现成通道降低负载，自建组件通过资源验收后启用 |
| 不做推荐，只保留时间顺序 | 永久保留“最新”，同时交付“推荐”和本地个性化日报 |
| 刷新页面只是拉本地列表 | 列表页打开、浏览器重载和刷新按钮都会提交服务器更新请求 |
| 手动收藏可以替代自动订阅 | 手动收藏是补充，不能算作对应博主自动更新已完成 |
| 第三方精选与本地日报精选是同一回事 | 前者改变候选输入，后者在自己的关注内容中分配阅读优先级 |

## 1.4 第一版不做的事情

不做公共广场、多用户协作、商业付费体系、自动发现并关注新作者、外部 AI 推荐、复杂模型训练、全量视频下载、OCR 或音视频转录、原文翻译与 AI 重写。

  **第一版先不部署全文搜索引擎。**  可以浏览自己的笔记、高亮和文章，按来源、标签、时间过滤；不承诺跨全部正文和笔记的全文检索。这个削减不影响高亮和笔记保存。[S03]

# 3. 固定技术架构与职责

## 3.1 架构总图

```text
你关注的作者与标签台账
          │
          ├─ 原生 RSS / Atom ───────────────────┐
          ├─ 已有第三方按作者 Feed ─────────────┤
          ├─ 自建 RSSHub（知乎/B站/小红书）─────┤
          └─ 自建 WeRSS（未覆盖公众号）────────┤
                                               ↓
                         Reader Bridge：刷新调度与采集状态
                         普通 Feed → Miniflux 直接拉取
                         受限适配器 → 受控采集/缓存 → Miniflux
                                               ↓
                                    Miniflux + PostgreSQL
                                    Feed 解析、条目、已读状态
                                               ↓ API
                                   Reader Bridge：内容同步
                             元信息入索引；HTML 归档导入阅读器
                                               ↓
                                    Karakeep 最小安装
                                本地阅读、收藏、高亮、批注
                                               │
                     ┌─────────────────────────┴────────────┐
                     ↓                                      ↓
          Bridge 推荐/最新/日报页面                  原生笔记与阅读界面
                     │
                     └── 本地日报与告警 → 自建 ntfy → 已授权客户端

        Caddy 作为受保护访问入口；数据库与采集管理接口不直接公开
```

## 3.2 组件选择不再横向摇摆

| 组件 | 决定 | 核实能力与限制 |
|---|---|---|
| Miniflux | 固定使用 | RSS/Atom 等订阅与文章 API；读取正文、刷新、已读状态。[S01—S02] |
| PostgreSQL | 固定使用 | Miniflux 的数据存储依赖，不用 SQLite 冒充替代。[S08] |
| Karakeep | 固定使用最小安装 | 原文归档导入、阅读、高亮、备注；不配 Meilisearch 时搜索完全关闭。[S03—S06] |
| Reader Bridge | 固定开发一个独立服务 | 调度、映射、卡片、推荐、日报、健康状态；不是现成开源产品名称 |
| RSSHub | 固定为需要自建适配时的首选 | 只启用已有关注源需要的路由；浏览器功能受资源与账号验收约束。[B1，§8.1] |
| WeRSS / we-mp-rss | 固定为缺失公众号通道的验证对象 | 不迁移已失效的 wewe-rss；先验证选定授权模式、API 和正文链路。[S11] |
| ntfy | 固定为第一版通知服务 | 自建、鉴权、持久消息；默认不接外部推送上游。[S12] |
| Caddy | 固定为新平台入口 | HTTPS 和路径反向代理；不再另叠一套身份平台。[S13] |

Miniflux 按 Apache-2.0 提供代码；Karakeep 使用 AGPL-3.0；本次 RSSHub 的 LICENSE 为 AGPL-3.0；WeRSS 仓库提供 MIT 许可。许可证审核最终针对锁定源码和实际镜像依赖，而不是项目名称；需要启用搜索时再审查 Meilisearch 社区版依赖。[S07、S09、S11、S21]

Karakeep 的首轮接口验收基线选   **v0.33.2**  ，其官方发布记录为 2026-08-11。主分支文档中出现但该版本没有的字段，不能直接写入部署脚本；确需变更发布版时更新版本锁和测试结果，而不是长期追踪 `main`。[S07]

## 3.3 为什么保留 Miniflux

它负责成熟的 Feed 解析、条目持久化、元信息和已读 API；Bridge 不再写通用 RSS 阅读后端。Karakeep 接收已经取得的 HTML，而不是让所有来源重新经历一次网页抓取。

这也是防止“上游已经给正文，阅读器只接收链接后又被原站拦截”的设计决定。需要在选定版本实测归档导入结果，不能把接口存在等同于所有格式已通过。[S01、S04、S05]

## 3.4 只有一个刷新调度所有者

  **Bridge 统一接收定时、页面刷新、手动重试和日报前检查。**  Miniflux 负责执行单 Feed 拉取与解析，不再由多套定时器互相触发。

实施时使用 Miniflux 的 `DISABLE_SCHEDULER_SERVICE=1` 关闭内部调度，并验证单源刷新 API 仍正常。该配置已在官方源码手册中核实；当前内部调度同时包含清理循环，关闭后不能假定上游仍自动清理数据，保留策略必须显式管理。[S09]

WeRSS 采用可由 API 控制的更新方式；可用模式验证后关闭重复的自动采集计时器。若某个上游没有主动刷新 API，则记录 `upstream_refresh=provider_only`，Bridge 只检查其现有 Feed，不假装控制了上游采集。

Karakeep 不再次订阅同一批 RSS，旧 quiet-river 不并行抓同一来源。生产状态改变前先证明没有双重轮询。

# 4. 多平台来源接入

## 4.1 一个作者可以有多个采集通道

保留独立的 `source`（作者/关注对象）和 `channel`（Feed/回答/文章等通道）。例如，一个知乎作者可以同时有回答 Feed 和文章 Feed；不能因为导入了其中一个就算完整覆盖该作者。

通道优先顺序固定为：

1. 已有且可用的原生 Feed。
2. 已有、逐作者提供内容的第三方 Feed。
3. 必须自建时使用 RSSHub 的匹配路由。
4. 对仍无出口的公众号验证 WeRSS。

前一通道失效后可以切到  **同一作者**  的备用通道，但不能自动换成另一位作者或公共推荐池。新收费服务、交付账号凭证或变更关注对象仍需用户授权。

## 4.2 平台接入矩阵

| 来源 | 实施通道 | 必须验证 | 失败后的真实状态 |
|---|---|---|---|
| 博客、GitHub、arXiv、CSDN、掘金、YouTube、播客、Semantic Scholar | 导入真实配置中的 Feed；无 Feed 字段的逐源补适配 | 原始链接、时间、列表更新、正文/摘要类型 | 通道异常或待配置，不能漏出迁移台账 |
| 知乎 115 个作者 | 自建 RSSHub，分别覆盖回答和文章；使用自己的有效授权 | ECS 出口、凭证、请求节流、实际返回条数、两类内容和全文 | 认证失效/受限/正文不可得分别展示 |
| 公众号已有 49 条转发源 | 原样保留两类目录中的实际 Feed 地址 | 实时可达性、更新年龄、条目数、作者身份与原文链接 | 第三方异常；历史可看但新更新未知 |
| 手动登记公众号 | 已有目录先按作者匹配；仍缺的进入 WeRSS 接入任务 | 实际名字与公众号身份；选定授权模式、API、正文 | 待接入，不把“去微信搜索”算成自动更新 |
| X 28 个作者 | 使用清单中已确定的逐作者转发地址 | 最新条目、作者映射、有限历史窗口和服务依赖 | 第三方通道异常，不尝试从 handle 猜哈希地址 |
| 小红书 13 个作者 | 先验证指定作者的合格 Feed；没有时验证 ECS 上 RSSHub 浏览器路由 | 会话可用性、列表与笔记原链、图片/视频内容、浏览器资源 | 未接通仍是未完成项；不默认仅保留快照 |
| B站 4 个来源 | 验证已有通道；需要自建时使用带浏览器依赖的 RSSHub 路由 | 视频与专栏各自路由、浏览器启动和并发 | 资源/通道失败，不将作者主页当新视频卡片 |

平台数量、现有通道和服务器不可直接复用本机浏览器的限制来自 [B1，§4—§8]。本文不以架构选择推翻这些实测。

  **不再试用已在简报中验证失效的公共 RSSHub 实例、wewe-rss 或闭源 JAR 作为生产捷径。**  允许现有逐作者 Feed，不等于重新把公共通用 RSSHub 镜像当作可靠服务。

## 4.3 凭证和浏览器的具体边界

知乎新路由需要的凭证条件按简报 §10 的说明纳入验收：不仅检查旧适配器使用的字段，也检查新路由需要的身份锚点。本文不记录凭证值、不提供规避付费、验证码或访问控制的实现。

小红书采用原站返回的时间时标注 `time_basis=platform`；若只能沿用简报中的 ID 推算时间，应标注 `time_basis=id_derived`，不能写成平台直接提供的精确发布时间。取不到时间可显示“未知＋首次发现时间”，不以伪造发布时间换取接入完成。

浏览器采集在 ECS 上完成，但  **“目标中包含浏览器来源”与“2C2G 已证明能跑浏览器”不是同一结论**  。浏览器路由及 WeRSS 按第 12 节资源门槛启用。未通过时，接入任务继续处于阻塞状态，不把平台移出范围，也不默认把 Mac 变成生产节点。

## 4.4 WeRSS 的固定使用规则

使用 `rachelos/we-mp-rss`，不是名称相似的 wewe-rss。已有 49 条可用公众号转发不会为了统一技术栈而全部替换。

启用时必须同时打开正文采集和 RSS 全文输出，保留永久原始文章地址；当前配置将 `gather.content` 与 `rss.full_context` 分开。[S11]

验证 `web` 等选定模式是否支持自己的账号、是否直接完成采集、是否具有可调用的单公众号更新动作。没有源码或运行证据时，不宣称整个授权链零外部依赖。关闭非必要外部代理、级联、AI 和重复调度；当前配置中 Redis 及其内置服务有独立选项，不能只省略一个 Redis 容器就假设没有此依赖。[S11]

不固定臆造的刷新 API 路径。实施者从锁定版本的 OpenAPI/代码取到真实路径，写入适配器契约测试；接口未验证则该自动刷新能力不能验收。

## 4.5 “全部帖子”的覆盖方法

采集不预先按兴趣删除；但 Feed 可能只保留最近若干条，断线后也不一定能回补。对每条通道记录：列表窗口、是否支持分页、最近成功时间、是否存在疑似缺口。

若源一天发布量超过窗口，或故障跨越整个窗口，记录 `gap_suspected=true`。有合法分页接口才有限补抓；没有则明确“历史可能缺失”。初次导入的旧文章标记为 `bootstrap`，不全推入当天日报。

# 5. 页面刷新与自动更新

## 5.1 刷新的产品合同

以下操作提交真实服务器更新请求：进入“最新/推荐”列表、浏览器重新加载列表、点击刷新按钮。

```text
页面立即取得本地分页列表
            ↓ 同时
POST /desk/api/refresh
            ↓
创建 refresh_run，返回 202 + run_id
            ↓
按当前范围形成来源任务，复用正在执行的同源任务
            ↓
能检查的立即排队检查；受限的显示等待及下一次可检查时间
            ↓
发现条目 → 去重与元信息入库 → 卡片可见
            ↓
正文处理独立排队，不阻塞卡片
            ↓
页面提示“发现 N 条新内容”，用户选择加载，保持当前阅读位置
```

以上 `/desk/api/...` 均是  **待实现的 Bridge 接口**  ，不是 Miniflux 或 Karakeep 的现成地址。

初版用轻量轮询读取任务结果即可：运行中每 2 秒，闲置时停止高频轮询。离开页面不取消已经提交的后台任务。相同范围在短窗口内连续刷新合并执行，但每次操作都返回可跟踪的运行结果，而不是无提示地忽略。

## 5.2 刷新范围

| 当前页面 | 默认检查范围 |
|---|---|
| 全部关注 / 综合推荐 | 所有启用采集的关注来源，分批执行 |
| 标签页 | 该标签下的来源，重复作者只检查一次 |
| 博主页 | 该作者各个启用通道，优先执行 |
| 正文或笔记页 | 不自动反复抓全库；提供返回列表及更新入口 |

后台定时采集继续运行；用户不开网页不影响正常更新。系统不会通过“只有你刷页面才采集”的方式掩盖持续订阅需求。

## 5.3 刷新不等于绕过上游缓存和限流

三个时间必须分开保存：

- `last_attempt_at`：我们上一次尝试检查的时间。
- `last_feed_success_at`：成功取得有效 Feed/列表的时间。
- `provider_checked_at`：上游自己声明的原平台检查时间；没有提供就保持空值。

文章的 `published_at` 是第四种时间，不替代上述任一项。对第三方 Feed 成功取回 304，可以说明订阅源按其缓存状态没有变化，不能证明原平台刚刚没有发布内容。

页面必须明确区分：`RUNNING`、`SUCCEEDED_NEW`、`SUCCEEDED_NO_NEW`、`COOLDOWN`、`AUTH_REQUIRED`、`UPSTREAM_ERROR`、`RESOURCE_WAIT`。已知上游内容可能滞后时显示提示，不显示笼统的“全部已是最新”。

## 5.4 防止重复请求与双重调度

普通 Feed：Bridge 执行定时/手动计划，调用 Miniflux 的单源刷新 API，再读取结果。

受限来源：Bridge 先通过同一账户/平台的限制器执行采集，将成功原始 Feed 缓存到本地，再让 Miniflux 读取内部只读缓存地址。  **缓存地址只返回内容，不再次触发爬虫。**  首次没有有效缓存时返回错误而非伪造空 Feed；旧缓存存在时保留，并用独立状态说明本次上游失败。

缓存需保留原始基址，处理相对链接，不让 `source_url` 被内部地址覆盖。Miniflux 自身的 `checked_at` 只代表它检查了什么 URL，前端以通道台账的真实上游状态为准。

同平台限流应跨多个镜像/Feed 域名按 `rate_limit_group` 聚合；不能用换主机名规避同一供应商或账户的请求预算。

## 5.5 初始更新策略

| 类型 | 自动检查初值 | 手动刷新 |
|---|---|---|
| 普通原生 Feed | 30 分钟 | 除短时间任务合并外，提交实际检查 |
| 逐作者第三方 Feed | 60 分钟，或服从提供方约定 | 读取提供方当前 Feed；无 API 不承诺强制回源 |
| 知乎自建路由 | 起始沿用旧通道的保守保护，再逐源验证调整 | 进入更新队列；受限时显示冷却与原因，不假报已更新 |
| 小红书/B站浏览器路由 | 通过验收后起始 60 分钟，全局浏览器并发 1 | 优先排队，服从会话、供应商与资源限制 |
| 自建公众号 | 通过验收后起始 120 分钟 | 有已验证接口则先采集再拉 Feed；否则说明仅检查现有 Feed |

这些是  **本文初始参数**  。旧知乎 8 秒间隔、6 小时重抓和失败 3 次保护来自实测，不能无验证地取消；但六小时也不能被伪装成用户认可的产品时效。若其长期妨碍交互更新，该通道记为时效不达标并安排改进。[B1，§5]

一次刷新可能涉及上百位作者，不承诺整批在几秒内完成。首屏读取缓存、各源进度持续可见、发现即展示，才是本方案的交互保证。

# 6. 正文提取、保存与外链降级

## 6.1 正文处理顺序

1. 从 Miniflux 读取原始 HTML 和元信息，不能从旧 400 字摘要反推正文。
2. Feed 已给可读正文时直接使用；部分正文时仅做必要的一次补抓，并将补抓纳入同一来源的限制器。
3. 识别登录页、验证码、跳 App 提示、广告模板、错误页及空内容，不能仅看 HTTP 200 或字数判断成功。
4. 安全清洗，保留文章结构、代码、表格、图片和引用；保存来源和抓取版本。
5. 通过 Karakeep 的归档接口导入，解析完成后才将阅读按钮标记为可用。[S04—S05]

采集所有已发现帖子与“需要全文时再处理”不冲突。2C2G 上可以让正文队列单并发，优先当前打开文章和待阅读的新文章；未完成正文的卡片也保留。

## 6.2 内容状态不是一个成功布尔值

| 状态 | 含义 | 用户动作 |
|---|---|---|
| `FULL` | 已验证具有可读正文 | 站内阅读、高亮、批注、查看原文 |
| `PARTIAL` | 只有摘要/部分正文/排版缺失 | 阅读已有部分，明确非全文，可查看原文 |
| `META` | 标题等元信息及原文链接可用 | 打开原文，写整篇备注 |
| `PROCESSING` | 正文正在处理 | 先看卡片或原文，不阻塞列表 |
| `FAILED` | 本次正文处理失败 | 保留上次有效内容及重试信息 |

更新发现失败独立记录在来源状态中。没有新标题和原文链接时，不生成“最新文章”占位卡片。

## 6.3 永久原链与去重地址分离

保存 `original_url`、`canonical_key`、`source_home_url` 和 `feed_url`。卡片“看原文”用具体文章地址，“去主页”用作者主页，不能混用。

删除跟踪参数只在经过验证的平台规则中进行；微信公众号文章识别参数、带签名的访问地址不统一清空。第三方 X 转发地址中的哈希直接从原配置复制，不自行推导。[B1，§8.5]

同一文章从多个通道出现时，合并为一个可读对象，同时保留所有来源关联。语义相似的不同作者文章只折叠分组，不强行视为同一文章。

## 6.4 HTML 与媒体策略

归档保存原文，不做生成式改写。脚本、事件属性、表单、跟踪像素和危险 URL 协议必须去除；不运行外站脚本，也不默认用 iframe 嵌入外站。

正文图片尽量下载至自己的归档并修正懒加载和相对 URL。  **图片本地化是一项独立实现任务，不能假设启用 SingleFile 接口就自动下载了所有外部图片。**  第一版每张图片、每篇正文和总附件体积设置上限；超限保留占位与原文入口，不静默截断并标记“完整”。

【初始参数】单张图片上限 5 MiB；单篇归档上限 20 MiB；普通下载 20 秒超时；全篇任务 90 秒上限；附件下载并发 1。数值可在样本测试后调整，不是组件要求。

公式、复杂表格、SVG 和代码高亮必须用真实技术文章验收。可使用本地静态渲染资源，但不能因公式渲染依赖外站脚本而重新开启原页脚本执行。不能保留时标记排版受限，仍保留原文链接。

不自动下载整段视频、播客音频，不承诺从图片文字中选中高亮。封面图可用于卡片，但不能作为原文链接。

## 6.5 导入与补齐的正确状态机

| 已有状态 | 新内容到达时的操作 |
|---|---|
| 尚无 Karakeep 对象 | HTML 导入使用 `ifexists=skip`，记录返回 ID |
| 仅链接对象、尚未向用户提供可批注正文 | 保留备注；验证后可 `append-recrawl` 补正文 |
| 已有公开给当前用户阅读的正文版本 | 默认冻结；新版本只追加归档，不自动重解析替换 |
| 上次导入超时但可能已成功 | 先按原始 URL 查询/对账，再决定重试，避免重复对象 |
| 已有用户高亮、批注或备注 | 不覆盖用户字段，不自动迁移锚点，不删除旧附件 |

`skip` 不会替已有链接对象自动补上新全文。实现时必须区分首次导入和后续补齐；Karakeep 当前源码提供 `skip`、`append`、`append-recrawl` 等模式。[S05]

归档上传成功不等于解析完成。Bridge 要确认返回对象、内容状态和本地阅读结果；失败保留卡片。进入用户可阅读状态后使用本地版本锁，防止异步补抓与用户批注并发时替换正文。

# 7. 高亮、笔记与版本保护

## 7.1 复用原生阅读器

文章内的选择文字、高亮、批注、整篇备注和收藏由 Karakeep 负责，不重写编辑器或 DOM 锚点系统。官方文档支持保存备注与高亮。[S06]

“我的笔记”入口必须能找到自己的记录，不得只在产品图中出现。优先使用锁定版本的原生高亮列表/文章详情；若该版本没有满足需要的跨文章列表，Bridge 通过官方 API 分页列出高亮和备注，跳回原生详情，  **不另存一份可编辑正文或笔记主库**  。

这种最小列表只做时间、作者、来源标签过滤。无 Meilisearch 时不承诺关键词全文检索。[S03]

## 7.2 不同内容的笔记粒度

- 文字正文：段落级高亮、批注和整篇备注。
- 部分正文：只对已保存内容高亮，始终提示不是完整文章。
- 只有元信息：整篇备注，不假装能在本站标注原站未取得的句子。
- 视频/图片为主：资料级备注和已有说明文字高亮，OCR/转录不属于第一版。

仅元信息文章需要写笔记时，创建关联原文的 Karakeep 对象。若对象会自动触发抓取，必须限制其并发/域名并排除受限平台的非授权二次回源。必要时使用带来源链接的文本对象作为整篇备注载体，后续关联正文对象，但不自动移动或覆盖用户笔记。

## 7.3 可恢复与可导出

第一版包含 Markdown/JSON 导出：文章标题、作者、原文链接、本地对象 ID、创建时间、摘录和备注。导出用于个人 Obsidian 或备份，不自动公开。

笔记正文的主数据仍在 Karakeep；Bridge 可以缓存只读投影，但其丢失后应能由上游 API 重建。文本导出不能替代完整数据库和归档备份，高亮定位还依赖对应正文版本。

每篇至少保留内容哈希、采集时间、来源类型与处理版本。默认不自动覆盖已经可阅读的正文；新版本可手动选择切换，但先备份旧版本和记录。多份归档存在并不证明高亮迁移已经解决。[S04—S05]

手工使用浏览器扩展保存自己已获准访问的网页是补充方式，不把它当作自动订阅成功。Karakeep 有 SingleFile 集成入口。[S04]

# 8. 本地个性化推荐

## 8.1 推荐在采集之后，不控制是否采集

```text
全部关注来源的新内容
          ↓ 先保存
本地候选集合
          ├─ 最新视图：时间排序
          └─ 推荐视图：兴趣、偏好、时效和多样性排序
                                  ↓
                              个性化日报
```

源端发现、Feed 保存和元信息同步不按推荐分过滤。低分文章仍在“最新/全部”中；未入日报不等于删除、已读或取消关注。

默认推荐候选为：当前关注且未被用户明确隐藏的来源中，最近 7 天发现、尚未标记已读的条目。标签页再加显式标签条件。“全部”仍可查看更早和已读条目；因错误暂停采集的来源不能从健康覆盖统计分母中消失。

手动收藏的其他网页默认属于单独收藏集合，不自动进入“关注博主日报”。需要纳入时由用户显式勾选。

## 8.2 现有标签用作来源级先验

现有 16 个标签按阅读需求划分，保留原组织方式。[B1，§4、§8.10]

每个来源保留 `source_tags`，文章内容匹配得到 `article_topic_features`，二者不混同。某位作者属于 Agent 标签，不意味着他每篇文章都是 Agent 内容。

冷启动时标签权重相同，来源优先级中性；用户当前选择的阅读主题优先。标签下有更多作者，不能自动获得更高偏好权重；一个作者重复命中多个标签，也不能简单累加占优。

为避免初版退化成纯时间线，基于已有标签建立一份本地、可编辑的主题词与同义词配置，用标题、摘要和已取得正文计算内容匹配。词表是初始特征工程，不是已经训练好的语义模型；明确保留匹配证据。

## 8.3 固定第一版排序算法

第一版采用 CPU 上的确定性规则，不部署大模型或向量数据库。所有特征均归一化到 0—1：

```text
R(i) = 0.7 × 文章主题匹配 + 0.3 × 来源标签先验

Score(i) = 0.55 × R(i)
         + 0.20 × 作者显式优先级
         + 0.15 × 时效性
         + 0.10 × 显式反馈相似度
```

这是  **本文初始参数，不是离线实验或 A/B 测试结果**  。未配置的作者优先级、无足够反馈的反馈项均取中性值；没有近期主题选择时使用持久兴趣设置，不杜撰个人画像。

时效性采用可解释的衰减，例如半衰期 48 小时。时间未知时用首次发现时间并标明时间依据，不把估算时间当成原始发布时间。

内容匹配使用简单规范化、词组匹配和词频上限，防止重复堆关键词无限加分；标题权重高于正文中偶然出现的单个词。只有摘要的文章依据现有字段计算并标注特征不足，  **不把“没有全文”当作低质量惩罚**  。

显式“感兴趣”增加相关主题的偏好，“不感兴趣”先作用于该文章和相关特征。第一版不把打开、停留时间、高亮自动视作赞同；用户可能是在批评内容。

## 8.4 去重与多样性重排

精确同一文章按稳定标识合并，不重复占日报名额。不同作者谈同一事件时，可以按标题相似度分组，在推荐视图折叠但允许展开，保留每位作者的原文。

【初始参数】前 10 条同一作者尽量不超过 2 条；同事件默认先显示 1 条；候选不足时放宽，不为了凑数引入未关注作者。

“最新”视图保持完整可核验列表，明确标注被折叠的条数。用户操作“不感兴趣”后在推荐和日报中隐藏该条，不从本地库硬删除。

## 8.5 可解释与可复现

每次排序记录 `ranking_version`、特征摘要、最终得分和使用的兴趣配置版本。卡片用简短理由说明：匹配哪个阅读主题、是否为优先作者、是否为新发布内容。

不写“猜你一定喜欢”“深度评分 95 分”一类无依据结论。排序列表使用稳定的快照 ID；新内容到达时提示用户加载，不在用户点击过程中重新洗牌。

建议验收不是问“算法是否足够聪明”，而是：更改兴趣是否改变相关条目的顺序；外链卡片是否公平参与；推荐是否越过关注范围；同一配置下结果是否可复现。

# 9. 日报生成与推送

## 9.1 日报就是本地精选，不是另一个外部来源

日报在自己的内容库中执行筛选，与推荐页共享特征和排序模块。采集链只运行一份，不为日报再接一个第三方精选流。

【初始参数】每天 08:00 生成一次，最多 15 条；可选 30 分钟阅读预算；按应用的业务时区划定日期。条目不足时只发实际数量，不凑满。以上是待部署的应用任务配置，  **本文没有创建 ChatGPT 定时任务或发送任何通知**  。

时间戳统一以 UTC 保存；`APP_TIMEZONE` 决定页面和日报日界线。本文将 `Asia/Shanghai`（北京时间）定为初始业务时区，这是可修改的产品默认值，不根据访问 IP 自动改变；同一次日报不能混用服务器时区和用户时区。

## 9.2 日报的候选窗口

从“上次日报候选截止时间”至“本次截止时间”首次发现的关注内容中选择，排除首次批量迁移的历史 `bootstrap` 条目和明确不感兴趣的条目。发布较早但本次才发现的文章，单列为“延迟发现/补充阅读”，不冒充当天发布。

生成前提前发起一轮正常更新检查，但设置等待截止，不让失效来源把整个日报无限卡住。截止时冻结候选快照，报告哪些来源尚未成功检查、上游时效是否未知。之后到达的文章进入下一次日报或用户手动生成的补充版。

对有大量历史未读内容的情况，另设“积压待阅读”视图；不把所有积压自动混入每日新增日报。

## 9.3 日报页面内容

```text
日期、候选截止时间、生成版本
本轮发现条目数、成功检查来源数、异常来源数

优先阅读
  标题、作者、来源、原始发布时间
  原文摘要或已有内容摘录
  本地推荐理由
  站内全文 / 部分内容 / 原文链接

其他更新
  查看本轮全部内容

采集说明
  哪些来源授权失效、冷却、第三方可能延迟、存在缺口
```

第一版用原始摘要/摘录与模板，不生成模型改写摘要。没有正文时不得生成“全文要点”。“摘要”与“推荐理由”分开，防止把系统判断当作作者观点。

文章阅读预算是估算；可以提供依据和修改入口，不当作真实阅读时长观测。

## 9.4 推送与幂等

用自建 ntfy 发送日报链接、日期和简短计数。默认通知不携带私人笔记和完整正文；点击后仍需登录阅读平台。ntfy 开启鉴权和磁盘消息缓存，不采用默认匿名公开主题。[S12]

本地通知表保存 `digest_id`、`revision`、`channel`、`attempts`、`sent_at` 和服务返回 ID。生成任务幂等，重复触发不产生多份正式日报。

网络超时可能出现“服务已收到但调用方未知”，不能在无幂等支持的投递协议上承诺绝对不重复送达。此类状态记为 `delivery_unknown`，避免立即无脑重发；客户端可依据日报 ID 去重。

用户点击“重新生成”只产生新修订页面，默认不再次推送。日历日期相同但内容更新应有明确 revision，不覆写已经被阅读的正式版而无痕修改。

## 9.5 通知的真实依赖

默认不接 ntfy 的外部推送上游。可直连的客户端收到实时事件；离线客户端恢复后读取缓存。iOS 后台即时通知、浏览器 Web Push 等可能依赖系统推送服务，不能把它们描述成完全与第三方无关。[S12]

这不取消日报推送要求：第一版要验收至少一个用户实际使用的接收端。尚未配置外部渠道时，本地日报照常生成。第三方投递出口将来可以授权启用，但不会获得推荐或笔记主库的控制权。

# 10. 数据模型与一致性

## 10.1 数据归属

| 数据 | 唯一权威存储 | 其他服务可以保留什么 |
|---|---|---|
| 作者清单、标签关系、通道配置、可见/采集状态 | Bridge 来源台账 | Miniflux Feed ID 等映射 |
| Feed 条目原始内容与已读状态 | Miniflux / PostgreSQL | Bridge 的只读投影和待同步事件 |
| 正文阅读版本、附件、收藏、高亮、批注 | Karakeep 数据目录 | Bridge 的本地对象 ID 和只读笔记摘要 |
| 兴趣、反馈、排序快照、日报、刷新任务 | Bridge SQLite | 可导出备份 |
| 推送消息 | ntfy 缓存＋Bridge 投递台账 | 客户端缓存 |

  **打开文章不自动标记读完。**  第一版从卡片上的明确操作更新 Miniflux 已读状态；Karakeep 的 archive 不自动等同于已读。两边的收藏/稍后读语义需要映射时，采用单向明确规则，不建立难以解释的循环同步。

## 10.2 核心对象

| 对象 | 关键字段与约束 |
|---|---|
| `sources` | `source_id`、平台、名称、主页、平台作者 ID、`followed`、`collection_enabled`、`presentation_enabled`；三种开关分开 |
| `source_tags` | `source_id + tag_id` 唯一；保留多对多关系 |
| `channels` | `channel_id`、`source_id`、类型、Feed/route、提供方、凭证组、限流组、刷新能力、优先级、备用关系 |
| `source_health` | 尝试/成功/上游检查时间、错误类别、下次允许时间、疑似缺口、最近成功快照 |
| `items` | 原始 URL、平台条目 ID、标题、作者、原始时间及依据、首次发现、bootstrap、内容状态 |
| `item_sources` | 一个条目关联多个 Feed/来源，不抹掉出处 |
| `bookmarks_map` | Miniflux entry ID、Karakeep ID、幂等键、同步状态、内容版本、映射版本 |
| `refresh_runs` / `jobs` | 刷新范围、状态、租约、重试、到期时间、关联请求；崩溃可恢复 |
| `feedback` | 明确操作、条目/主题、时间和配置版本；不存推测性赞同 |
| `ranking_snapshots` | 候选截止时间、分数、理由、配置/算法版本 |
| `digests` / `notifications` | 日界线、候选截止、修订、正式发送状态和去重键 |

各字段是待实现的数据合同，不是声称上游已有相同字段。

## 10.3 增量同步与故障恢复

新条目用递增 ID 分页拉取；已存在条目的正文补齐、修改和状态变化，用 `changed_after` 等 API 做重叠时间窗对账。文档支持这些筛选字段。[S01]

只有一条记录的对应阶段落盘后才能推进该阶段游标。一个条目导入失败不能阻止其他条目，也不能因为全局游标前进而永远跳过它；持久失败队列独立重试。

对同一条目采用稳定幂等键。上传请求超时后先查是否已创建；不靠标题去重。内容同步和元信息卡片是不同阶段，必须允许“卡片可见、正文待处理”。

Bridge 单实例运行，一个 Web 服务加进程内受控任务队列，任务状态持久化到 SQLite；避免多 worker 各自启动一套 scheduler。进程重启后过期租约重新入队，不把正在运行状态永远留在数据库。

# 11. Reader Bridge 的开发合同

## 11.1 最小实现选型

采用 Python、轻量 Web 框架和服务端 HTML 模板，SQLite 保存任务和台账，异步 HTTP 客户端连接上游。初版推荐使用普通词表/规则计算，不为一个用户引入向量库或训练框架。

这不是重做 Miniflux 或 Karakeep。允许开发的模块固定为：

| 模块 | 必须实现 | 不实现 |
|---|---|---|
| `registry` | 完整来源迁移、标签、作者与通道关系 | 作者发现和自动关注 |
| `refresh` | 统一队列、同源合并、冷却、缓存、手动与定时触发 | 通用分布式调度系统 |
| `sync` | API 分页、版本/ID 映射、正文导入、重试 | 私改上游数据库 |
| `ranking` | 本地特征、显式反馈、排序、多样性 | 大模型训练、云端推荐 |
| `desk` | 元信息卡片、最新/推荐、来源状态、笔记入口 | 高亮编辑器、完整文章阅读器 |
| `digest` | 本地日报快照、ntfy 投递、幂等 | 广场、播客生成、海报流水线 |
| `health` | 凭证组、通道健康、告警、资源等待 | 自动规避验证/付费/访问限制 |
| `export` | 来源台账和笔记的个人导出 | 自动向公开站点发布 |

## 11.2 自定义接口

| 接口 | 行为 |
|---|---|
| `POST /desk/api/refresh` | 提交范围和原因，返回 `202 + run_id` |
| `GET /desk/api/refresh/{run_id}` | 读取逐源结果、冷却和错误；不包含密钥 |
| `GET /desk/api/items` | 分页元信息，按最新/推荐和来源标签过滤 |
| `POST /desk/api/items/{id}/feedback` | 显式感兴趣、不感兴趣、已读等操作 |
| `GET /desk/api/sources` | 来源清单、健康、更新时间、刷新能力 |
| `POST /desk/api/digests` | 手动生成本地日报修订，默认不重复发送 |
| `GET /desk/api/notes` | 通过上游 API 形成只读笔记列表或跳转信息 |
| `GET /internal/feeds/{channel_id}` | 受限通道的缓存 Feed，只读、仅内部鉴权访问 |

所有写接口要求认证、CSRF 防护/来源校验、输入验证和服务端权限检查。获取列表的 GET 不产生隐式全量采集副作用；页面初始化显式 POST 才触发更新。

## 11.3 上游接口使用原则

Miniflux 使用 `X-Auth-Token`；Karakeep 使用 Bearer API Key。它们不共享同一登录 cookie，Bridge 后端代为调用，浏览器不持有这些服务密钥。[S01、S04]

用户日常不需要进入两个管理后台依次点击刷新；有主动采集能力的上游由适配器串联。必须进入原站重新授权属于账号操作，不是用户每次刷新的固定步骤。

不调用 Miniflux “刷新全部”接口制造不受控请求风暴，统一拆成可限流的单源任务。单源 API 是同步执行语义，整批工作由 Bridge 异步调度。[S01]

禁用内部 scheduler 是为了只有一个刷新所有者，但也意味着 Bridge 有明确的调度开发量。不能把这套组合称为“只启动 Docker 就已完成”或“零二开”。

## 11.4 未确认接口的处理

当前核查证明了 Miniflux 读/刷新接口、Karakeep HTML 导入及备注高亮能力。WeRSS 单源触发路径、Karakeep 发布版的笔记枚举和具体页面路由，需要在版本契约测试中记录。  **不通过猜 URL 或直接写数据库绕开兼容性问题。**

正文 HTML 转存、卡片页、推荐、日报和运维桥接代码，本次文档交付中没有实现；开发完成后需按第 17 节验收。

# 12. 2C2G 资源与扩容边界

## 12.1 当前机器不变，但不能提前承诺全部组件都装得下

【现状】原系统在 2C2G 上主要保存摘要和元信息，ECS 登录态源当时停在快照；这不是新全文阅读、数据库、批注和浏览器采集栈的负载测试。[B1，§3、§6]

【决定】先用现有 2C2G 验证，不默认买新机，不为了省内存删除用户指定的平台。利用已有第三方逐博主 Feed 减少 ECS 上重复抓取；确实需要浏览器的来源仍按需求进入验收。

资源不足的后果是  **相应组件尚未通过上线门槛**  ，不是把自动采集改成静态主页就算交付。

## 12.2 服务组合分层，而非功能排除

| 层 | 服务 | 启用规则 |
|---|---|---|
| 阅读核心 | Miniflux、PostgreSQL、Karakeep 最小安装、Bridge、Caddy、ntfy | 首先验收的 6 个常驻服务 |
| 非浏览器适配 | 自建 RSSHub | 相关来源需要时启用，限制并发、缓存和正文导入量 |
| 浏览器采集 | RSSHub 所需浏览器能力 | 小红书/B站适配实测通过后启用；全局并发 1，浏览器资源不得无界增长 |
| 缺失公众号采集 | WeRSS | 仅为仍无合格 Feed 的来源启用；账号、依赖和资源通过后增加 |
| 搜索增强 | Meilisearch 开源社区版 | 第一版不启用，后续单独资源变更 |

是否独立浏览器容器、具体镜像名和启动依赖按锁定 RSSHub 版本的官方部署文件确定；不从旧的 Node/pnpm 安装坑重新手工拼依赖。必须固定镜像/源码，不使用未经核实的社区公共实例。[B1，§8.1]

  **不安装 Karakeep 的独立浏览器容器。**  上游取得的 HTML 通过归档导入；Karakeep 自身只允许必要的普通 HTTP 处理，动态页面失败就明确回退。官方最小安装支持这种功能取舍。[S03、S10]

## 12.3 首轮限额

以下是本文保守初始值，需要以实际指标调整：

| 资源动作 | 初始策略 |
|---|---|
| 全局普通来源任务并发 | 2 |
| 每个平台/账户活跃采集 | 1；同时受请求间隔和冷却限制 |
| 浏览器任务并发 | 1，不与批量正文导入同时制造峰值 |
| 正文转存/图片下载 | 各 1 |
| Karakeep crawler worker | 1 |
| 本地模型、OCR、截图、PDF生成、视频下载 | 关闭 |
| Web 前端编译和容器镜像构建 | 在另一台受控构建机器完成，ECS 只运行固定产物 |
| 数据库连接池 | 单用户小池，具体上限按镜像配置验证 |

不把 `NODE_OPTIONS` 的堆上限当作整个 Node 进程的内存上限；浏览器和图片解码可能在额外内存中。容器内存上限设置后要做任务失败和队列恢复测试，不能只看到“主机不崩”就忽略持续 OOM 的采集容器。

Swap 可以用于应急缓冲，不作为生产长期靠换页运行的容量方案。资源不足时排队、提示并告警，不悄悄丢掉任务或文章。

## 12.4 容量验收和唯一变更路径

依次启用核心、RSSHub、浏览器、WeRSS，每一步记录空闲/峰值内存、CPU、任务延迟、OOM、重启次数和磁盘增量。

【验收目标】代表性负载下连续 72 小时无 OOM、无持续换页造成的交互不可用；稳定负载保留约 250 MiB 以上可用内存作为观察目标；缓存列表在选定网络和样本负载下 p95 不超过 2 秒。以上都是测试阈值，不是已经测得的结果。

若未通过：先降低并发、移除重复抓取、关闭非核心功能和减少无用媒体；仍不能通过，就形成资源变更单。  **变更单优先讨论内存提升至 4 GiB，必要时再看 CPU和磁盘；价格取阿里云控制台实际报价。**  在用户批准前不购买、不更改实例、不换成闭源付费代采，也不自动缩减平台需求。

这明确区分了“架构已决定”和“现有预算已足以满足全部负载”。后者目前未知。

## 12.5 存储策略

没有提供 ECS 的剩余磁盘容量，因此部署前实测。不能把原 5.7MB 摘要缓存当成全文档案容量依据。

计算方法：

```text
月正文增量 ≈ 每日新增文章数 × 单篇平均保存大小 × 30
总需求 ≈ 应用数据 + 附件 + 镜像 + 日志 + 本地备份暂存 + 安全余量
```

例如每天 100 篇、每篇含图片平均 1MB，档案约增加 3GB/月；这是示例算式，不是对当前来源更新量的预测。

默认不按“每源 60 条”删除新平台的知识资产。元信息和有笔记/收藏的正文保留；普通附件的保留期须显式配置后再启用清理。磁盘使用 70% 提醒，85% 暂停大附件并提醒，90% 阻止危险批量写入；不删除笔记腾空间。因空间暂停全文时，继续尽可能保存小型元信息，并显示 `RESOURCE_WAIT`。

## 13.2 版本与源码归档

Karakeep 首轮基线 v0.33.2；其他组件选择实施时经过接口和安全检查的稳定版本。所有镜像记录实际 digest，不能编造一个看起来固定的摘要。

`versions.lock` 必须包含组件、来源仓库、tag/commit、镜像 digest、许可证、文档版本与契约测试结果。RSSHub 高频变化的路由也固定到验证过的提交/镜像，不用浮动 `latest`。

PostgreSQL 选支持的固定版本，并按该主版本确定数据挂载目录。官方示例提醒 PostgreSQL 18 与 17 及以前的镜像目录不同；不能换了主版本却继续无检查挂载旧路径。[S08]

本地保留源码和构建说明、必要制品及锁文件，能够构建自己的修改版。不能只能运行厂商镜像，却找不到对应源码和依赖版本。

## 13.3 初始化顺序

1.   **前置备份。**  导出现有完整来源配置和历史缓存，校验哈希，记录旧服务启动配置与监听端口。
2.   **主机检查。**  确认发行版、架构、内存、磁盘、时钟、已有容器/端口、安全组与出站网络；不默认停掉旧服务。
3.   **内部启动数据库与应用。**  先启动 PostgreSQL、Miniflux、Karakeep，再启动 Bridge 和 ntfy；此时只通过回环映射＋SSH 隧道访问。
4.   **创建本地账号和服务 API Key。**  只在隔离访问条件下开放首次注册；创建用户后关闭 Karakeep 注册，移除初始化管理员明文环境变量。
5.   **执行接口契约测试。**  Feed创建/读取/刷新、SingleFile导入、高亮/备注回看、写入与备份均通过后导入少量样本来源。
6.   **逐层接入来源组件。**  先现成 Feed，再知乎等非浏览器路由，再浏览器和公众号自建通道；每层单独验证资源。
7.   **启用刷新、同步、推荐、日报和告警。**  确认唯一调度所有者，旧系统同源采集停止后才全量上线。
8.   **建立正式受保护入口。**  完成网络与域名要求后启用 HTTPS；进行未登录访问、密钥泄漏和附件权限测试。

这里的启动文件需在实施阶段生成并执行 `docker compose config` 校验；本文没有附带已完成 Bridge 镜像的 Compose，所以不能直接把目录规划当作可运行安装包。

## 13.4 访问入口

日常采用一个阅读域名，地址均为示例：

```text
https://reader.example.com/desk/         推荐、最新、来源、日报、笔记入口
https://reader.example.com/...           Karakeep 原生路由
https://notify.example.com/              私有 ntfy
```

Karakeep 保持根路径部署，Bridge 使用 `/desk/` 前缀，避免修改上游前端构建路径。具体文章深链接从选定版本确认，使用一次集成封装，不把猜测路由散落在所有模板里。

Bridge 页面由 Caddy HTTPS Basic Auth 或等价的受保护入口控制；Karakeep 使用自身账号。  **接受第一版分别登录，不声称已有单点登录。**  反向代理不应把同一 Basic Auth 无差别套到所有 Bearer API 上，避免鉴权头冲突。[S13]

Bridge 的服务端 API 请求使用容器内网地址。所有数据库、RSSHub、WeRSS 管理、浏览器调试端口不直接开放公网。内部管理可以通过 SSH 隧道进行，正常刷新操作不要求用户进入管理后台。

## 13.5 网络与防火墙

只开放正式 HTTPS 所需入口及受限制的 SSH。没有正式域名和证书时，先使用 SSH 隧道调试，不用明文公网口令作为长期入口。

Docker 端口发布可能绕过 UFW 的预期过滤规则；同时配置 ECS 安全组和 Docker网络，数据库不写 `0.0.0.0:端口` 映射，不能只依赖 UFW。[S15]

采集网络、应用网络和数据库网络分开；只授予所需访问。内部缓存 Feed 需要显式允许访问指定服务，但不意味着给采集器开放全部私网地址。重定向和 DNS 变化后也须再次校验目的地址，屏蔽云元数据、环回和无关内网。

验证公网连接应使用真实移动网络或其他可信出口，不只依赖已知存在透明代理的公司网络。IPv4/IPv6 状态单独检查；不要用一次 `curl 200` 就判定所有客户端可达。[B1，§8.7]

大陆地域 ECS 对外提供网站时按阿里云现行要求办理备案等事项。简报中的非标准端口排障经验不构成法律豁免，本文不把换端口列为规避备案的方案。[S16]

# 14. 健康监控与凭证运维

## 14.1 先解决“静默失效”

以凭证组而非来源数量作为认证故障单位。共享一组登录态的 115 个知乎来源，发生明确认证失效时只做必要确认，暂停关联组，发送一条聚合告警，不继续用其余来源重复验证到封禁。[B1，§7]

本地运行状态每 15 分钟检查一次；它检查队列和时间戳，不额外请求平台。认证健康优先复用正常采集结果，长期没有可用结果时才做低频受控验证。

【初始目标】在系统在线、任务服务正常的条件下，认证组最长 6 小时有一个有效健康结论；正常请求一旦发现明确失败立即记录和通知。平台轮询保护较长时须在状态页说明，不保证作者更新立刻被发现。

## 14.2 错误分类与恢复

| 错误 | 行为 | 恢复条件 |
|---|---|---|
| 明确认证失败 | 暂停凭证组，告警 | 用户完成授权后单点验证，再渐进恢复 |
| 403/验证页面 | 不直接等同 Cookie 过期；有限健康判断后退避 | 有成功验证，且不绕过平台限制 |
| 429/明确限流 | 尊重 Retry-After 或配置退避，显示冷却 | 到期后单任务恢复 |
| 网络超时/临时 5xx | 有限重试，不立刻停掉整组 | 重试成功或超过阈值告警 |
| 返回 HTML 非 Feed | 标记格式/通道异常，不显示无更新 | 提供方/路由修复 |
| 全文失败、列表正常 | 只降级正文，更新卡片继续 | 后续补抓成功 |
| 资源不足 | 暂停重任务，卡片与已存正文尽量可用 | 负载下降或资源变更 |
| Bridge 心跳停止 | 进程管理重启，恢复持久任务 | 内部健康验证通过 |

告警包含受影响源数、最后成功时间、脱敏错误类别和需要的操作，不包含 Cookie、完整 token、签名请求或授权二维码。二维码转发需要单独考虑敏感性，不默认发送到第三方。

## 14.3 没有新文章与没有检查成功必须分开

依据 `last_success_at` 和计划周期检查健康，不根据最近文章发布时间判断。作者停更不等于爬虫失败，Feed HTTP 200 也不等于原平台所有帖子均已捕获。

统计至少保留：当前关注总数、启用采集数、健康来源数、认证失效数、待接入数、疑似缺口数。错误导致暂停的来源仍算在应覆盖范围，不能通过改状态美化成功率。

每次日报列出异常输入范围；全量列表顶部有健康摘要，不要求用户进入日志才能知道知乎整体失效。

## 14.4 告警系统自身的边界

ntfy 配置持久磁盘缓存、登录和 `deny-all` 默认权限，创建受限发布/订阅密钥；默认不接外部推送上游。[S12]

ECS 整机离线时，同机告警也无法发送。需要外部心跳监测时，可由另一台受控设备检查；这是监控或备份角色，不是默认生产采集节点。未增加这种监控时，文档和健康页必须说明故障检测边界。

# 15. 安全、隐私与开源依赖

## 15.1 数据不默认离开自己的平台

关闭云端 AI 自动标签、摘要、embedding、非必要遥测和外部错误上报。网页不依赖外部统计脚本和字体 CDN；正文不加载原站脚本。

外部 Feed 可以看到我们请求了它的地址，这属于已标注的输入通道依赖；它不获得本地阅读行为、笔记、兴趣权重或推荐结果。不得为方便把这批数据附带给提供方。

私人来源名单、cookie、API Key、日报和笔记不进入公开 GitHub 仓库或 Pages。本文和之后的配置模板不包含真实密钥。

## 15.2 账号与密钥

初始化在内部访问环境完成，随后关闭公开注册。使用不同的网页登录凭据和服务间 API Key；密钥只放服务端受控配置/挂载，权限最小化，定期轮换。

项目升级可能引入细粒度 API scope，启用时验证只给所需资源权限；不能把“缺 scope 返回403”误当作原平台访问问题。

日志对 URL query、cookie、headers 做脱敏。第三方转发地址可能含私有 token，完整地址只在管理视图出现，普通卡片不显示。

## 15.3 内容安全

所有 Feed 与 HTML 当作不可信输入。禁用外部实体和危险 XML 解析行为，限制解压/下载大小，限制重定向次数，防止 SSRF、压缩炸弹和超大数据触发内存耗尽。

只允许 HTTP/HTTPS 原文链接，外链使用安全的新窗口属性。上传 HTML 的解析与保存不执行 shell 指令；文章内容不能变成调度命令、抓取配置或工具指令。

媒体归档应隔离处理，不能把不受信 SVG/HTML 当成站点脚本执行；附件下载必须有权限控制。随机链接不是认证替代。

## 15.4 版权和平台访问条件

平台定位为个人私有阅读与学习，保留原作者、原文链接和时间。取得内容不自动意味着允许再公开发布；不提供公开全文镜像，不绕过付费墙、验证码或访问限制。

资料中对某些旧通道的失效和限制按原文保存，不扩写成新的法律结论。平台条款和访问条件变化时，更新对应通道风险记录。

## 15.5 软件依赖审核

核对实际部署版本的许可证、源码完整度和构建路径。不能仅凭“代码在 GitHub”“镜像可下载”就认定完整开源；也不因项目有收费托管就自动排除可独立运行的开源版本。

需启用 Meilisearch 时只选择满足开源要求的社区代码/构建，并在依赖清单中记录，不把企业版许可混进主栈。对 WeRSS 等采集组件检查选定模式的网络依赖，而不只检查前端许可证。

# 16. 来源迁移与旧系统切换

## 16.1 迁移入口固定为完整来源配置

从 `subscriptions.json` 逐源生成新台账；OPML 只用于辅助导入有 Feed 的那部分。不能以 Miniflux 导入了 122 个 Feed 就宣称 271 个来源全部迁移。[B1，§4]

保存原 `source_id` 或稳定映射、作者主页、平台作者 ID、Feed 地址、标签、展示状态、采集状态、旧通道备注。多条内容通道不重复创建作者。

Miniflux 的 Feed 分类是单个 category，不能承载16个标签的多对多关系；标签关系放 Bridge台账。[S01]

## 16.2 迁移对账

迁移报告至少输出：

```text
原始来源总数
→ 已建台账数
→ 有可用通道数
→ 自动更新验收通过数
→ 正文验收通过数
→ 仅元信息但自动发现可用数
→ 待授权 / 资源阻塞 / 未找到通道数

另列：所有标签及每个来源的标签关系、3个关闭展示记录、17/18差异
```

注意，Feed 数量可以大于作者数；同一知乎作者有回答和文章两个通道。台账完整与自动覆盖是两个指标，不把它们合成一个“已迁移百分比”。

## 16.3 历史缓存

现有 7,474 条缓存先做只读备份。默认不把它们全部导入 Karakeep，也不设成新平台未读；需要时提供历史时间轴查询或按需补抓。

新来源第一次拉到的历史窗口标记为 bootstrap，用户可以浏览，但不自动成为日报“今日新增”。以后真实更新才进入正常增量链路。

## 16.4 旧 quiet-river 的角色

过渡期保留旧站点为只读历史和迁移对照，不继续给其核心添加推荐、全文、批注和账号体系。新平台保留“最新”视图，不再为此永久维护两套活跃采集系统。

每个来源切换成功后停止旧侧对应自动采集，特别是共享账号来源。不可用来源可以保留旧历史，但不能在新平台标记为仍在正常更新。

迁移不需要先给旧应用新写 RSS 出口。需要复用某段平台识别逻辑时，按原许可与测试迁移规则；简报已说明旧 XML 模块只有解析能力，不假定它能生成 RSS。[B1，§2]

## 16.5 回退

切换前备份配置与映射。新平台发生问题时可将访问入口临时回到旧只读时间轴，但新平台已产生的笔记和正文仍是必须保留的资产，不能用旧 JSON 覆盖新数据库。

恢复旧采集前先关闭新采集，避免同源双重请求。回退不是恢复成“只有元信息所以笔记可以丢”的状态。

# 17. 验收标准

## 17.1 需求与测试一一对应

以下是验收合同，不是已有测试成绩。

| 测试 ID | 测试 | 合格条件 |
|---|---|---|
| A01 | 全量来源迁移 | 271 个来源均有去向；16 个标签关系保留；17/18差异单列，无静默遗漏 |
| A02 | 多通道作者 | 同一知乎作者的回答/文章均可登记和检查；不重复算作两位作者 |
| A03 | 既有第三方来源 | 不因第三方性质擅自关闭公众号/X Feed；能说明提供方和更新时间依据 |
| A04 | 原生 Feed 更新 | 受控测试 Feed 新增条目后，刷新会发起请求并进入本地列表 |
| A05 | 页面刷新 | 开页、重载、按钮均产生可跟踪 run_id，而不是只 GET 本地缓存 |
| A06 | 连续/多标签页刷新 | 同源实际任务合并，不产生重复条目，不延后已有最早可执行时间 |
| A07 | 上游缓存 | 只取得提供方现有 Feed 时不声称原平台已经实时检查 |
| A08 | 限流/凭证失败 | 模拟401/403/429，状态分类正确；共享凭证组不会触发逐源重复验证 |
| A09 | 更新发现与正文失败 | 取得新标题但正文失败时出现卡片；列表失败时显示来源异常而非“无新帖” |
| A10 | 正文导入 | 中文长文、代码、表格、图片、公式各有真实样本；版式限制明确标注 |
| A11 | 正文补齐 | 先摘要后全文的条目能被重新处理；`skip`不被误用为覆盖升级 |
| A12 | 高亮持久化 | 高亮和备注在刷新、重启、重新登录后仍能找到并对应原句 |
| A13 | 正文更新保护 | 新快照不无提示覆盖已提供阅读的版本，不导致既有高亮错位 |
| A14 | 仅元信息笔记 | 用户可写整篇备注并回看；原文按钮指向具体文章而非图片/作者页 |
| A15 | 我的笔记 | 在不部署搜索服务时仍有可用的笔记/高亮查看入口和个人导出 |
| A16 | 推荐范围 | 插入未关注作者的测试条目也不会自动进入推荐/日报 |
| A17 | 推荐有效性 | 改变主题或显式反馈会改变相关条目顺序；结果可复现、有理由 |
| A18 | 全量保留 | 不入日报和低分文章仍可查；展开重复组能看见各作者文章 |
| A19 | 日报 | 新增候选、历史bootstrap和延迟发现区分正确；截止时间与时区一致 |
| A20 | 日报幂等 | 重试不产生多个正式快照；未知投递状态可追踪，不承诺不可证明的exactly-once |
| A21 | 故障恢复 | Bridge中断/导入超时/上游暂不可用后可恢复，不重复笔记、不丢待处理项 |
| A22 | 未登录访问 | 页面、API、附件、导出、ntfy主题均不能绕过权限获取私有数据 |
| A23 | HTML/URL安全 | 恶意脚本、内网URL、异常重定向、超大归档被拒绝或隔离 |
| A24 | 2C2G资源 | 核心及每个新增采集层通过第12节压力测试；失败任务可恢复 |
| A25 | 完整备份恢复 | 空目录/新实例恢复后，来源、正文附件、笔记、映射、日报和配置一致 |
| A26 | 关闭厂商后台依赖 | 不配置厂商云账号与外部AI时，已存内容阅读、笔记、推荐和日报仍可工作 |
| A27 | 自动采集真实覆盖 | 每个平台逐源报告正常/待接入/认证失败/资源阻塞；不能仅演示一个源就宣称平台全部支持 |
| A28 | 旧系统切换 | 新旧同源不会同时采集；回退不会覆盖新笔记和正文 |

A26 只隔离非必要平台供应商后台，不阻断用户主动选择的外部内容来源；不是要求在完全断网时继续取得互联网新帖子。

## 17.2 用三个覆盖指标，而不是一个成功率

  **来源健康覆盖**  ：计划自动更新来源中，在各自要求窗口内成功检查的比例。待接入、认证失效和被错误暂停的来源应单独列出，不从项目总范围里消失。

  **已发现文章全文率**  ：已发现的适合文字阅读条目中，取得可读正文的比例。纯视频/音频单独统计，不能为了提高数字混分母。

  **抽样更新召回**  ：对实际作者页面进行人工抽样核对，计算真实新发布内容是否被系统发现。它能发现“Feed成功但列表漏条目”，不能由前两个指标推导。

上线报告给出分平台数据、样本数、时间窗口和失败原因。没有实测就留“未测”，不写猜测百分比。

## 17.3 基础上线与完整交付

基础平台可在核心链路通过后先投入使用，但发布说明必须列出每个平台未通过的条目。  **“可使用”与“原始要求全部完成”是两个不同状态。**

完整交付至少要求：既有可用来源迁移不回退；每个待接入来源有实际结果；用户指定平台仍有阻塞项时不能擅自宣布该平台完成。需要用户改变预算、授权或来源要求时，通过变更单记录，而不是在报告中改掉验收分母。

# 19. 风险、未验证事项与变更规则

## 19.1 风险台账

| 风险 | 已知依据 | 固定应对 |
|---|---|---|
| 登录态在ECS机房出口无效 | 简报明确为最大未知 | 用真实授权小样本验证；未通过不冒充自动更新 |
| 第三方Feed停止或延迟 | 现有公众号/X依赖说明 | 保留提供方信息、监控、备选同作者通道；不删除来源 |
| Feed窗口导致漏历史 | 已有目录仅给有限条目 | 记录窗口和疑似缺口，有合法能力才分页补抓 |
| 浏览器与2C2G冲突 | B站/小红书既有实测与资源未知 | 单并发、逐层压测、资源变更单，不自动删平台 |
| WeRSS授权或隐藏依赖 | 新采集模式未在目标账号验证 | 核查选定模式的完整调用链；关闭不必要代理/附属服务 |
| HTML解析不完整 | 单接口不能保证全部格式 | 真实样本验收、状态标记、原文入口 |
| 高亮随正文变更错位 | 正文版本与锚点关系 | 默认冻结阅读版，追加不自动重解析 |
| Bridge变成第二个大平台 | 多系统集成边界 | 仅做协议、索引、卡片、排序和任务；不改上游核心 |
| 2C2G不能运行完整栈 | 没有目标实例实测 | 先核心后适配；数据驱动申请变更，不伪造内存结论 |
| 通知不能在所有设备后台直达 | ntfy与系统推送机制不同 | 真实设备验收，说明依赖；持久事件不等于必然已读 |
| 备份只复制数据库不带附件 | 正文/批注/文件有关联 | 一致性备份＋恢复演练，不能仅检查压缩包生成 |
| 旧系统接口造成手机卡顿 | 现有4.9MB首屏响应 | 列表分页、正文按需、避免实时乱序 |

## 19.2 当前不应再问用户的产品问题

不再询问是否需要推荐、是否允许第三方逐作者Feed、是否刷新要检查上游、是否仅自己使用、是否部署ECS、是否要保留外链降级。这些已由对话确定。

需要实施时填入的是：完整来源清单、有效账号授权、域名/私有访问方式、备份目的地、实际通知接收端和版本摘要。它们不改变本文架构；不能因为尚未输入凭证就伪造测试结果。

## 19.3 需要单独审批的变更

仅以下事项需要重新决策：增加费用或ECS规格；把账号凭证交给第三方；新增常驻采集节点；开放公开访问/分享；让外部服务处理笔记或执行推荐；更换阅读/数据主栈。

普通来源增删、同作者Feed替换、缓存/轮询参数、主题权重、日报篇数、修复适配器、经过测试的版本升级属于运行配置或维护，不再次进行整套工具选型。

增加搜索、大模型摘要、OCR、音视频转录和复杂训练归入后续版本，不以隐性依赖方式塞进第一版。

## 19.4 备份、恢复与升级

第一版默认每日备份、保留最近7份日备份和4份周备份，至少一份加密副本位于ECS以外的受控设备。保留份数是初始运维参数，不构成可恢复保证。

一致性备份流程：暂停Bridge新任务和写入入口；等待在途写入完成；备份PostgreSQL；对Karakeep、Bridge、WeRSS和ntfy的SQLite采用其备份能力或停止写入后备份完整数据目录；同时保存附件、配置、权限和版本锁，再恢复服务。[S17—S18]

`pg_dump`可提供单库一致性快照，但跨多个应用的数据和附件不会自动形成同一时刻的全栈快照；暂停桥接写入与保留映射版本是本方案的协调措施。SQLite运行中随意复制单个`.db`文件可能遗漏未合并状态，不采用这种备份方式。[S17—S18]

恢复演练在空目录进行，核对条目数、来源关系、若干高亮原句、附件哈希及日报。版本升级前备份；若数据库迁移不向后兼容，回退需恢复升级前数据，不能只换回旧镜像。

# 20. 与个人主页和公开笔记站的关系

本平台只负责私人信息输入、阅读、批注、推荐和日报。个人主页负责身份与作品导航，公开笔记站负责经过用户选择的原创笔记和报告。

```text
外部更新 → 私人阅读平台 → 划线与个人思考
                              ↓ 用户明确选择
                         Markdown导出/整理
                              ↓ 用户明确发布
                         公开笔记站与个人主页
```

不自动公开整个订阅列表、阅读历史、第三方原文和批注。自己的公开笔记可以作为一个明确订阅源加入，但默认进入“我的发布”分组，不重新混入外部输入日报制造反馈循环。

第一版不做自动发布、跨站单点登录或双向笔记同步。导出是可审查、可撤回的边界，避免私人阅读资料意外变成公开网页。
