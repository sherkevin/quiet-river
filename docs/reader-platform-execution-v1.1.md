# Quiet River：v1.1 执行合同与分步任务

状态：用户于 2026-09-17 同意，按 W0–W5 增量执行；不是全部完成报告。
依据：会话附件《quiet-river_Gap评估与收敛实施方案_v1.1.md》。
本文件不覆盖该附件的历史采样；实时状态另写进工作日志和证据文件。

## 1. 不再变动的需求

- 用户选择关注对象；允许原生 RSS、自建采集与逐博主第三方转发。
- 打开/刷新列表发起真实检查；自动更新不依赖浏览器在线。
- 已取得内容先入库，本地算法只改变阅读优先级，不反向删除低分内容。
- 取得正文则站内阅读和高亮；只有元信息时允许打开具体原文并写整篇备注。
- 高亮、整篇备注、阅读版本、附件和映射可回看与恢复；不另建可编辑笔记主库。
- 日报在本机从订阅新增内容中选取，保留截点、版本、缺失来源与投递状态。
- 各目标平台继续在验收范围内；权限、资源和采集能力的缺口明确记录。
- 不新增付费服务、不自动升级 ECS、不向第三方交付登录凭证。

## 2. 技术与数据归属

Miniflux/PostgreSQL：文章条目、已取得正文和已读状态。
Karakeep：阅读版本、附件、高亮与备注。
Node Reader Bridge/SQLite：来源标签台账、映射、作业、偏好、排序和日报。
Caddy 与 ntfy：访问入口和通知传递；服务接受不等于手机已收到。
受限内容经 Bridge 主动导入 Miniflux；保持私网抓取总开关关闭。
不重选阅读器、不重写通用正文引擎、不修改上游应用数据库。

## 3. 执行纪律

每批顺序：核对实际状态 → 文档任务 → 回归测试 → 提交/推送 → 恢复点 → 指定提交发布 → 实测 → 日志。
只操作指定 ECS；不使用其他已连接设备，不输出环境文件或授权内容。
不覆盖脏工作区，不强推 main；部署失败恢复原版本，不把回退写成发布成功。
源码存在、单元测试、真实 API、真实来源、浏览器交互、长期稳定性分别记录。
root 用于安装、权限、恢复和服务管理；业务进程继续以专用用户运行。
外部访问失败不无限重试；手动刷新不绕过同宿主/凭证组冷却。

## 4. 工作包与验收门槛

| 工作包 | 交付 | 门槛 |
|---|---|---|
| W0 基线 | 发布清单、测试版本绑定、CI、调度归属、入口和恢复检查 | 干净提交可重现；线上文件可逐个验证；两套服务不重复采集 |
| W1 来源 | 完整来源对账与逐源接入状态 | 登记/启用/检查成功/全文各自计数；缺失来源不从分母删除 |
| W2 阅读 | 正文策略、归档作业、批注、整篇备注与导出 | 卡片到真实正文、划线、回看、导出及重启恢复；原有批注不被覆盖 |
| W3 更新 | 有界公平调度、增量同步、稳定分页、增量提示 | 慢源不堵其他宿主；重复刷新不重复抓；未变化的正文不伪造更新时间 |
| W4 推荐日报 | 本地偏好、候选截点、日报版本、投递 | 修改偏好只改变顺序；已投递日报可追溯；ntfy接受与设备收件分开 |
| W5 交付 | 全栈验收、负载记录、完整恢复、回滚 | 真实来源与交互通过；长期观察有真实时间跨度，不靠测试条数替代 |

W1 与 W2 可在 W0 后并行；W3 的数据正确性修复可先于扩大来源负载。
优先样板：一个已成功的博客、一个已成功的公众号，另加元信息降级夹具。
当前会话只报告实际完成的工作，不承诺离线后持续开发。
