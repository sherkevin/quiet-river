## 1. 目标与七项能力

一个**对内开放**的自用平台：没有其他用户，没有公共广场，展示的全部内容来自
自己关注的来源。

| # | 能力 | 现有 quiet-river 的状态 |
|---|---|---|
| 1 | 抓取不同平台的信息源 | **已建成**（271 源 / 13 类平台），但登录态通道当前失效（§5 问题 2） |
| 2 | 有自己的推荐算法，**只决定排序不决定可见性** | **刻意没有**（README：「时间倒序是唯一排序」） |
| 3 | 站内直接阅读全文，不跳转外部网站 | **刻意没有**（README：「不做全文抓取……要看全文点进原文」），且数据模型无正文字段 |
| 4 | 阅读时划线高亮、写笔记 | **没有** |
| 5 | 能回看自己的笔记 | **没有** |
| 6 | 灵活自定义信息源 | **已建成**（贴链接自动识别平台、找 feed、实际抓一次验证） |
| 7 | 日报推送 | **刻意没有**（README：「不做移动端推送」） |

> **这是产品定位的扩展，不是功能追加。**能力 2、3、7 现在都是 README 里明写的
> 「刻意不做的事」。评审任何方案时请把这个冲突当前提：新平台要么取代现有产品哲学，
> 要么与它并存（§5 问题 7）。

## 2. 当前立场（评审循环第 2 轮）

### 2.1 采纳外部方案的哪些部分

外部方案（RSSHub + We-MP-RSS + Miniflux + Karakeep + 自研 Bridge）经源码级核实，
**12 条技术断言 12 条成立**，含 3 条核到源码行级。采纳：

- **整体架构分层**：采集（RSSHub / We-MP-RSS）→ 订阅与正文保存（Miniflux）
  → 阅读与批注（Karakeep）→ 同步与排序（自研 Bridge）。数据归属三分、
  全部走 API 不碰别人的库，这个边界划得对。
- **加 Miniflux 这一层的理由成立**：已核实 Karakeep 的 RSS 解析器
  （`feedParser.ts`）只取 `id/link/guid/title/categories`，创建书签时只传
  `url/title/source`，**RSS 里已有的正文被丢弃**，随后自己去抓原站。
  对知乎/小红书/公众号这类有反爬的原站，这会导致「上游已拿到正文、
  阅读器却因二次抓取失败而丢正文」。
- **降级哲学**：全文 / 部分 / 元信息 / 失败四态显式建模；四类故障分别显示；
  **「更新失败不能显示为没有新文章」**。这条正好解我们当前的实际故障
  （128 个源静默失效 5 天没人发现，见简报 §7）。
- **已批注的正文冻结不覆盖**：已核实 Karakeep 高亮用**纯字符偏移**定位
  （`startOffset`/`endOffset`，无 DOM 路径、无锚点、无指纹），
  正文任何字符变化都会让高亮**静默错位**。冻结是这套数据模型下唯一正确的选择。
- **安全边界**：SSRF 防护（允许指定内部服务、禁止云元数据地址）、HTML 清洗、
  Basic Auth 与 Bearer 的冲突、Docker 端口映射绕过 UFW。这几条都识别到了。

### 2.3 本项目侧的自我纠错（第 1 轮评审的错误）

第 1 轮评审（`private-reader-platform-review.md` v1）有两处错误，已在 v2 纠正：

1. **把「条数更多」当成「资产更好」，漏了正文维度。**v1 认为我们现有的知乎适配器
   （20 条）优于 RSSHub（7 条）。实测两者请求参数：我们要 `include=data[*].excerpt`
   （摘要），RSSHub 要 `include=data[*].content`（**完整正文**）并做了图片清洗。
   **在「拿到可阅读正文」这个维度上 RSSHub 更优**，而正文正是能力 3 的核心。
2. **把「登录态资产」当成已建成的，而它当下停摆。**v1 说「115 个知乎源正在跑」，
   实测 115 个**全部报错**（109 个 401、6 个 403），单点健康检查也失败，
   按项目自己的判别法是**凭证真失效**，已失效约 5 天。

因此 v1 提的「第五条路」（保留 quiet-river 当抓取层、加 RSS 出口让 Miniflux 订阅）
**从「强烈建议」降级为「备选」**：出口只能吐摘要，Miniflux 拿不到正文就会回去抓原站，
**原样复现了外部方案给 Karakeep 挑出的那个毛病**。要走这条路，前提是先让适配器存正文，
而那是「给一个按摘要设计的产品加全文存档能力」，量级和 Bridge 相当。

### 2.4 三条候选路线的当前评估

**第 3 轮更新：路线已收敛到 A，且 A 现在有一份 1428 行的实施方案。**
外部评审人交付的 [`private-reader-platform-impl-v1.md`](private-reader-platform-impl-v1.md)
就是路线 A 的完整设计稿，并在 §16.4 **明确否掉了路线 C**
（「迁移不需要先给旧应用新写 RSS 出口」，理由是旧 XML 模块只有解析能力）。
这与本文 §2.3 的自我纠错结论一致。

| 路线 | 内容 | 当前评估 |
|---|---|---|
| **A** | RSSHub + We-MP-RSS + Miniflux + PostgreSQL + Karakeep（最小安装）+ 自研 Reader Bridge + Caddy + ntfy | **已选定，有完整实施方案**。我们的源码级评审判定「可以实施」，但**两处 P0 必须在 P1 开工前修掉**（见 §2.5） |
| **B** | 在 quiet-river 上自建阅读与批注层，从 NewsBlur 借数据形状与打分权重 | 不再考虑。实施方案 §16.4 把旧系统定为「过渡期只读历史与迁移对照」，不给它加推荐/全文/批注/账号 |

路线 B 的调研依据在 [`oss-reading-platforms.md`](oss-reading-platforms.md)：
NewsBlur（MIT，7620★）是唯一七项能力全中的开源项目，已把它的
`briefing/scoring.py`、`analyzer/models.py` 等五个文件拉到本地参考。
**但 NewsBlur 对中文平台没有知乎/小红书/公众号任何通道**，选它等于把
271 个源的清单重新接一遍，且依赖栈是 Postgres + Mongo + Redis + ES + Celery + Node 六件套。
这条调研仍然有价值——它解释了为什么我们不走「换一个现成开源阅读器」这条路。

### 2.5 实施方案 v1.0 的评审结论

> **本节是第 3 轮的结论，保留作历史。第 4 轮的状态见 §2.6：**
> 下面两条 P0 他都接受了；其中 P0-A 的解法他用一条我们没查到的入向路径改写了
> ——受限来源仍然进 Miniflux，但由 Bridge 主动推，不让 Miniflux 回拉（ADR 0016）。

完整评审见 [`private-reader-platform-impl-review.md`](private-reader-platform-impl-review.md)。
**总判断：方案可行，证据纪律是真的**（他给的三个 blob SHA 里两个与我们独立核对
逐字符相同，第三个指向 main 分支而非锁定版本，我们替他做了对照，差异无害），
**但有两处按方案照抄部署就会失败**：

| 编号 | 问题 | 为什么是阻塞 |
|---|---|---|
| **P0-A** | §5.4 要让 Miniflux 读 Bridge 的**内网**缓存地址，但 Miniflux 默认在 dial 阶段拒绝一切非公网 IP（`request_builder.go:184-199` + `IsNonPublicIP`），Docker 网段与 loopback 全在内。唯一的原生开关 `FETCHER_ALLOW_PRIVATE_NETWORKS` 是**全有全无**的布尔值（上游没有主机白名单），而打开它会把**阿里云元数据地址 `100.100.100.200` 一起放进来**——该地址落在 RFC 6598 段内，Miniflux 专门加了判定去拦它 | 第一个受限来源（知乎/小红书）就会失败；或者为了修它而拆掉一道专门针对云元数据的 SSRF 防护。他 §15.3 想要的「只允许指定内部服务、屏蔽云元数据」Miniflux 原生**做不到** |
| **P0-B** | §4.4 要求 WeRSS 开 `gather.content: true` 采公众号正文，实测调用链是 `web.py:112 → content_extract → driver/wxarticle.py:14,29` 直接实例化 `PlaywrightController`，配置里还有 `browser_type: firefox`。**WeRSS 采正文也要起浏览器**，但他 §12.2 的「浏览器采集」层只写了 RSSHub，§12.3 的 `browser_concurrency: 1` 语境也是 RSSHub | 2C2G 的资源模型里只算了一份浏览器开销，实际可能两份（Chromium + Firefox，运行时和内存峰值都不同）。§12.4 的 72 小时验收如果只压 RSSHub，会在启用 WeRSS 时才发现装不下——那时 P2 已做完 |

另有四条非阻塞修正：Miniflux **自带**每源全文提取（readability + goquery
`scraper_rules` + `fetch-content` 端点）方案完全没提，约 40 个博客类源可能白拿（P1-A）；
§6.5 的 `append-recrawl` 结论**对得偶然**，靠「先 attach 再 recrawl」的执行顺序保证，
方案没写成不变量（P1-B）；§21.7 的 curl 示例会在契约测试里直接 403，singlefile 需要
`assets:readwrite` + `bookmarks:readwrite` 两个 scope（P1-C）；
机房 IP 登录态实测排在 P2，但它失败会改变 P2~P5 的形状，应前移（P1-D）。

**他也纠正了我们一处**：简报 §4 把「手动登记的公众号」写成 18，实际是 17。
已核实并修正。他处理得很对——没擅自选一个数字，而是标记差异要求逐条对账。

**两条我们上一轮的判断被他证实**：Karakeep 的 `feedParser.ts` 丢弃 RSS 正文
（这是他保留 Miniflux 的核心理由），以及高亮是纯字符偏移所以要冻结正文。
**一条被他推翻**：我们上一轮建议用两步式导入（`POST /assets` → `precrawledArchiveId`）
而不是 singlefile 端点，理由是后者不在 OpenAPI spec 里。本轮核实两条路**都通**
（两步式的两步都在 spec 里；singlefile 在 v0.33.2 实现里存在且有 e2e 测试覆盖），
singlefile 更省事但不在 spec 契约内、且需要两个 scope。**这个选择留给实施阶段**，
不影响架构。

### 2.6 第 4 轮：他接受了阻塞，但推翻了 0014 的双库结论

他的完整回复在 [`private-reader-platform-reply-r3.md`](private-reader-platform-reply-r3.md)。
一句话概括这一轮发生了什么：**我们提的两条 P0 阻塞他全接受了，但他不接受我们
为 P0-A 开出的药方。** 他找到了 Miniflux 的另一条路径，我们把源码核了一遍，
他是对的，我们上一轮的推理漏了一步。ADR 0014 因此被 0016 取代。

**P0-A 的新解法：把调用方向反过来。**

我们第 3 轮查的是「Miniflux 能不能去拉 Bridge 的内网地址」——答案是不能，
抓取器在建连前检查 IP，私网一律拒绝（这条约束本身真实，0016 继承）。
他查的是另一个方向：**外部能不能把条目推进 Miniflux**。答案是可以：

```http
POST /v1/feeds/{feedID}/entries/import
```

我们核实了这条路径，它是纯数据库写入，完全不碰抓取器：
端点注册在 `internal/api/api.go:55`，handler 在 `entry_handlers.go:354`，
落库走 `storage/entry.go:252` 的 `InsertEntryForFeed`，整个函数只有
事务开始 / 查重 / 写入 / 提交，没有任何 fetcher、scraper 或网络调用。
正文在 handler 内就地清洗，不经过抓取链路。
**所以私网拦截在这条路上根本不参与判断。**

于是架构变成：

```text
普通来源：Miniflux 主动拉公网 Feed → Miniflux 入库
受限来源：Bridge 调度采集 → Bridge 调导入接口推 → Miniflux 入库
```

全库回到**单一文章主库**，实施方案 §10.1 的数据归属表不用改，
我们也不必承担双库的分页、去重、已读双写、日报候选集合并那一堆成本。
`FETCHER_ALLOW_PRIVATE_NETWORKS` 保持关闭（0014 的安全决定原样继承），
受限来源的记录用 OPML 导入创建并带 `miniflux:disabled="true"`，
让 Miniflux 的调度器不去轮询它们。

**核这条路径时又挖出四条他没写、实施时会咬人的细节**，已一并写进 0016：

| 发现 | 后果 |
|---|---|
| 导入不传 `status` 时默认 `read`（`entry_handlers.go:384-386`） | 首次导入忘了显式传 `unread`，文章直接以已读入库，在未读视图里永远看不到，日报候选集整批消失且不报错 |
| 重复导入不改正文，但**无条件重写已读状态**（落库后 `:446` 调 `SetEntriesStatus`，该函数是裸 `UPDATE`） | 拿重新导入当「补正文」无效；若重试统一带 `unread`，用户读过的文章会被反复重置为未读 |
| 补正文要走 `PUT /v1/entries/{entryID}`，它只改标题和正文、**不碰状态**，且成功返回 **201 不是 200** | 「先有摘要后补全文」正好用它；契约测试别按 200 断言 |
| 屏蔽/保留规则只在抓取路径生效，导入路径**完全不应用**（`processor.go:75,147` vs 导入 handler 零调用） | 同一套规则对普通源生效、对受限源不生效，排查极难。**第一版干脆不配任何过滤规则** |

**P0-B 他接受得更彻底，还比我们精确。** 他确认 WeRSS 采正文必须起浏览器，
资源表漏计成立，并加了一条我们没说对的修正：**不能咬定是 Firefox**。
配置样例里写 `browser_type: firefox`，但他指出运行代码的默认值不是它。
我们复核后比他更进一步——`gather.browser_type` 这个配置项在内容采集链路上
**根本没被读过**（只有 PDF 导出路径 `tools/mdtools/export.py:90`、
`core/exporter.py:67` 用它），正文采集走 `driver/wxarticle.py:29,81` 直接
实例化无参 `PlaywrightController()`，用的是代码默认 `webkit`
（`driver/playwright_driver.py:54`），可被 `BROWSER_TYPE` 环境变量或本地 Chrome
自动发现覆盖。**结论：磁盘上装几套浏览器和运行时实际起哪套，要分开测。**

**他还白送了两件事**：一是确认 Karakeep v0.33.2 的 `GET /highlights` 可用，
「我的笔记」从不确定项变成有正式 API 支撑（与我们第 3 轮的 P1-C 修改要求 8 一致，
他独立核到了同一结论）；二是发现 WeRSS 的 `main.py` 在 `__main__` 下
无条件遍历打印所有环境变量（`main.py:18-21`），若用环境变量注入凭证，
启动日志会写进凭证。我们核实属实，这条要进 P0 的安全清单。

**这一轮的方法论教训也记进了 0016**：0014 的错不在查得不细，
而在把「A 路径不通」直接当成「目标不可达」。网络限制通常是不对称的——
出向严、入向松很常见。看到「出向被拦」，下一句应该先问「那入向呢」。

## 3. 阻塞项（必须先解决，与架构选型无关）

### B1 凭证健康检查与失效告警

**现状（第 4 轮实测更新）**：253 个缓存键里 146 个带 error，无人发现。
细分是**知乎 109 个报 401（从 9-15 起，一天多）、小红书 13 个的错误是 9-13 的陈旧记录
（凭证实测仍活着）**，其余 24 个是 fetch failed / 超时 / 限流等杂项。
第 2 轮写的「128 个源全部失效 5 天」不准确，失效面比估的小，但知乎这一半是真死的。

**要做**：定时打单点端点（知乎 `/api/v4/me`，小红书 CLI 的 `whoami`），
失败即告警。判别法沿用项目既有约定：**批量失败可能是限流，单点也失败才是真失效**。

**第 4 轮：这条判别法本身被实测抓出一个 bug。**
我们唯一的凭证自检工具原本只对 403 做分类，401 落进兜底分支被报成
「网络或风控页，稍后重试」。这是错的，而且错的方向危险：
**403 等一会儿可能自己好，401 等多久都不会好**。
把一个必须重贴的故障说成可以等，和「静默失效没人发现」是同一类错误。已修。
知乎适配器的错误文案同样只写「知乎返回 HTTP 401」，109 个源的问题栏里看不出要重贴凭证，也补了。

**更要紧的是 B1 的状态要改**：第 3 轮写「设计已定，可直接采用」，
实测发现**目前只有一个手工 CLI，没有调度、没有告警、没有凭证组概念，
而且这个 CLI 的分类逻辑是错的**。「设计已定」不等于「已落地」，
B1 的工作量要按从零实现估。

**第 3 轮更新：这件事现在有现成设计，不必我们自己想。**
实施方案 §14 整章是我们收到的七个回答里质量最高的一章，直接采用：

- **以「凭证组」而非「来源数」作为认证故障单位**。「共享一组登录态的 115 个知乎来源，
  发生明确认证失效时只做必要确认，暂停关联组，发送一条聚合告警，
  不继续用其余来源重复验证到封禁」——这条直接解我们当前的故障形态
  （115 个源各自报错，等于拿同一个失效凭证打了 115 次）。
- 本地运行状态每 15 分钟检查一次（**只查队列和时间戳，不额外请求平台**）；
  认证健康优先复用正常采集结果，长期无可用结果时才做低频受控验证。
- 八类错误的分类与恢复表（§14.2），其中「403 不直接等同 Cookie 过期」
  与项目既有约定一致。
- **§14.3「没有新文章与没有检查成功必须分开」**：依据 `last_success_at` 和计划周期
  判断健康，不根据最近文章发布时间判断。作者停更不等于爬虫失败。
  这条正是我们 5 天没人发现故障的根因。
- 告警不含 Cookie、完整 token、签名请求或授权二维码。

**这件事独立于 P0-A/P0-B，可以现在就做，不必等外部评审人回复。**
第 4 轮已经动了一部分（修分类与文案），但**凭证组、`last_success_at` 健康判定、
聚合告警这三件核心的都还没做**。

**为什么排在第一**：新架构如果仍押在单一登录态凭证上，同样会静默失效。
这件事独立于任何架构选型，且是验收标准里「授权失效能发现，不静默漏文章」的前提。

### B2 重贴凭证，恢复现有抓取

**第 4 轮实测：知乎凭证已经死了，小红书还活着。**
这是第一批跑出来的数据，详见 [`p0-measurements.md`](p0-measurements.md)。

知乎单点端点返回 **401 `ERR_TICKET_NOT_EXIST`**，连跑两次一致，
所以不是限流（限流是 403，等一会儿会好）。缓存里 **109 个源从 9-15 起就在报 401**，
已经持续一天多。

**`d_c0` 缺失已实测确认**：现有 cookie 文件里**只有 `z_c0` 一个字段**。
RSSHub 的知乎路由需要 `d_c0`（设备标识），只贴 `z_c0` 大概率仍被风控挡。
所以 B2 不是「重贴一次」，是「换一种取法重贴，且必须包含 `d_c0`」。

小红书 `whoami` 返回 logged_in，**会话是活的**。缓存里那 13 条错误的时间戳是
9-13，比会话状态旧——**是数据陈旧，不是凭证失效**。
这修正了第 2 轮「128 个登录态源全部失效」的判断：
实际是**知乎 109 个真失效、小红书 13 个凭证活着但 3 天没刷**。

**注意**：按项目既有约定，频繁重登会作废旧 cookie，别轻易动；
读到 403 先退避一两分钟再判断。**401 不用等，它不会自己好。**

### B3 机房 IP 上登录态是否可用（最大未知数）

ADR 0013 的结论是「登录态源在机房 IP 上更容易触发平台风控，所以它们**不上服务器**，
停在快照时刻」。所有实测数据都来自家庭宽带。

**如果这条结论依然成立**，那么新平台上的知乎与小红书也只能是快照，
和现在的 ECS 部署形态一样——**这会直接改变路线 A 的价值**
（它最大的收益就是让这两个平台在服务器上活起来）。

必须实测，不能假设「换了架构就能在机房跑登录态」。见 §4 阶段 0。

**第 4 轮：这条的优先级因为 B2 的实测结果变高了。**
如果机房 IP 上登录态本来就不可用，那「重贴知乎凭证」在 ECS 上是白做的——
重贴只能在 Mac 上做，服务器照样停在快照。**所以 B3 应该排在 B2 之前**：
先确认机房 IP 能不能用登录态，再决定要不要费那个劲重贴。

测法已明确（见 `p0-measurements.md` §7）：在 ECS 上装好那个小红书 CLI
（npm 公开包，Apache-2.0，v1.8.7），登录后打一次小红书 `whoami` 与
知乎 `/api/v4/me`，与本机结果对比。

**第 3 轮更新：影响范围比上一轮估计的更大。** 实施方案把它列为风险台账第一条
（§19.1「登录态在 ECS 机房出口无效」），应对写的是「用真实授权小样本验证；
未通过不冒充自动更新」——判断正确。但 §18 的阶段表把它排在 **P2**，
P0 是资产与版本、P1 是阅读核心。问题是知乎 115 + 小红书 13 = **128 源，占 47%**：

- 若不可用，§5.4 的内网缓存设计（P0-A）**必要性大幅下降**——没有实时采集就不需要缓存中转
- §12.2 的浏览器层可能整个不启用，2C2G 的压力判断随之改变
- §8 排序候选集里近一半来源没有新增内容，日报的「今日新增」会长期偏少
- A27「自动采集真实覆盖」的验收分母要重新定义

**所以我们要求把它前移到 P0/P0.5**（见 §5 修改要求 4）。这不是新增工作，只是换顺序，
而它决定后面四个阶段的范围。

**第 4 轮补充：B3 应该排在 B2 之前。**
如果机房 IP 上登录态本来就不可用，那「重贴知乎凭证」在 ECS 上是白做的——
重贴只能在 Mac 上做，服务器照样停在快照。先确认机房能不能用，再决定要不要费劲重贴。

### B4 部署前提实测（第 4 轮新增，方案里完全没有）

实施方案 §13 写「采用现有 Ubuntu 24.04、Docker Engine 与 Compose 插件」，
把容器运行时当成既有条件。**实测是零**，详见 `p0-measurements.md` §2、§3。

| 实测项 | 结果 | 影响 |
|---|---|---|
| 容器运行时 | **docker / podman / compose 全都没装** | §12.2 六个常驻服务一个都起不来。P0 的第一项工作应该是装 Docker，方案没给它排位置 |
| 数据库与反代 | postgres / caddy / redis-server 都没有 | 同上 |
| 内存 | **total 1740MiB / available 1201MiB**（标称 2GB，内核与云监控 agent 吃掉约 300MB）；现有 node 服务已占 175MB | 全文以「2C2G」为基线，但**可用比标称少约 300MB**。§12.4 的「保留 250MiB 以上」目标在这个基线上很紧 |
| swap | **没有** | §12.4 写「Swap 可以用于应急缓冲」，这条缓冲现在不存在。要么先建 swap，要么把验收目标改成「无 swap 下不 OOM」 |
| 出网 | **Docker Hub 直连不通**（`registry-1.docker.io` → 000）；`ghcr.io` 可达；apt 走阿里云内网镜像可达 | **PostgreSQL 官方镜像只在 Docker Hub**，而它是 Miniflux 与 Karakeep 的共同硬依赖。这条不解决，部署第一步就停 |
| 镜像加速器 | 实测 5 个加速器活着，其中一个走完整认证流程后**取到 `library/postgres:17-alpine` 的 manifest（200）** | M4 有解：配 `/etc/docker/daemon.json` 的 `registry-mirors`。**但加速器是第三方服务**，§12.2「必须固定镜像、不用未核实的社区实例」这条原则对它同样适用——**要按 digest 固定并核对与官方一致**，加速器返回 200 不等于返回的是官方镜像 |

**这一批数据足以支撑提 §12.4 预留的那张「内存提升至 4GiB」变更单。**
建议在装任何服务之前先提，别等 OOM 了再提。同时先做一次空载基线，
再按 §12.4 的顺序逐层启用并记录，不要一次装完再看。

### B5 历史 7474 条要不要补正文（第 4 轮新增，需要产品决策）

实测条目字段只有 `guid / title / link / author / published / summary / image`，
**没有正文字段**，`summary` 是截断过的摘要。全库 7474 条无一条有正文
（与第 2 轮发现一致），占缓存 5.7MB。

对迁移的影响方案没算：历史条目导入 Miniflux 后**只有摘要**，
按 §6 的五态模型**大概率全部落在 `META` 态**。技术上可以用 ADR 0016 的
`PUT /v1/entries/{id}` 逐条补，但那是 **7474 次带登录态的抓取**，
而原文可能已删、知乎凭证当前还是失效的（B2）。

**倾向不补**：历史条目的价值已经被三个月人工筛选沉淀在 tag 与清单里，
补全文的边际收益低。**但这是产品决定不是技术决定，要显式定下来落 ADR**，
不要默认。这条排在 §7 的 0022 槽位。

## 4. 阶段计划（gate 制，每个 gate 不过就停）

**第 3 轮重写。** 第 2 轮我们自己排的顺序是「凭证健康 → 全文实测 → 清单迁移 →
阅读批注 → 排序日报」。实施方案 v1.0 §18 给出的是 P0~P5 六个阶段
（资产与版本 → 阅读核心 → 来源与更新 → 内容与笔记 → 推荐与日报 → 全量切换），
**两者基本一致**，采纳他的编号，只提一处顺序调整：

| 他的阶段 | 我们的调整 |
|---|---|
| P0 资产与版本 | **加进 B1/B2/B3/B4**（凭证健康检查、重贴凭证、机房 IP 实测、部署前提）。他把登录态实测排在 P2，但 128 源占 47%，失败会改变 P2~P5 的形状（见 §3 B3）。也加进 WeRSS 的浏览器实测（P0-B）。**第 4 轮：顺序要改——B4（装 Docker + 配加速器）排第一，B3 排 B2 前**（机房不可用的话重贴是白做） |
| P1 阅读核心 | **加一条前置**：先用 Miniflux 原生 readability/`scraper_rules` 测约 40 个博客类源，再决定 Bridge 要不要自写抓取（P1-A）。可能省下一大块开发量 |
| P2~P5 | 照他的。**P0-A 第 4 轮已定案**（ADR 0016：受限来源由 Bridge 主动推给 Miniflux，单库不分家），P2 开工前不必再等这一项 |

### P0：资产、凭证与风控实测（gate）

- **B4（第 4 轮新增，排第一）**：ECS 上装 Docker Engine + Compose 插件（走阿里云内网 apt 镜像，实测可达），
  配 `/etc/docker/daemon.json` 的 `registry-mirrors`（Docker Hub 直连实测不通，
  PostgreSQL 镜像只能靠加速器；加速器实测可用，但要**按 digest 固定并核对官方一致**）。
  顺带定 swap：实测无 swap，要么建，要么把 §12.4 验收改成「无 swap 下不 OOM」。
  **这一步不通，后面所有服务都起不来**，所以它排在凭证工作之前
- **B3（提到 B2 之前）**：在 ECS 上实测机房 IP 的登录态可用性（最大未知数）。
  装好那个小红书 CLI（npm 公开包 v1.8.7，Apache-2.0），登录后打小红书 `whoami`
  与知乎 `/api/v4/me`，与本机结果对比。**机房不可用的话，B2 的重贴在服务器上是白做的**
- **B2**：重贴凭证。知乎已实测失效（401 `ERR_TICKET_NOT_EXIST`，不是限流），
  且现有 cookie **只有 `z_c0` 没有 `d_c0`**，要换一种取法重贴
- **B1**：凭证健康检查。第 4 轮已修了自检工具把 401 误报成「稍后重试」的 bug，
  但**凭证组、`last_success_at` 判定、聚合告警这三件核心的还没做**，按从零实现估
- 从真实 `data/subscriptions.json` 生成 `source-manifest.json`。
  他 §2.4 明确说了他没有这份数据、不会编造，**这步只能我们自己出**
- 在**本机**起 RSSHub，用真实凭证 + 真实博主实测三件事：
  1. 知乎路由能否拿到**完整正文**（含图片清洗效果）
  2. 小红书路由在有 cookie 时能否拿到**正确的笔记链接与全文**
     （`renderNotesFulltext` 是逐条二次请求，要测延迟与限流）
  3. 13 个小红书源连续请求的**浏览器开销实测**（内存峰值、单次耗时、503 概率）
- **新增（P0-B）**：WeRSS `model: web` + `content: true` 采 3 篇真实公众号文章，
  记录**冷启动内存、单篇耗时、并发 1 时的 CPU 占用**。
  实测调用链 `web.py:112 → content_extract → driver/wxarticle.py:14,29`
  会实例化 `PlaywrightController`。
  **第 4 轮修正：起哪套浏览器要实测确认，不要照配置样例写 Firefox。**
  `gather.browser_type` 这个配置项在内容采集链路上**根本没被读**（只有 PDF 导出
  `tools/mdtools/export.py:90`、`core/exporter.py:67` 用它）；正文采集走
  `driver/wxarticle.py:29,81` 实例化无参 `PlaywrightController()`，用代码默认
  `webkit`（`driver/playwright_driver.py:54`），可被 `BROWSER_TYPE` 环境变量或
  本地 Chrome 自动发现覆盖。所以**磁盘上装几套**与**运行时起哪套**要分开测，
  并以实际启动日志为准。
- **新增（P0-B）**：先证明能调用「单个公众号更新」并拿到正文，
  再把 `content_auto_check` 设为 false。否则 17 个公众号会**静默无正文**
  （`main.py:72` 的自动补抓任务由 `content_auto_check` 把门，关掉后正文只能由
  `get_Articles` 触发，而那需要一个尚未验证的单账号入口）
  **第 4 轮：这个入口他查到了**，是 `GET /api/v1/wx/mps/update/{mp_id}?start_page=0&end_page=1`
  （路由 `apis/mps.py:342`，前缀 `/mps` 在 `:22`，总前缀 `API_BASE=/api/v1/wx` 在
  `core/base.py:16`）。**注意它是有副作用的 GET**：只能由 Bridge 后端调用，
  不能让浏览器预取，不能被反向代理缓存。且「返回 200」不等于「正文补上了」——
  底层错误会被吞掉返回空内容，验收要一直查到「需要正文的条目是否完成提取」
  与「失败项是否进入可见可重试状态」，并专测「首次正文失败、下次触发能否补齐」。
- **新增（P0，第 4 轮）**：接入真实凭证前，处理 WeRSS `main.py:18-21` 在 `__main__`
  下**无条件遍历打印所有环境变量**的问题（没有 debug 开关保护）。若用环境变量注入
  Cookie/密钥/数据库口令，启动日志会写进凭证。删掉这段全量输出或改成非敏感白名单，
  并用假密钥做一次启动测试，确认日志里不含它们。这个很小的安全补丁可以接受——
  「尽量不改上游」是降维护成本的原则，不是明知会漏凭证仍照原样部署的理由。
- **新增（P0，第 4 轮）**：在**锁定版本**上做导入接口的契约验收（不在 main 上做）：
  创建来源（OPML 带 `miniflux:disabled="true"`）→ 首次导入（**必须显式传
  `status:"unread"`**）→ 查询 → 重复导入（确认正文不变、但已读状态会被刷）→
  用 `PUT /v1/entries/{id}` 补正文（确认**不动已读状态**，且断言返回 **201**）→
  重启恢复 → 抓包确认 Miniflux 对受限来源原站域名**零出向请求**。详见 ADR 0016。
- 在 **ECS** 上重复 RSSHub 的 1、2，回答 B3

**Gate 判据**：知乎与小红书至少一个能在机房 IP 上稳定拿到正文。
若都不行 → 受限来源就没有实时采集，Bridge 的导入与采集调度大幅简化（ADR 0016 的
架构不变，但驱动它的实时数据流没了），§12.2 浏览器层可能整个不启用，
A27 的验收分母要重新定义。**不是推翻路线 A，但 P2~P5 的范围会显著缩小。**
