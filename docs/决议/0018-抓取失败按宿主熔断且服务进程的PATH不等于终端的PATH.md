# 0018 抓取失败按宿主熔断，且服务进程的 PATH 不等于终端的 PATH

状态：Accepted（2026-09-17）

## 背景

用户报「一次刷新太久」。实测把问题定位到两处，都不是「网络慢」，而是代码在明知会失败的地方继续花时间。

### 一、15.2 分钟纯等待，换来 115 个 401

`lib/refresh.js` 里同宿主的最小请求间隔（`HOST_MIN_GAP_MS`）是必要的：知乎 2026-09-11 实测约 17 次请求 / 15 秒就 403，8 秒这个值不能动。问题在 sleep 的位置——它在请求之前无条件执行，不看上一个请求的结果：

```js
const gap = HOST_MIN_GAP_MS[entry.host] || 0;
if (gap) {
  const wait = (lastRequestAt.get(entry.host) || 0) + gap - Date.now();
  if (wait > 0) await sleep(wait);
}
```

知乎返回 401 只要几十毫秒，但下一个源照样先睡满 8 秒。按真实订阅清单算墙钟时间：

| 宿主 | 源数 | 间隔 | 纯 sleep |
|---|---|---|---|
| `adapter:zhihu` | 115 | 8000ms | **912 秒 = 15.2 分钟** |
| `wechat2rss.bestblogs.dev` | 40 | 1000ms | 39 秒 |
| `api.xgo.ing` | 26 | 1500ms | 38 秒 |
| 其余 41 个宿主 | 69 | 0 | 0 |

`adapter:zhihu` 的 115 个源属于**同一个宿主队列**，而队列由单个 worker 独占（同域串行是刻意的，见代码注释），所以并发度对它毫无帮助。手动点「刷新」传 `force=true`，它会忽略 `failCount >= 3` 的跳过规则，于是**最痛的场景恰好是最慢的**：15.2 分钟等待，结果是 115 个已知的 401。

### 二、13 个小红书源坏了 4 天，报错指向错误方向

缓存里这 13 个源的 error 停在 9-13 15:02，之后一次都没重试（`failCount` 到 3 就被非 force 刷新永久跳过）。但手动直连测底层命令，3 秒返回 20 条笔记，`opencli xiaohongshu whoami` 也是 `logged_in: true`。登录态一直是好的。

真凶是 PATH。launchd 给服务进程的 PATH 实测是：

```
PATH=/usr/bin:/bin:/usr/sbin:/sbin
```

不含 `/opt/homebrew/bin`，而 `opencli` 在那里。用这个 PATH 复现：

```
err.code = ENOENT
err.message = spawn opencli ENOENT
```

而错误消息说的是「opencli 调用失败：先跑 `opencli xiaohongshu login` 完成登录」。旧代码把 `err` 整个丢掉，无论什么原因失败都报这一句，于是排查方向被引向凭证。这和 ADR 0015 记的 `check-credentials.js` 把 401 误报成「稍后重试」是同一个形状：**兜底文案覆盖了真实原因**。

还有第二层：`opencli` 本身是个 node 脚本（shebang 是 `#!/usr/bin/env node`）。就算用绝对路径找到了它，它内部还要靠 PATH 找 node，于是报 `env: node: No such file or directory`。

## 决策

### 一、按宿主熔断，判据是「错误完全相同」而不是「连续失败」

同一宿主连续 5 次报**逐字符相同**的错误，就认定本轮不必再试剩下的源，直接标记同一个错误、不发请求、不 sleep。

判据为什么必须是「错误相同」：网络抖动每个源报的不一样（超时、DNS、502 混着来），那种情况下熔断会误伤；凭证失效或平台封禁才会 115 个源一字不差地报同一句。这条界线在测试里有用例钉住（`test/refresh-circuit.test.js` 的「错误各不相同就不熔断」）。

被熔断跳过的源**不写缓存**：`failCount` 不涨，`fetchedAt` 不动，上次抓到的条目原样留着。它们没被试过，不该被记为失败。

成功一次就清零连击，所以恢复是自动的，不需要人工干预。

`refreshAll` 的返回值新增 `circuit` 字段，说明哪个宿主熔断了、跳过了几个、错误是什么。前端可以据此说清「为什么这 110 个知乎源没试」，而不是让人以为刷新成功了却少了一大片内容。

### 二、并发度 4 → 8

43 个活跃宿主，`CONCURRENCY` 是同时处理几个宿主队列。4 太保守：实测 4 个不同宿主并发总耗时 3283ms，单个 arxiv 请求就要 5372ms，说明并发没有成为瓶颈。同域串行的约束不受影响，它靠的是宿主队列独占，不是靠全局并发数。

### 三、外部 CLI 用绝对路径解析，并给子进程补 PATH

`resolveBin()` 按候选位置找一个真实可执行的文件，支持 `QR_OPENCLI_BIN` 显式覆盖。`childEnv()` 把 `path.dirname(process.execPath)`（当前正在跑的 node 的目录）补进子进程的 PATH，解决第二层问题。

### 四、错误消息必须带真实原因

`ENOENT` 单独报，并且把当时的 PATH 一起打出来。其余错误带上 `err.stderr`。不再有任何兜底文案替真实原因说话。

### 五、`failCount` 从「永久跳过」改为指数退避

熔断解决了效率，但它带来一个新问题：**现在「快」的一部分原因是永久放弃了坏源**。小红书就是这么静默坏了 4 天——`failCount >= 3` 之后非 force 刷新直接 `return false`，再也没有任何自动机会。效率不能是用「河会悄悄变陈旧」换来的，所以这条一起改：

| failCount | 退避 |
|---|---|
| ≤ 2 | 不退避（归 `HOST_MIN_RECHECK_MS` 管） |
| 3 | 6 小时 |
| 4 | 12 小时 |
| 5 | 24 小时 |
| 6 | 48 小时 |
| ≥ 7 | 72 小时封顶 |

到阈值就开始退避，不白试那一次：同一个宿主上一轮刚连坏三次，下一轮立刻再试一遍多半还是同样的错误。成功一次 `mergeIntoCache` 就把 `failCount` 归零，立刻恢复正常节奏。`backoffMs()` 导出以便测试直接核对退避表。

**两个机制的交互要说清楚**：退避按源算、用 `fetchedAt` 判断到期，而被熔断跳过的源**故意不写缓存**、`fetchedAt` 停在旧值。于是那批源的退避在它们被真正试过之前不生效，每轮刷新还是会轮到队列最前面的几个。这个行为是自愈的，而且方向是对的：每轮试 5 个左右，它们的 `failCount` 涨上去、退避拉长，下一轮就轮到别的源。约一天之内 115 个知乎源会被逐个试到一次并全部进入各自的退避档位，之后请求量从「每小时 115 次」降到「按档位摊薄的几次」。收敛前每小时约 5~12 次知乎请求，每次间隔 8 秒——这正好符合 ADR 0015 的要求：不要拿一份失效凭证反复敲平台的门。

**错误消息会交替，所以实测试的源数比 5 略多**：知乎同时返回 401（凭证失效）和 403（限流）两种消息，连击计数遇到不同消息就清零，实测一轮试了 12 个。这是判据「错误必须逐字符相同」的正确后果，不是 bug：403 确实可能等一会儿自己好，不该和 401 一起被熔断掉。

## 实测结果

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 强制刷新 250 个源的墙钟时间 | 15 分钟以上（知乎队列独占） | **59 秒** |
| 第二次刷新（多数源还新鲜） | 同上量级 | **36 秒** |
| 每小时自动刷新（非 force，退避生效后） | 同上量级 | **42 秒** |
| 小红书 13 个源 | 全错，停在 9-13 | **全活，最新笔记 9-16** |
| 全局出错 feed 数 | 147 | 121（剩下 115 个是知乎凭证真失效） |
| 测试数 | 66 | **73**（新增 7 个熔断与退避用例） |

熔断在真实知乎数据上生效了，返回值是 `{"host":"adapter:zhihu","skipped":109}`，即 115 个源只发了 5 个请求。

退避的实测落点（当前缓存状态）：103 个知乎源 `failCount=3`（错误消息还是修复前那条旧的「知乎返回 HTTP 401」，`fetchedAt` 停在 9-15）、7 个 =4、5 个 =5；另有 3 个源 =5、2 个 =6、1 个 =7。小红书 13 个源与其余 119 个源都是 `failCount=0`。

## 后果

**好的**：手动刷新从「十几分钟且必然失败」变成「一分钟内且能看清哪一类源坏了」。小红书恢复。错误消息可以直接指导排查，不再需要先怀疑一遍凭证。

**要注意的**：熔断会让「平台在某个时刻短暂全面封禁」的情况下，本轮剩下的源不被重试。但下一轮刷新会重新开始，连击计数每轮重建，所以最坏情况是晚一个刷新周期发现恢复。这个代价对自用平台可以接受。

**ECS 侧的连带效果**：ECS 上没有 `adapters.private.js`，那 128 个源每轮都报「未知适配器」。这也是逐字符相同的错误，所以熔断同样生效，ECS 不再每轮白试 128 次。

**部署拓扑的问题被这次排查暴露出来**：Mac 与 ECS 各有一份 `data/cache.json`，各跑每小时定时器，互不同步。`wechat2rss.bestblogs.dev` 40 个源、`api.xgo.ing` 26 个、博客类 41 个宿主，两边各抓一遍，对第三方是双倍压力。而 ECS 因为缺适配器，128 个登录态源永远停在 seed 快照。手机通过 Pages + FC 中继看到的是 ECS 那份，所以**手机上的知乎小红书内容是陈旧的**。这需要单独决策：要么把登录态抓取收在 Mac、ECS 只做静态出口，要么想办法把凭证与适配器搬到 ECS（但要先过 B3 机房 IP 风控实测）。
