# 0017 评审文档与决议目录全部发布，只留本机操作手册不发

状态：Accepted（2026-09-17）
关联：扩展 [0009](0009-订阅清单从绝不发布翻转为默认发布.md)

## 背景

用户要求「都放在 github 上」。当时 `tools/publish.sh` 的 ALLOW 白名单里只有 4 份文档
（部署一致性、私有适配器指南、现状汇报、公众号），而 `docs/` 下实际有 15 份，
外加 `docs/决议/` 16 份 ADR 全部排除在外。

排除的理由散在三处，写于不同时间，**没有一处是经过复核的**：

1. 决议目录 README：「决议里有具体博主的昵称与内容构成，那是本机阅读清单的一部分，
   和 `data/subscriptions.json` 同级处理（后者在 NEVER 名单里）」
2. `private-reader-platform-review.md` 顶部横幅：「本文提到凭证文件名、
   本机私有 CLI 名，与 scan-leaks.js 同性质，不过扫描也不许过」
3. `p0-measurements.md` 顶部横幅：「正文写了本机私有 CLI 工具名与凭证文件的字段构成」

## 决策

**评审循环 15 份文档 + `docs/决议/` 16 份 ADR 全部进 ALLOW 白名单，随公开仓发布。**
公开仓文件数从 103 增到 130。

**`docs/` 下唯一仍排除的是 `LOCAL.md`**，理由有三条且都还成立：
本机 git 身份（含公司邮箱）、凭证文件的值形态示例、公司安全代理域名。
它是本机操作手册，不是项目知识。

继续排除的还有 NEVER 名单里那七项：登录态适配器源码、全量缓存、凭证本体、
`publish.sh` 与 `scan-leaks.js` 自己（后两者的脱敏模式表写明了
「这台机器上哪些串算痕迹」，发布它们等于公开一份绕过指南）。

## 理由

### 一、三条排除理由经核实全部过时

**决议目录那条自我矛盾。**它说博主昵称与 `data/subscriptions.json` 同级处理，
「后者在 NEVER 名单里」。但 0009 在 2026-09-13 已经把订阅清单从 NEVER 翻转到 ALLOW，
理由是「这个项目要成为别人也能直接用的开源项目，清单就是产品的一部分」。
实扫确认公开仓里的 `data/subscriptions.json` 带着 271 个源的博主昵称
（样本首条即含昵称）。**同一类信息只挡决议、放行清单，是自相矛盾的**——
挡住的那份反而信息量更小。这条理由写于 0009 之前或同期，此后没人回头核。

**review 文档那条的前提被证伪。**它说文中写了「本机私有 CLI 名」。
实测：那是 npm 公开包 `@jackwener/opencli`，license Apache-2.0，
仓库 `github.com/jackwener/opencli`，maintainer 是第三方（非本项目作者）。
本机 `opencli --version` 输出 1.8.7，与 `npm view @jackwener/opencli version` 一致，
即装的就是公开包，不是私有工具。
至于「凭证文件名」——文中出现的是路径字符串，**凭证值从来不在文里**。

**p0-measurements 那条把两件事混了。**「凭证文件的字段构成」指的是
cookie 里只有 `z_c0` 没有 `d_c0` 这个发现。那是**字段名的有无**，
不是字段的值，本身是 RSSHub 公开文档里的事实。CLI 名同上。

### 二、翻转不等于放宽标准：删规则与豁免的界线

扫描器里那条把该 CLI 标为「本机私有 CLI 工具链」的规则，理由被证伪了。
处理方式是**删规则**，不是加豁免。界线是：

- **规则理由被证伪 → 删规则**，并在注释里留下核实证据（包名、license、仓库、
  版本一致性）。留着一条错误规则会让正当内容天天误报，而误报多了就没人看扫描结果
- **规则正确但子串匹配撞上公开事实 → 钉行豁免**。例如凭证环境变量名规则命中的
  其实是 RSSHub 的公开变量名（复数形式，子串包含关系）。这种豁免钉到「行内精确子串」，
  改动那一行任何文字都会让豁免失效并重新报警

**删规则后立即做安全回归**：构造一份含凭证值、公司域名、公司邮箱、本机 git 身份、
本机绝对路径、知乎 url_token 与昵称、其他本机工具名的样本，
确认凭证类三条规则一条没动、其余命中全部照旧被抓。
**删一条错规则不能顺手削弱真规则的覆盖**，这一步是强制的。

钉行豁免这个机制本身是这次新加的。此前扫描器只有高熵串有 `EXEMPT`（精确匹配 + 理由），
固定串模式没有豁免出口，撞上误报只能改文档绕着写或删规则。
现在有了窄口子，但它刻意做得很窄：钉到行内子串，文档一改就失效。
这是有意的——避免养成「扫描失败就加一条豁免」的习惯。

### 三、白名单逐个文件列，不用目录通配

`docs/` 下现在只有一个文件不发布，但 ALLOW 里仍逐份列出 31 个路径，
没有写成整个目录。理由是白名单的意义在于**新文件默认不出去**：
用目录通配等于把默认值反过来，将来往 `docs/` 里丢一份本机笔记就会被自动带出去，
而且不会有任何报警。多写十几行的代价换这个性质，值。

## 后果

- 公开仓新增 27 份文档、8152 行。评审循环的完整推理过程（含两次自我纠错、
  一次被外部评审人推翻）现在对外可见。这是这个项目的真实价值之一：
  结论可以复核，错误的路径也留了痕
- **三份外部评审人写的文档一并发布**（原始方案、实施方案 v1.0、他的第 4 轮回复）。
  发布前实扫确认其中**不含他的任何个人身份信息**，文中一律以「外部评审人」指代，
  链接全是上游项目的公开技术文档
- 改写 4 处本机绝对路径（决议 0007、0010 ×2、0011），改成 vault 内相对路径或
  「本机那份源码」这类说法。**决议的价值在推理过程，不在路径**
- 文档里所有「本机文档，不外发」的自我描述都已翻转或加注日期，
  否则公开仓里会出现自相矛盾的说明。方案主文档 §8 变更记录按项目约定
  **不覆盖历史**，保留当时的表述
- **发布不等于送达**：公开仓是给人看的存档，外部评审人未必去读。
  要他改方案仍要单独发信（`private-reader-platform-reply-r4.md`）
- 本决议自己也在发布范围内，所以「决议目录不发布」这句话在公开仓里是历史陈述，
  读者要看到 0017 才知道边界已变。这是把决策写进文件而不是留在聊天里的直接收益

## 一个自伤记录

在文档里描述「凭证类三条规则一条没动」时，把三条规则的字面量抄进了正文，
扫描器当场抓住三处。**这是设计正确的表现，不是扫描器的问题**：
模式表里的串就是不该出现在待发布内容里，包括以「我在解释这些规则」的形式出现。
已改写为不写字面量，并在原文注明这个坑，避免下一个人重犯。
