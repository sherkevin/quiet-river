# 0002 筛选要算覆盖率，简介不能当唯一证据

状态：Accepted（2026-09-12）

## 背景

按 [0001](0001-收录标准看专业性不看活跃度.md) 的标准，从知乎 905 个关注里入库了 5 个
源之后，被问了一句"你确定都排查完一遍了吗"。

一算就发现没有。当时的流程是：905 人按"昵称 + 简介"粗筛出 208 个候选，再对候选做
标题级实扫。这个流程有三个洞：

1. **90 人简介是空的**，其中 82 人连候选都没进。对这批人，粗筛等于零证据——
   没简介不等于没内容。
2. 208 个候选里只有 114 人真的被扫了，**76 人从未进入第二轮**，还有 18 人抓取失败
   后没有重试。
3. "扫过了"这个状态没有落盘成可核对的集合，所以缺口是靠回忆发现的，不是靠对账。

补扫 175 人（76 未扫 + 18 失败 + 82 无简介被丢，去重去在库）之后，结论是原判断
基本站得住，但站得住的理由变了：不是因为粗筛准，而是因为**补扫证明了粗筛没砍错**。

## 决策

**筛选类任务必须交付覆盖率账目，而不只是结论。**

这套账目做成了 `tools/zhihu-coverage.js`，只读已落盘的 JSON，不发请求也不读 cookie，
跑一次就输出上面三项。有漏网时退出码非 0，可以直接挂在检查里。

具体三条：

1. **算式要能闭合**：总数 = 实扫 + 确认无内容 + 靠文本排除，三项相加必须等于总数。
   本次闭合结果：905 = 319 实扫 + 13 注销/空号 + 573 文本排除。
2. **对"靠文本排除"的那部分做一次反向抽查**：用一个明显更宽的词表重扫一遍，
   看漏网的有多少。本次用宽到包含 `engineer`/`AI`/`增长`/`data` 的词表扫 578 个
   未实扫者，命中 21 人，其中 16 人已在库，剩下 5 人全部标题级实扫复核，
   命中率 0%。另外按机构号/大厂职衔维度再扫一遍，命中 46 人，全是美食、医学、
   法律、IC 后端、考研类，无搜广推。
   这一刀也证明了一件反直觉的事：**粗筛那一刀本身没砍错**——被丢掉的 697 人里
   简介带搜广推核心词的只有 13 个，而这 13 个全都在库里（当初是作为重复项排除的）。
3. **空简介的人不许靠文本排除**，必须实扫或者明确记账为"无内容"。

判定门槛仍沿用 0001 的 `coreRatio >= 15%`，本次没有改动。

## 一个边缘案例：琦琦

补扫唯一的非零命中是琦琦（`yang-ru-qi-3`），简介只写了"一个爱跳舞的程序猿"，
被粗筛当无信号丢掉。实扫结果是 5/59 = 8.5%，命中词为推荐系统/推荐算法/生成式推荐。

**判定不加。** 两个理由：8.5% 低于 0001 的 15% 门槛；而且那 5 条都是观点性讨论
（"生成式推荐是不是伪范式"这类），他的主线是大模型训练、医疗时序信号、旅游攻略
和育儿。0001 里"命中部分本身要有质量"那半句，在他这儿不成立。

这个案例同时说明粗筛确实会漏人——简介为空或写得不相关的人里藏着真博主是有可能的。
本次的运气是：漏掉的那个人没过线。

## 后果

- 已扫集合落盘成可对账的 JSON（`data/experiments/`，gitignored），下次追问
  "扫全了吗"跑一次 `tools/zhihu-coverage.js` 就能回答，不用回忆。
  写这个脚本时它自己抓出一个误报（把一个早已入库的源标成"零证据待扫"），
  说明对账逻辑本身也需要被复核。
- 新增 `tools/zhihu-gap-resume.sh`：标题级脚本退避超过 5 次会自己停手保 cookie，
  但它没有续跑能力。这个脚本从已有结果里挑出没扫成功的人重新组批，把"续跑"
  做成一步。它和 `zhihu-coverage.js` 都不读 cookie，但都**不在** `tools/publish.sh`
  的 ALLOW 白名单里，所以只进本机仓、不进公开仓——和它们要读的那批
  `data/experiments/*.json`（含被关注者昵称）保持同一级别。
- 成本教训：知乎限流约 17 请求 / 15 秒，30 秒一人是安全间隔。全量实扫 905 人
  要 7.5 小时以上，所以"先文本粗筛再实扫"这个分层本身是对的——错的只是没给
  粗筛这一刀算误差。
- **下次同类任务的默认动作**：粗筛之后立刻算一遍"被丢掉的人里，有多少是零证据
  丢的"，这个数字大于 0 就要么补扫要么明确写进结论。
