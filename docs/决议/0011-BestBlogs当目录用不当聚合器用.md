# 0011 BestBlogs 当目录用，不当聚合器用

状态：Accepted（2026-09-14）

## 背景

[0010](0010-wewe-rss这条路死了因为转发服务是闭源单点.md) 证死 wewe-rss 之后，公众号只剩
wechat2rss 免费目录一条路，覆盖率低（18 个目标号只命中 1 个）。同时用户点名要「关键的技术
博客，特别是大公司的技术公众号和分享博客」，并问 X 能不能接——库里 X 一行写的是
「❌ 不支持，Nitter 已死」。

[ginobefun/BestBlogs](https://github.com/ginobefun/BestBlogs)（4023★，bestblogs.dev 的公开
镜像仓）一次性给了四样东西：另一个 wechat2rss 实例的 375 个号、160 个 X 账号的
`api.xgo.ing` 转发地址、40 个 YouTube 频道、30 个小宇宙播客，外加一个带 AI 评分的
聚合 RSS（`bestblogs.dev/zh/feeds/rss`）。

**这里有个陷阱**：最省事的做法是把那个评分 RSS 直接订进来，一条源就拿到全网高分文章。
那是聚合器思路，和本项目的立场冲突，所以要先决一件事。

## 决策

### 一、当目录用：只取「源在哪」，不取「该读什么」

BestBlogs 对本项目的价值是**一份现成的、活着的 feed 地址目录**，不是一个内容源。
所以入库方式是：从它的 OPML 里挑出符合我们自己判据的具体账号，逐个 `verifyFeed`
验证（HTTP 200 + 有条目 + `pubDate` 新鲜 + 标题是真文章），再各自建一个订阅。

**明确不订 `bestblogs.dev/zh/feeds/rss`**（那条评分聚合流，`category=ai&minScore=85` 之类）。
三个理由：

1. **排序权在它手里。** 六维 AI 评分决定哪些文章进流，这正是本项目要摆脱的东西——
   README 第一段写的就是「没有推荐算法，你关注谁就看到谁」。订一条别人筛过的流，
   等于把选择权换给了另一个推荐系统，只是它没有广告。
2. **源会丢。** 聚合流里看不到「这是谁写的」，同一作者的文章被拆散、按分数进进出出。
   本项目的河是按源组织的（每个博主有专属页 `#/author/<id>`），聚合流进不了这个结构。
3. **重复计数。** 它收录的文章大量来自我们已经直接订的源（机器之心、PaperWeekly、
   各厂技术号），订它等于同一篇出现两次，而 itemId 是按 feedUrl 算的，去重不了。

同理**不接** OpenAPI v2 / `@bestblogs/cli` / 那 25 个 agent skills：都要 API Key，
而 RSS 端点已经免费够用。要 Key 的东西进来就多一个要续的凭证，违反
[0010](0010-wewe-rss这条路死了因为转发服务是闭源单点.md) 的教训——少一个外部依赖就少一个单点。

### 二、两个 wechat2rss 实例都要认，因为是互补不是替代

`wechat2rss.xlab.app`（395 个号）和 `wechat2rss.bestblogs.dev`（375 个号）
**只重叠 23 个名字**。只查一个会漏掉一半，而且漏的正好是我们要的那一半：
大厂技术号（快手技术、大淘宝技术、小红书技术REDtech、百度Geek说、蚂蚁技术、
京东技术、腾讯技术工程、滴滴技术、vivo互联网技术）**基本只在 bestblogs 那个实例里**。

所以 `lib/resolve.js` 的识别从「单个域名硬编码」改成 `RELAY_HOSTS` 表 +
`relayOf()`，两个实例并列。匹配仍按点边界，`evil-wechat2rss.bestblogs.dev`
和 `wechat2rss.xlab.app.evil.example` 都不认（测试里有这两条回归用例）。

**两个实例的返回条数不同**：bestblogs 每源 10 条，xlab 20 条。这不是配置问题，
是服务方各自的取舍。影响是公众号卡片能往回翻的深度减半，可接受。

### 三、X 从「无路可走」翻成「有转发可走」，但档位仍是第 3 档

`api.xgo.ing` 把 X 账号转成标准 RSS。2026-09-14 实测 22/22 个账号 HTTP 200、
每源 50 条、`pubDate`/`guid`/`link`/`author` 齐全、最新文章在当天。据此入库 34 个。

**档位故意留在第 3 档**，不因为「贴地址就能抓」提到第 1 档：平台本身仍是登录态墙，
能抓到只是因为有个第三方在转发。`resolve` 因此在成功结果上带一条 note，说清楚
这是第三方转发、服务方下线源就断。这条 note 不是免责声明，是给半年后的自己看的——
wewe-rss 当初也是「贴地址就能抓」。

两个实现细节：

- **哈希不可由 handle 推导**。试过 `md5(handle)` 与小写变体，都不是；
  `/rss/user/karpathy`、`?screen_name=`、`/api/user/` 等猜测路径全 404 或返回
  `{"success":false,"code":"xgo-9999"}`。所以只能从现成目录取地址，
  添加页的「X / Twitter」卡收的是转发地址而不是 handle。
- **`url` 存 `x.com/<handle>`，feed 存转发地址**。卡片上的「去主页」该跳作者，
  且跳转不该随服务方改域名而失效。连带改了 POST 的重复判定（要比到 `feeds`，
  否则同一条转发地址换个贴法就会建两个源）和 PATCH（补 feed 地址时别把 `url`
  覆盖成转发地址）。

源名从频道标题 `Sam Altman(@sama)` 拆成 `Sam Altman（X @sama）`，
与库里既有的「王树森 ShusenWang（B站）」同构。

**一个分支顺序的坑**：`resolve` 里原本「地址以 `.atom/.rss/.xml` 结尾就按直连 feed 验证」
这条规则排在最前面（理由是对的：用户显式贴 `commits.atom` 时不该被 GitHub 仓库的
「只订 release」默认覆盖）。但 wechat2rss 的地址正是 `…/<sha1>.xml`，会被那条规则先接走，
于是公众号源拿不到「这是第三方转发」的 note，而 X 源（地址无扩展名）能拿到——
**同样脆弱的两类源，只有一类被告知了脆弱性**。
修法是把转发宿主检测挪到 `.xml` 直连分支之前。不会误伤那条规则：转发宿主只会吐 feed，
不存在「显式贴 commit 流覆盖平台默认」这种情况。改完实测三类都对：两个 wechat2rss
实例都带 note，`github.com/.../commits.atom` 仍走直连分支且 platform 仍是 github。

教训是**「按后缀判断地址类型」和「按宿主判断来源性质」是两条正交的规则，谁先谁后决定
哪一类源会漏掉说明**。这次漏的是说明文字不是抓取，代价小；如果漏的是抓取就会更难查。
### 四、给第三方宿主单独设节流

`lib/refresh.js` 原本只给知乎与 Reddit 设了请求间隔和重抓周期。这次一次性给
同一个第三方宿主加了 34（xgo）+ 45（bestblogs wechat2rss）个源，不设节流就是
一轮刷新里连续砸人家几十次。加了：

| 宿主 | 请求间隔 | 重抓周期 |
|---|---|---|
| `api.xgo.ing` | 1.5 秒 | 30 分钟 |
| `wechat2rss.bestblogs.dev` | 1 秒 | 30 分钟 |

同宿主串行（既有机制）只保证不并发，不保证不打得太密——这句话是文件里原本就写着的，
这次是它第二次被用上。推文和公众号文章都不按分钟变，转发服务自己也带缓存
（bestblogs 那个 `max-age=600`），半小时足够。

**注意重抓周期对 `force` 也生效**（和知乎那条规则一致，代码里原本就这么写的）。
所以手动点「刷新」半小时内不会重打第三方。想立刻重拉只能删源重加，
这是有意的取舍，不是 bug。

### 五、公司技术博客按「在做 vs 在说」筛，资讯媒体不收

BestBlogs 的 170 个文章源里有大量 AI 资讯号（量子位、InfoQ 中文、机器之心、
AI前线、智东西）。按
[0004](0004-词表要随批次修，判据是一手还是转述.md) 的判据「看作者是在做，还是在说
别人做了什么」，这些是**在说**，不收——即使它们分数高、更新勤。

据此从 170 个源里只挑出 8 个直连博客入库：Google Research Blog、
Microsoft Research Blog、Apple Machine Learning Research、AWS Machine Learning Blog、
GitHub Engineering、Spotify Engineering、Latent Space、Simon Willison's Weblog。
前六个是公司自己的研究/工程一手记录，后两个是个人一手实践。

两个边界判断记下来：

- **Spotify Engineering 与既有的 Spotify Research 不是重复**：实测两个 feed 的
  guid 完全不同，Engineering 在写 A/B 测试与数据湖索引（「Why Spotify Is Not Using
  Bayesian A/B Testing」），Research 在写生成式推荐与多目标平衡。都收。
- **Apple Developer News 不收**：142 条全是「App Store submissions now open」
  这类平台公告，是发布记录不是文章，和 GitHub 仓库默认不订 commit 流同理。

### 六、YouTube 40 个与播客 30 个这轮不收

不是判据不合格，是**优先级与噪音**：40 个里大量是 AI 资讯类频道（Matt Wolfe、
Wes Roth、AI Explained）与创业访谈（My First Million、Lenny's Podcast），
按 0004 属「在说」。合格的那几个（Hung-yi Lee、Andrej Karpathy、Two Minute Papers、
ByteByteGo）留到下一轮单独看，避免这一批一次性把库从 188 推到 300+ 之后
tag 分布失控、河被视频标题冲淡。

播客那 30 个走 `rsshub.bestblogs.dev/xiaoyuzhou/...`。实测该公共 RSSHub 实例
的小宇宙路由可用，但 **bilibili 路由超时、zhihu 404、weibo 超时**——是个受限实例，
不能拿来替 `rsshubBase`。而且本机 RSSHub 已经能跑小宇宙路由，没必要依赖公共实例
（依赖公共实例正是 0010 那个错误的形状）。

## 后果

> 本节的源数与 tag 分布是**入库当时**的快照。同日的内容复核砍了 6 个源、
> 重打 6 个 tag，数字已变（X 34 → 28、金融量化 10 → 3、数据分析 16 → 8）。
> 最新口径见 [0012](0012-收录后要做内容复核，tag按内容定不按名声定.md)。

- 库 188 → 276 源：公众号 26 → 71（+45）、X 0 → 34（**新平台**）、博客 18 → 27（+9，
  其中 1 个是用户自己在页面上加的 Gino Notes）。条目 5392 → 7672。
- tag 分布变化：大模型Infra 42 → 90、Agent 21 → 43、推荐系统 32 → 43、
  搜广推 31 → 40、金融量化 1 → 10、数据分析 2 → 16、CV 6 → 13、NLP 14 → 22。
  「金融量化」从 1 源变 10 源，[0008](0008-小红书没有关注列表可挖，改走搜索聚合加主页实读.md)
  里「这个 tag 几乎是空的」的说法从此作废。
- **README 的 X 一行从「无路可走」翻成「走 api.xgo.ing 转发」**，公众号那段从
  「唯一渠道是 xlab.app」改成两个实例并列。添加页多了一张「X / Twitter」来源卡。
- 第三方依赖从 1 个（wechat2rss xlab）变成 3 个（+ bestblogs 实例、+ xgo.ing）。
  这是这次最大的代价，也是 0010 教训的直接重演风险：**三个都是闭源单点，
  任何一个死了，对应的源就集体变「读档」**。缓解只有节流 + 把 note 写清楚，
  没有根治办法。真要根治就得自部署，而自部署 X 抓取没有开源方案（Nitter 已死）。
- 一轮刷新变长：新增 79 个源，其中 79 个都在第三方宿主上串行 + 间隔，
  约多 2~3 分钟。仍在可用范围，但这是
  [0004](0004-词表要随批次修，判据是一手还是转述.md) 里「再往上涨就要考虑只刷新
  用户当前在看的 tag」那条预警的第二次触发。

## 顺手修的一个真 bug

`tools/zhihu-import.js` 的 `KNOWN_TAGS` 白名单里写的是「量化金融」，
而库里实际在用的 tag 是「金融量化」（`data/subscriptions.json` 与
本机 vault 的 `Contents/RecSearch/Sources.md` 都是后者）。

这正是 [0007](0007-深度学习是个筐，按阅读需求拆七个tag.md) 第四节预警过的失效模式：
白名单和实际 tag 漂移之后，下次导入挂「金融量化」会被拒（报「未知 tag」，
错误信息里列的还是旧名），而挂「量化金融」会静默建出一个孪生 tag，
UI 上两个 tag 各带一半源。改法是把白名单对齐到实际在用的「金融量化」。

## 遗留

1. **17 个手记公众号仍无解**。逐个查过两个目录，都不在里面。它们继续是
   「只登记名字、去微信里搜」的手动源。要覆盖只能接受 wechat2rss 私有部署
   （150 元/年，采集端闭源不可审计，见 `docs/wechat.md`）。
2. **三个第三方宿主的存活没有监控**。断了只会在刷新时变成 problem 条目，
   要人打开页面才看得见。可以做一个自动化的健康检查（对每个 relay 源探一次
   `verifyFeed`，失败累计到阈值就告警），但这轮没做。
3. **YouTube / 播客那 70 个源留到下一轮**，判据同第五节。下一轮做的时候要先决定
   视频源在河里的呈现——视频标题的信息密度比文章低，混在一起会冲淡。
4. **`api.xgo.ing` 的限流阈值未知**。这轮串行 + 1.2 秒间隔共打了约 80 次请求，
   没被限。批量再加源时如果撞到 429，先怀疑是自己打太密，不是服务坏了。
