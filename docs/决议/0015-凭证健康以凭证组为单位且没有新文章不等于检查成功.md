# 0015 凭证健康以「凭证组」为单位，且「没有新文章」不等于「检查成功」

状态：Accepted（2026-09-16）

## 背景

2026-09-16 实测发现：知乎 115 个源、小红书 13 个源**全部失效**，
`data/cache.json` 的 253 个缓存键里 146 个带 error，
**静默持续了约 5 天没人发现**。

诊断过程按项目既有判别法走完：知乎返回 401 `ERR_TICKET_NOT_EXIST`（认证失败而非限流）；
单点健康检查打 `/api/v4/me`（即 RSSHub 的 `check-cookie.ts` 用的同一端点）同样 401；
按「批量失败可能是限流，**单点也失败才是真失效**」判定为凭证真失效。

两个失效模式叠在一起：

1. **发现不了**。前端只在源卡片上显示 error，没有一个「整体健康」的视图；
   知乎 115 个源同时红，在时间轴上表现为「这些博主最近没发文」，
   和真的停更**在界面上无法区分**。
2. **发现得太贵**。115 个源共享同一份 cookie，失效时是 115 次独立的失败请求，
   等于拿同一个失效凭证反复敲平台的门——这本身有加重风控的风险。

外部评审人的实施方案 v1.0 §14 给了完整设计，是我们收到的七个回答里质量最高的一章。
本决议采纳它，并记下采纳的理由，以便将来不必重新推导。

## 决策

### 一、以「凭证组」而非「来源数」作为认证故障单位

共享一组登录态的来源（知乎 115 个源共享一份 cookie）视为**一个故障单位**。
发生明确认证失效时：只做**必要的一次**确认 → 暂停整组 → 发**一条聚合告警**。
不继续用其余来源重复验证。

恢复同样以组为单位：用户完成授权后先做单点验证，再渐进恢复。

### 二、「没有新文章」与「没有检查成功」必须分开

健康判定的依据是 `last_success_at` 和计划周期，**不是最近文章的发布时间**。
作者停更不等于爬虫失败；Feed 返回 HTTP 200 也不等于原平台所有帖子都已捕获。

三个时间分开保存（实施方案 §5.3）：

- `last_attempt_at`：我们上一次尝试检查的时间
- `last_feed_success_at`：成功取得有效 Feed/列表的时间
- `provider_checked_at`：上游自己声明的原平台检查时间，没有就保持空值

文章的 `published_at` 是第四种时间，不替代上述任一项。
对第三方 Feed 成功取回 304，只能说明**订阅源按其缓存状态没有变化**，
不能证明原平台刚刚没有发布内容。

### 三、状态必须分类，不允许笼统的「全部已是最新」

七种状态（实施方案 §5.3）：`RUNNING`、`SUCCEEDED_NEW`、`SUCCEEDED_NO_NEW`、
`COOLDOWN`、`AUTH_REQUIRED`、`UPSTREAM_ERROR`、`RESOURCE_WAIT`。

八类错误的分类与恢复（§14.2）：明确认证失败 / 403 或验证页面 / 429 限流 /
网络超时与临时 5xx / 返回 HTML 而非 Feed / 全文失败但列表正常 / 资源不足 /
Bridge 心跳停止。
其中「**403 不直接等同 Cookie 过期**」与项目既有约定一致：
登录态通道普遍限流，翻页太快或探测太密都会 403，退避一两分钟就恢复。

### 四、检查频率与代价

本地运行状态每 **15 分钟**检查一次，但它**只查队列和时间戳，不额外请求平台**。
认证健康**优先复用正常采集的结果**；只有在长期没有可用结果时，
才做一次低频的受控验证（即单点端点）。

目标：在系统在线、任务服务正常的条件下，认证组最长 **6 小时**有一个有效健康结论；
正常请求一旦发现明确失败**立即**记录和通知。
平台轮询保护周期较长时须在状态页说明，不保证作者更新立刻被发现。

### 五、统计口径不许美化

至少保留六个数：当前关注总数、启用采集数、健康来源数、认证失效数、
待接入数、疑似缺口数。**因错误被暂停的来源仍算在「应覆盖范围」的分母里**，
不能通过改状态把成功率做上去。

全量列表顶部有健康摘要；每次日报列出异常输入范围。
**不要求用户去翻日志才能知道知乎整体失效。**

### 六、告警内容

包含：受影响源数、最后成功时间、脱敏后的错误类别、需要用户做的操作。
**不包含**：Cookie、完整 token、签名请求、授权二维码。
二维码转发需要单独考虑敏感性，不默认发送到第三方。

## 理由

- **一 和 五 是这次 5 天静默失效的直接对症**。发现不了的根因是「停更」与「失效」
  在界面上同形（决策二解决），发现太贵的根因是故障单位选错（决策一解决），
  而即使前两条都做了，如果失效源被移出统计分母，健康率照样好看（决策五解决）。
- **决策四 的「不额外请求平台」是关键约束**。健康检查本身如果变成一轮轮询，
  就是拿风控风险换可见性，与项目「低频使用，读到 403 就停手退避，不要轮询」
  的既有底线冲突。复用正常采集结果、只在长期无结果时才单点验证，
  既拿到结论又不增加请求量。
- **这件事独立于架构选型**。无论最终走 RSSHub + Miniflux 还是保留现有适配器，
  只要还押在单一登录态凭证上，同样会静默失效。所以它排在 P0，
  且**不必等外部评审人回复就可以开工**。
- 采纳外部设计而非自己重造，是因为它比我们原本设想的「定时打单点端点 + 失败告警」
  多了三个我们没想到的点：凭证组聚合（避免 115 次重复验证）、
  检查本身不产生平台请求、以及分母不许缩小。

## 后果

- **新增一个常驻的健康检查任务**与一份健康状态存储。在现有 quiet-river 形态下
  可以很轻（一个 JSON 文件 + `server.js` 的定时器），在新架构下属于 Bridge 的
  `health` 模块（实施方案 §11.1 的八个模块之一）。
- **前端要加一个整体健康视图**，不能只在源卡片上显示 error。
  这是「发现不了」的修复点，也是六项能力之外新增的必要 UI。
- **告警通道是新的依赖**。实施方案用自建 ntfy（§9.4、§21.6），
  开启鉴权与磁盘消息缓存，`auth-default-access: deny-all`，不用匿名公开主题。
  注意它 §9.5 的诚实声明：iOS 后台即时通知、浏览器 Web Push
  **可能依赖系统推送服务**，不能描述成完全与第三方无关。
- **告警系统自身有边界**（§14.4）：ECS 整机离线时，同机告警也发不出去。
  需要外部心跳监测时，可由另一台受控设备检查——那是监控/备份角色，
  **不是默认的生产采集节点**。未增加这种监控时，文档和健康页必须说明检测边界。
- **B2（重贴凭证）与本决议是两件事**：本决议解决「下次失效能当天发现」，
  B2 解决「这次恢复」。重贴时知乎 cookie 要带 `d_c0`
  （RSSHub 的 `mergeGeneratedCookies` 只剔除 `d_c0`/`__zse_ck`，
  缺 `d_c0` 时 `z_c0` 会被丢弃）。按既有底线：频繁重登会作废旧 cookie，别轻易动。
- **验收标准**：实施方案 §17.1 的 A08（模拟 401/403/429，状态分类正确，
  共享凭证组不触发逐源重复验证）、A09（列表失败时显示来源异常而非「无新帖」）、
  A27（逐平台逐源报告，不能仅演示一个源就宣称平台全部支持）。
  本项目另加一条：**凭证失效当天就能发现**——告警真的响了，而不是事后翻日志。
