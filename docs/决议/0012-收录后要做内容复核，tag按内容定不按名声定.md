# 0012 收录后要做内容复核，tag 按内容定不按名声定

状态：Accepted（2026-09-14）

## 背景

[0011](0011-BestBlogs当目录用不当聚合器用.md) 把库从 188 推到 276 源，其中 34 个 X 账号
和 45 个公众号是**按名单批量收的**——从 BestBlogs 的 OPML 里挑出名字熟的账号，验证
feed 能抓、条目新鲜、标题像真文章，就入库了。验证只证明「这个源是活的」，没证明
「这个源值得读」。

用户打开页面看实际效果时，第一页 40 条里 X 占 35 条（88%），Gary Marcus 一个人占 17 条。
第一反应像是「X 配额太多，该限流」。但先量了一下再下结论：

- 全库 7475 条，条目年龄中位数 **194 天**，p90 达 1542 天。
- X 源每源稳定 50 条、30 分钟重抓一次；知乎/公众号源大量条目停在几个月前。

**所以「第一页全是 X」不是配额问题，是新鲜度问题**：X 是唯一在持续产新条目的平台，
按时间倒序排，它自然浮在最上面。这条河的设计就是时间倒序
（[0001](0001-收录标准看专业性不看活跃度.md)），不做配额、不做加权。真要改变首页构成，
要么让别的源更新更勤，要么砍掉产噪最多的高频源。后者才是这一轮实际做的。

于是补了一轮**入库后内容复核**：逐源读标题，按 [0004](0004-词表要随批次修，判据是一手还是转述.md)
（一手 vs 转述）、[0005](0005-收录范围再扩到跨领域干货，判据加一条导流.md)（导流剔除）、
[0007](0007-深度学习是个筐，按阅读需求拆七个tag.md)（tag 诚实度）三把尺子重判。

## 决策

### 一、复核要看标题，不看简介，也不看名字

0011 的验证步骤是机械的（HTTP 200 + 有条目 + 新鲜），漏掉的正是内容判据。
这一轮逐源读了标题，砍掉 6 个源：

| 源 | 平台 | 标题实证 | 违反 |
| --- | --- | --- | --- |
| 格兰投研 | 公众号 | 「周一，开盘必读！」「巨鲸，又要上市了？」全是标题党，无一篇量化研究 | 0004 转述 |
| 饭统戴老板 | 公众号 | 「永远不要低估小米」「董建华的狮子山下」商业叙事散文 | tag 不诚实 |
| 香帅的金融江湖 | 公众号 | 同一篇「2026 财富展望——换轨」重复 4 次，其余是散文 | 0004 + 重复 |
| 阿里研究院 | 公众号 | 「Qwen3.8 正式开源」「Wan3.0 正式上线」产品发布公告 | 0004 在说不在做 |
| 神经现实 | 公众号 | 「50 天神经科学实战：常青藤终身教授指导」课程导流 | 0005 导流 |
| Gary Marcus | X | 「translation: we will go as fast as we can…」「Just a little poll on the future of humanity」全是 AI 行业评论与骂战 | 0004 转述 |

Gary Marcus 这一刀是本轮最贵也最关键的判断。他是知名 AI 批评者，名字够响，50 条里
18% 是回复、41 条像「干」内容——按 0011 的机械验证他完全合格。但逐条读下来，
内容是**评论别人的评论**：转译 Dario 的表态、开民意调查、预告自己即将发的文章、
讨论中美 AI 竞赛。这是「在说」，不是「在做」，而且他一个人吃掉首页 17/40。

### 二、同一个判据，反向要用：LeCun 的 60% 噪声不构成砍的理由

复核时 LeCun 噪声率最高（60%，含「Tired of winning」梗图、「GOAT」、表情符号刷屏），
按 0003 的 dryRatio 尺子早该出局。但他剩下那 40% 是：

- 「Using optimization at inference time is a foundational concept of Energy-Based Models」
- 「it's not merely physical agents, it's anything that deals with something else than sequences」
- 「For about 10 years now, I have argued that the *only* way forward is…」
- JEPA vs 生成式架构的长讨论、对世界模型的论述

**这是提出 EBM/JEPA 的人本人讲他自己在做的研究方向**，是一手里最一手的那一档。
所以判据是「干的占比够不够 + 干的那部分是不是本人一手」，不是「噪声率超没超阈值」。
噪声率高但干的部分是一手研究者本人 -> 留；噪声率低但全是转述评论 -> 砍。
这条和 [0004](0004-词表要随批次修，判据是一手还是转述.md) 第二节「占比低不等于不收，
要看低在哪里」是同一个意思，只是这次用在了 X 账号上。

同理保留：Jeff Dean（28% 噪声，KDD 演讲实录、训练细节）、Karpathy（34%，
但 pelican test 的实测方法是有信息量的）、Fei-Fei Li / Jim Fan / Demis Hassabis /
Thomas Wolf（都是本人在讲自己团队的发布与技术判断）。

### 三、tag 按内容定，不按名声定——6 个源重打 tag

0011 批量入库时，tag 是按账号的名声/领域印象挂的，不是按抓到的内容挂的。
复核后重打 6 个（PATCH `{"tags": [...]}`）：

| 源 | 原 tag | 新 tag | 依据（实读标题） |
| --- | --- | --- | --- |
| Qunar技术沙龙 | 搜广推,推荐系统 | 大模型Infra,Agent | 「AI Coding 驱动核心系统重构」「ES 分片运维实战」，无搜广推内容 |
| 携程技术 | 搜广推,推荐系统 | Agent,大模型Infra | 整个「AI 专栏」系列讲 Agent 工程实践与 Karmada 治理 |
| vivo互联网技术 | 推荐系统,大模型Infra | CV,大模型Infra | 「TinySR 轻量级扩散超分」「VINS-120K CVPR 2026」「Octopus 梯度正交化」 |
| 数据可视化 AntV | 数据分析,CV | 数据分析,Agent | 「GPT-Vis 1.0」「一句话生成图表插件」，与 CV 无关 |
| Geoffrey Hinton | 深度学习,数理物理 | 深度学习 | 25 条里过半是安大略政治、播客、书讯；数理物理不成立 |
| AK（@_akhaliq） | 生成式推荐,多模态 | 多模态,深度学习 | 「AuK 语音生成模型」「Marigold V2 扩散单目深度」，非推荐 |

这和 0011「顺手修的一个真 bug」是**同一个失效模式的两个面**：那次是
`KNOWN_TAGS` 白名单写成「量化金融」而库里用「金融量化」（词表漂移）；这次是
tag 挂在源上但和源的内容对不上（语义漂移）。两者都让 UI 上的分组失真，
而 0007 的验收标准就是「点开这个 tag 会不会觉得跑题」。

### 四、砍出洞来要用一手源补，不是用同类号补

砍掉 4 个金融类公众号后，「金融量化」从 10 源掉到 2 源（30 条），几乎空了。
用户明确要过这个领域，所以必须补。补法是找一手源，不是再找几个财经号：

- **arXiv q-fin**（`https://rss.arxiv.org/rss/q-fin`，17 条/次）——量化金融的一手就是论文。
- **arXiv cs.IR**（`https://rss.arxiv.org/rss/cs.IR`，23 条/次）——信息检索/推荐的一手论文。
  这条本来就在库里，但是 `disabled`。

### cs.IR 重启：原决议的理由已经失效，要用数据推翻而不是靠印象

这里差点写错。cs.IR 被关掉的**原始理由不是限流**，vault 的 `Sources.md` 记得很清楚：
「每日新论文流太杂，被九老师日报与 Doragd 的 arXiv 推送覆盖了」——是**冗余**，
不是抓不到。所以重启它等于推翻一条既有决议，必须先证明那个理由已经不成立，
不能因为「反正它现在是空的」就顺手打开。量了一下：

| 源 | 在河条数 | 近 7 天 |
| --- | --- | --- |
| Recsys Frontier（九老师日报） | 6 | **0** |
| 搜广推工业实践策展（Doragd） | 20 | 8 |
| arXiv · cs.IR（重启后实抓） | 23 | **23**（全部当天，年龄 0.5 天） |

两个策展源的近 7 天产出是 0 和 8，cs.IR 是 23 条且全是当天的。
再查重叠：cs.IR 那 23 篇的标题，与九老师/Doragd 条目标题的交集是 **0/23**。
**「被覆盖了」这个前提已经不成立**——策展源是人工挑选的存量，cs.IR 是当日增量，
两者不重叠。这才是重启的依据。（顺带：cs.IR 的 23 条当天新论文，也直接缓解了
第一节那个「全库年龄中位数 194 天」的新鲜度问题。）

**另一个独立发现：arXiv 的 API 限流，RSS 端点不限流。** cs.IR 原先走的是适配器，
打 `export.arxiv.org/api/query`，本轮实测 HTTP 429 "Rate exceeded"；
而 `rss.arxiv.org/rss/<cat>` 实测 HTTP 200、23 条、`pubDate` 当天。
所以顺手把它从适配器源改成普通 feed 源。代价是丢掉文章级分类标签
（适配器能从 API 拿到每篇的 `<category term>`，RSS 不给），
换来的是这个源真的能稳定刷出内容。**有内容但标签粗 > 标签细但永远空着。**

教训是两条分开的，别混为一谈：冗余判断会随时间失效（要定期重量），
而限流是通道选择问题（换端点就解了）。本轮我一开始把后者当成前者的原因，
差点在决议里写下一条错的因果。

补完之后 16 个 tag 全部非空（复核前「信息检索」是 1 源 0 条）。

### 五、顺手修了一个真 bug：PATCH 改 feed 地址不清旧 adapter

第四节要把 cs.IR 从适配器源改成普通 feed 源，第一次 PATCH 之后**毫无变化**——
刷新仍旧打 arXiv API。原因：

```js
if (result.adapter) sub.adapter = result.adapter;   // 命中就换，没命中不清
```

`lib/refresh.js` 两条刷新路径都是「有 `sub.adapter` 就走 adapter，没有才抓 `feeds`」
（`refreshAdapter(sub, cache)` vs `refreshOne(feedUrl, cache)`）。所以留着一个过期
adapter，改 feed 地址就是空操作，而且 UI 上看不出任何异常——源还在、还能刷新、
只是刷的是旧地址。

修法是把这段逻辑抽成 `lib/store.js` 的纯函数 `applyResolvedFeed(sub, result, raw)`，
里面 `if (result.adapter) sub.adapter = ...; else delete sub.adapter;`，
PATCH 处理器调它。抽成纯函数是为了能测——`test/parser.test.js` 加了两条回归：
不命中要清掉、命中要换上（外加转发地址的主页不被覆盖那条既有行为）。
26 -> 28 条测试全过。

## 后果

- 库 276 -> 271 源：砍 6（5 公众号 + 1 X），补 1（arXiv q-fin），cs.IR 由 disabled
  转活。X 34 -> 28，公众号 71 -> 66，arXiv 1 -> 2。条目 7672 -> 7475。
- **首页 X 占比 88% -> 30%**（40 条里 twitter 12、wechat 15、arxiv 7、zhihu 5、blog 1）。
  注意这是**砍高频噪源 + arXiv 每日新条目**的结果，不是加了配额或改排序。
  排序仍然是纯时间倒序，符合 0001。
- tag 分布：金融量化 10 -> 3（仍是全库最薄的一组，但 3 源都是一手/券商研究，
  比 10 源里有 5 个标题党号要好）；信息检索 1 -> 1（但由 0 条变 23 条）；
  16 个 tag 全部有内容。
- 第三方宿主依赖不变（仍 3 个）；arXiv 从「适配器 + 会 429」变成「普通 RSS + 不限流」，
  实际上**减少**了一个脆弱点。
- 流程变化：以后批量入库不能停在 0011 那套机械验证，要补一轮读标题的内容复核。
  这条已经体现在本节判据里，但还没有工具支持（见遗留）。

## 遗留

1. **内容复核仍是人工读标题**，没有工具。0004 的 `tools/zhihu-shortlist.js` +
   `rejudge` 是给知乎批量扫描用的（靠词表算 dryRatio），对 X 和公众号不适用
   （X 标题是推文正文的前 100 字，词表命中率没有意义）。要做得先有一套
   跨平台的噪声启发式，但这轮先靠人读。
2. **「金融量化」仍是全库最薄的 tag（3 源）**。砍掉的都是标题党和商业散文，
   补的是 arXiv q-fin 和中金点睛。真要厚起来，得找一手做量化的人的博客/公众号，
   而不是财经媒体。下一轮的重点。
3. **首页构成随「谁在更新」波动，这是设计使然，但缺少可观测性**。
   本轮是靠人工量 platform 占比才发现 X 吃掉 88%。可以在页面上给一个
   「近 24 小时各源条目数」的视图，让「某个源刷屏了」这件事自己浮出来，
   而不是等用户觉得首页不对劲。没做。
4. **arXiv RSS 不给文章级分类**，所以 cs.IR / q-fin 两个源的条目在
   [0007](0007-深度学习是个筐，按阅读需求拆七个tag.md) 那套文章级 tag 下是粗的
   （只能继承源级 tag）。如果以后要细分，得回到 API，那就要处理 429
   （退避重试 + 降低 max_results + 拉长刷新间隔）。
