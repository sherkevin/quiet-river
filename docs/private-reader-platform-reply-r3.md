**他的两处核心批评成立，v1.0 不能原样作为部署清单执行。问题不在你的需求，也不需要重新选择整套产品，而在我漏掉了两个具体的工程约束：Miniflux 的默认网络安全策略，以及 WeRSS 正文采集的浏览器依赖。**

我已经对照了原方案和固定版本源码。两项现成功能也得到确认，应该用来减少二次开发。**另外，我又查到一个会影响“是否必须双库存储”的关键能力：Miniflux 已经有主动导入文章的 API。**因此，工程师指出的安全问题完全正确，但解决办法不一定只能是把受限来源的文章主库迁到 Bridge。

下面是需要与你和工程师明确对齐的结论。这里评审的是你贴出的回复、会话中的 v1.0 文档和公开源码；**我没有读取你电脑上的 ADR 原文，也没有在你的 ECS 上运行测试。**

## 一、第一处阻塞：判断正确，不能靠打开私网开关修补

### 1. 原方案确实没有闭合这条链路

v1.0 §5.4 设计的是：

```text
Bridge 获取受限来源
        ↓
保存为内部缓存 Feed
        ↓
Miniflux 访问内部缓存地址并入库
```

这不是工程师误读，原文确实如此。

我重新核查了 Miniflux 提交 `76889f08…`：其抓取器在 **DNS 解析之后、TCP 建连之前**检查实际目标 IP，默认拒绝非公网地址。它不是仅检查 URL 字符串，因此把 IP 换成 Docker 服务名也不能解决。

`FETCHER_ALLOW_PRIVATE_NETWORKS` 默认关闭。打开它是放开这一类限制，不是“只允许 Bridge”。阿里云元数据地址 `100.100.100.200` 位于 Miniflux 专门识别的 `100.64.0.0/10` 范围内。工程师指出的安全冲突成立。([Miniflux][1])

**这一项我接受为阻塞，而不是普通配置遗漏。**我写了安全目标，却没有给出能在所选软件默认行为下实现它的路径。

配置应继续保持：

```dotenv
FETCHER_ALLOW_PRIVATE_NETWORKS=false
```

不能为了让内部 Feed 通了，就默认拆掉保护；也不应通过把内部缓存暴露到公网来绕过这个架构问题。

### 2. 但“禁止 Miniflux 拉内网”不必然意味着“必须两套文章主库”

工程师的方案——普通来源存 Miniflux，受限来源存 Bridge，列表统一合并——**可以成立**。我不同意的不是这个架构，而是把它视为私网限制推导出的唯一答案。

我在同一份 Miniflux 固定源码中确认了：

```http
POST /v1/feeds/{feedID}/entries/import
```

这个接口接收标题、原文 URL、正文、作者、发布时间和外部 ID，清洗传入的 HTML 后写入数据库。**这条处理路径不是让 Miniflux 再去抓 Bridge 的地址。**官方 API 文档也列出了文章导入能力。  ([Miniflux][2])

于是可以把调用方向反过来：

```text
普通来源：
Miniflux 主动拉取公网 Feed → Miniflux 入库

受限来源：
Bridge 调度采集 → Bridge 主动调用导入 API → Miniflux 入库
```

**Bridge 调用 Miniflux 的入站 API，不等于 Miniflux 的抓取器访问私网。**前者使用可信内部服务通信和 API 认证，后者才受上述抓取限制约束。

这个方向能同时保留：

* Miniflux 的默认私网保护；
* Bridge 对限流、凭证组、更新缺口的控制；
* Miniflux 对文章条目和阅读状态的统一存储。

**“采集调度由 Bridge 管”与“文章必须存 Bridge”没有必然绑定关系。**

### 3. 来源记录的创建，我也继续核到了

仅发现导入接口还不够，因为它需要已有 `feedID`。

我核查的 OPML 导入实现是“解析配置 → 校验 → 创建来源记录”，这段路径没有调用抓取器，并且支持 Miniflux 自有的 `disabled`、`crawler` 等属性。因此，可以从完整来源台账生成相应记录，禁用 Miniflux 对这些通道的自动抓取，再由 Bridge 主动提交文章。

这里不是重新采用那个会漏掉 149 个来源的旧 OPML。**迁移依据仍是完整来源台账；OPML 只是调用上游现成创建能力的一种载体。**

但我不会据此直接宣布“已部署验证通过”。正式采用前，需要做一次固定版本的接口验收：创建来源、导入、查询、重复提交、内容更新、重启恢复，以及确认没有发生意外回源。

### 4. 导入接口有两个不能忽略的副作用

源码明确显示：

**没有传 `status` 时，默认是 `read`。**

**重复导入已有条目时，仍然会执行阅读状态写入。**所以每次重试都带 `unread`，可能把你已经读过的文章重置为未读。

因此，对接约定应是：

> 首次创建明确设置未读；保存稳定外部 ID 和返回的文章 ID；后续补正文使用更新接口，不把重新导入当作通用更新操作。请求超时后先确认是否已经写入，再决定是否重试。

这正是需要通过契约测试固定的行为，不能只测试一次返回 201。

### 我对决议 0014 的建议

**保留它的安全决定：受限来源不再通过 Miniflux 回拉内部 Feed 入库。**

但在投入“双文章主库”的开发之前，**补充验证“Bridge 主动导入 Miniflux”这条现成路径**。从最小化改造的目标看，我更倾向于这条路径。

如果本地最终仍选择双库，也可以，但必须同时修改原方案 §10.1 的数据归属、全局条目 ID、分页、去重、阅读状态写入、日报候选集和备份恢复。原方案明确把全部条目和已读状态放在 Miniflux；不能仅改接入图，其他部分继续照旧。

尤其不能将“两边各取一页后拼接”当作完整推荐候选集，也不能继续把 Bridge 中的受限文章称为随时可丢弃的缓存。

## 二、第二处阻塞：WeRSS 的浏览器依赖确实漏计了

### 1. 这不是“可能要浏览器”，选定路径已经确定要用

我核查的 WeRSS 提交为 `d8feb6a4…`。

调用链确实是：

```text
gather.model = web
gather.content = true
        ↓
MpsWeb.get_Articles()
        ↓
content_extract()
        ↓
driver.wxarticle
        ↓
PlaywrightController
        ↓
打开页面并提取正文
```

`web.py` 中的正文分支和 `wxarticle.py` 中的 Playwright 页面操作都能直接确认这一点。

原方案资源表把“浏览器采集”只写成 RSSHub 的依赖，却将 WeRSS 单列为公众号采集服务。**资源表与实际调用链不一致，工程师的批评成立。**

我写一句“正文是否需要浏览器必须实测”，不能抵消资源计划里已经漏掉它的问题。

### 2. 有一个细节需要再精确一点：不能直接认定一定是 Firefox

工程师根据配置默认值提出“Chromium＋Firefox”，方向上正确地发现了第二套浏览器负载，但实际浏览器引擎还要看运行代码。

在我核查的提交中，`PlaywrightController` 构造函数默认值是 `webkit`，随后又存在 `BROWSER_TYPE` 环境变量覆盖和本地 Chrome 自动发现逻辑。**配置样例中的默认名称，不一定就是最终启动的引擎。**

因此，资源表应改成：

> **WeRSS 正文路径必需浏览器；具体引擎、浏览器版本和启动方式，以固定代码与实际启动日志共同确认。**

这不削弱他的主要结论。它只是避免下一版再次把未经确认的具体运行依赖写死。

同时，“磁盘上安装两套浏览器”和“两个浏览器同时占用内存”不是一回事。现在可以确定需要补测，**不能仅根据依赖数量就断言 2C2G 必然能跑或必然 OOM。**

### 3. “全局浏览器并发 1”必须覆盖实际任务生命周期

修正后的控制对象应包含：

**RSSHub 的浏览器任务、WeRSS 的正文任务、补抓任务，以及可能启动浏览器的授权操作。**

这里的“1”指一个浏览器作业，不是只能有一个操作系统进程；单个浏览器本身会有多个子进程。

更关键的是：

> **请求返回、请求超时、任务完成、浏览器退出，是四种不同事件。**

不能 HTTP 请求刚返回就释放名额，后台浏览器还在继续抓；也不能请求超时后，直接开始第二个任务，而第一个浏览器进程尚未终止。

所以资源验收必须前移：**在开始全量接入前，分别运行 RSSHub 与 WeRSS 的真实采集作业，再测交错执行、超时、失败和清理。**最终连续运行验收也必须包含实际会启用的 WeRSS 负载，不能只压 RSSHub。

## 三、WeRSS 的触发接口现在查到了，但这不能代替端到端验证

工程师指出的隐藏耦合也成立：**关闭原有补抓任务之前，必须证明替代链路真的能补齐正文。**

原方案对 `server.enable_job` 写了“主动触发接口验证后再关闭”的前提，却直接将 `content_auto_check` 设为 false。两者的保护条件不一致，需要修改。

### 1. 真实接口，不再留给实施者猜

在这次固定源码里，单个公众号更新接口的完整路径是：

```http
GET /api/v1/wx/mps/update/{mp_id}?start_page=0&end_page=1
```

依据是 `apis/mps.py` 的更新路由、`/mps` 路由前缀，以及应用的 `/api/v1/wx` 总前缀。它使用现有认证依赖，并调用 `get_Articles`，通过 `UpdateArticle` 回调处理文章。

这是一个有副作用的 GET 接口。因此，应由 Bridge 后端调用，不作为普通网页链接让浏览器预取，也不能被反向代理缓存。

### 2. “有接口”和“接口调通”还不是完整结论

源码中有些底层错误会被捕获、记录，随后返回空内容或结束循环。上层不一定接收到异常，所以可能继续包装成功结果。

因此，不能只检查：

```text
HTTP 是 200 → 更新成功
```

而应检查：

```text
认证或平台检查是否成功
        ↓
列表是否真的完成检查
        ↓
新条目是否入库
        ↓
需要正文的条目是否完成提取
        ↓
失败项是否进入可见、可重试的状态
```

还必须专门测试：

> **第一次发现文章时正文失败，下一次触发能否补齐？**

因为列表路径有“是否已经采集过”的判断，重新刷新列表不必然等于重新处理空正文。不能关闭补抓后，仅凭正常文章首次成功就认为补偿能力也完成了。

### 3. 配置关闭的最终条件

我的修正决定是：

**保留“只由一处调度”的目标，但将关闭上游任务作为验收后的操作，而不是初始化时无条件执行。**

只有显式触发、完成判定、失败补偿和浏览器退出都验证通过，才关闭对应的上游自动任务。验证期间在隔离测试状态下运行，不能让两套生产调度同时抓同一批来源。

## 四、两个复用机会应当直接采纳

### 1. 常规正文提取交给 Miniflux，不再为 Bridge 写通用提取器

工程师说的能力存在。

固定源码中的处理流程会在启用 `crawler` 时调用 `scraper.ScrapeWebsite`；提取器支持 CSS 规则和 Readability。处理层只有在没有提取错误且内容非空时才替换原有正文。

因此，应该明确分工：

**Feed 已有完整正文：优先保留。**

**适合匿名访问的规整文章页：使用 Miniflux 原生提取或按源配置 CSS 规则。**

**登录态、反爬或动态页面：继续由已验证的专用采集通道处理，不让通用提取器承担它做不到的事。**

工程师提出的约 40 个源，是很好的**首轮候选集合**，不是已经确认的 40 个成功覆盖源。例如 GitHub 的不同 Feed 类型，未必都是适合按文章正文提取的页面。

这里能删除的是 **Bridge 通用正文抓取与提取引擎的开发任务**；HTML 归档导入、来源映射、状态判定和批注版本保护仍然需要。

另外两条边界不能遗漏：

**使用同一个 Miniflux 抓取器，不代表自动继承 Bridge 自定义的八秒间隔、凭证组预算等策略。**正常来源和受限来源仍要按各自调度约定执行。

**不要拿 Miniflux 的保留／屏蔽规则来做兴趣推荐。**源码中这些过滤会影响文章是否进入结果集合；你的要求是先保存已发现内容，再排序，而不是兴趣低就不入库。

### 2. Karakeep 跨文章高亮列表是已知能力，不应继续列为不确定

我直接读取了 **v0.33.2** 的高亮路由，确认它调用 `highlights.getAll` 并处理分页；官方接口说明也是返回当前用户跨书签的高亮集合。 ([Karakeep][3])

所以原方案 §7.1 应修改为：

> **使用 Karakeep 已有的高亮集合接口，Bridge 最多承担入口、来源信息关联和导出，不再设计另一套高亮主库。**

但需要保留一个精确边界：**“全部高亮”不自动等于“全部类型的笔记”。**整篇书签备注、独立文本笔记与附着在高亮上的备注，仍要分别确认 A15 的展示与导出范围。

这项改动是减少不必要的开发，不是取消“我的笔记”的验收。

## 五、我额外发现了一个需要在真实凭证接入前处理的风险

WeRSS 的 `main.py` 在直接作为入口运行时，存在如下逻辑：

```python
for k, v in os.environ.items():
    print(f"{k}={v}")
```

它会遍历打印环境变量。**若采用这个入口，并通过环境变量注入 Cookie、密钥或数据库凭证，就存在凭证写入启动日志的风险。**这段输出不是由 `debug` 配置保护的。

我没有证据说你的凭证已经泄漏；这是对固定源码中条件性风险的判断。

处理要求应写入实施清单：

**接入真实凭证前核查入口，删除这类全量输出或改成明确的非敏感白名单。**使用假密钥做启动测试，确认日志不包含它们。

如果需要一个很小、可审计的安全补丁，可以接受。**“尽量不改上游”是降低维护成本的原则，不应该成为明知会输出凭证仍照原样部署的理由。**

同样，Miniflux 保持私网保护，并不意味着 Bridge、浏览器和图片下载器天然安全。它们仍需要阻断不可信 URL 指向云元数据、宿主机和无关内部服务。只是固定配置的内部 API 调用与不可信文章 URL 获取，必须使用不同的权限边界。

## 六、实施顺序需要调整，但不重新推翻需求和选型

工程师采纳的决议 0015，我继续支持：**凭证组是故障单位、检查成功时间是健康依据、健康巡检本身不向平台发请求。**

既有简报已经说明，128 个登录态来源曾静默失效约五天。这项修复确实应先于推荐和日报，而不是被放到迁移尾声。

P0—P5 不需要重新命名，但依赖验证必须前移：

| 阶段             | 必须调整的内容                                                        |
| -------------- | -------------------------------------------------------------- |
| **P0：资产与依赖验证** | 固定源码／镜像版本；采纳凭证组状态；验证 Miniflux 主动导入链；核查 WeRSS 实际浏览器、入口日志和单源更新接口 |
| **P1：阅读核心**    | 用脱敏样本跑通正文导入、高亮集合、已读状态、备份恢复；确认核心资源基线                            |
| **P2：来源接入**    | 在前述接口与资源检查通过后接入真实来源；RSSHub 与 WeRSS 共享实际可执行的浏览器任务预算             |
| **P3：内容与笔记**   | 复用 Miniflux 提取和 Karakeep 高亮，集中实现补齐、冻结、映射和导出                    |
| **P4：推荐与日报**   | 继续在本地全部已发现的订阅内容上排序，不引入第三方筛选                                    |
| **P5：切换与连续运行** | 最终资源验收覆盖实际启用的全部采集任务；故障、重试、浏览器清理与恢复都进入测试                        |

**阶段前移不代表推迟公众号或删除小红书需求，而是不能等上层功能做完，才发现底层采集根本启动不了。**

版本记录也要修正：仓库提交 SHA、文件 blob SHA、发布标签、镜像 digest 分开记录。前面用主分支文件支持 v0.33.2 的判断，即使这次差异不影响结论，也不应继续作为标准做法。

## 我的最终处理意见

**接受并必须修改的部分：**

私网缓存回拉设计、WeRSS 浏览器资源清单、关闭自动补抓的前置条件、阶段顺序，以及对两项现成功能的不充分复用。

**需要补充讨论而不是机械照搬的部分：**

“受限来源必须由 Bridge 另建文章主库”。这个方案合理，但现在有官方主动导入 API 的源码证据，**应先验证能否通过改变调用方向解决问题，而不是直接承担双库分页、阅读状态和备份的一致性成本。**

**本轮新增的风险：**

WeRSS 启动日志可能输出环境凭证，以及文章导入接口默认已读、重复导入可能重写阅读状态。这些也要写进测试，不能留到上线后发现。

我建议给本地工程师的回应可以归结为：

> **两处阻塞认可，0015 保留；0014 的“不再让 Miniflux 回拉内部 Feed”安全目标认可，但请补测官方主动导入路径，再决定是否需要双文章主库。WeRSS 的浏览器依赖和任务关闭条件前移验收；正文抽取与高亮集合直接复用上游能力。**

**下一版要修的是调用方向、资源生命周期和接口契约，不是再写一份看起来更完整、却把关键条件继续留给实施者猜测的架构说明。**
